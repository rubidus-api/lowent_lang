# codec — 바이트 코덱 (hex · base64)

소스: `lib/codec.low` · 검증: `impl/tests/vm_codec.low`

## 처음 쓰는 사람에게

이 절은 이 모듈이 무엇이고 언제 쓰는지를 한 화면에 담는다. 나머지 절은 여기서 나온 말을
자세히 풀어 놓은 것이다.

**무엇을 하는 모듈인가.** 바이트를 hex 나 base64 **글자열로 바꾸고 되돌리는** 모듈이다.

**왜 이런 변환이 필요한가.** 세상에는 **텍스트만 통과시키는 자리**가 많다 — 설정 파일 한
줄, 로그, URL, 메일 본문, 화면 출력. 그런 자리에 바이트를 그대로 넣으면 0 바이트나 제어
바이트가 끼어 통로가 망가진다. hex(16진 표기 — 바이트 하나를 `0-9 a-f` 두 글자로 적는
방식)와 base64(임의 바이트를 `A-Z a-z 0-9 + /` 64가지 글자로 적는 방식)는 **임의 바이트를
안전한 글자만으로 나르기 위한 포장지**다. 포장을 벗기면(디코딩) 원래 바이트가 그대로
돌아온다.

**둘의 차이.** hex 는 사람이 읽기 좋지만 크기가 정확히 2배가 된다. base64 는 읽기는
어렵지만 약 4/3 배로 끝난다. 해시값을 눈으로 볼 때는 hex, 덩어리를 실어 나를 때는
base64 가 보통이다.

**언제 쓰나.** 설정 파일에 바이너리를 담아야 할 때, 해시값을 사람이 읽게 찍을 때, 텍스트만
오가는 통로로 바이트를 보낼 때 쓴다.

**최소 예제.** 아래가 이 모듈을 쓰는 가장 짧은 꼴이다. 각 줄이 무엇을 하는지는 주석에 적었다.

```lowent
use codec as c .

rem 바이트 3개를 hex 로 — dst 는 2배 크기(6)가 필요하다.
rem dst 는 이 모듈이 만들어 주는 것이 아니라 **호출자가 미리 잡아 두는 출력 자리**다.
let n option u64 . be c.hex_enc "abc" dst .
guard is_some n . else return 1 .          rem 자리가 모자라면 none 이다
rem 이제 dst 의 앞 6바이트가 "616263" 이다.
rem n 은 **실제로 쓴 바이트 수**다 — 결과는 dst 통째가 아니라 dst[0..n) 이다.
```

**세 낱말만 먼저.** 이 문서는 아래 셋을 계속 쓴다.

- **`option`** — "값이 있을 수도, 없을 수도 있다" 를 나타내는 타입이다. 이 모듈에서 실패는
  예외도 오류 코드도 아니고 **`none` 이라는 값**이다. 성공이면 `some <쓴 바이트 수>` 다.
  받는 쪽은 `guard is_some x . else …` 로 한 줄에 가른다.
- **전량 아니면 무** — 인코더는 출력 자리가 모자라면 **한 바이트도 쓰지 않고** `none` 을
  낸다. 절반만 쓴 결과를 주면 그 뒤의 모든 층이 "다 됐다" 는 거짓 전제 위에 서기 때문이다.
- **패딩 `=`** — base64 는 입력을 3바이트씩 묶어 4글자로 적는다. 마지막 묶음이 3바이트를
  못 채우면 모자란 자리를 `=` 로 메워 **길이를 항상 4의 배수로 맞춘다**. 디코더는 `=` 개수를
  보고 원래 길이를 되찾는다.

**읽는 순서.** 급하면 «op 한눈에» 표만 봐도 된다. 왜 이렇게 생겼는지가 궁금하면 «왜 있는가»부터, 실제로 쓰다 막히면 «반례»와 «주의사항»을 먼저 보면 된다.

## 왜 있는가

이 절은 **왜 이 기능이 빌트인이 아니라 라이브러리인가**를 설명한다. 답은 간단하다 — 이
변환은 바이트에서 바이트로 가는 순수 계산이라 언어의 도움이 하나도 필요 없었다.

hex 와 base64 는 바이트에서 바이트로 가는 **순수 계산**이다(RFC-0075 §5 · 3차 슬라이스 1).
capability(능력 — "세상에 닿아도 된다" 는 권한 표식) 도, 언어에 없는 표현도 필요 없다 —
실제로 이 파일은 `index·set·shl·shr·bit_and·bit_or·guard·while` 만 쓴다.
**언어는 아무것도 안 늘었다.** 그래서 빌트인이 아니라
라이브러리다: `effects none`(이 op 이 무슨 비용을 내는지의 선언 — `none` 이면 세상에 닿는
일도, 숨은 할당도 없다는 뜻이다) · 숨은 할당 0 · **출력 버퍼는 호출자의 것**(`strbuf` 과 같은
판단 — 버퍼를 마련하는 비용과 정책은 호출자만 안다).

## 설계 의도와 경계

이 절은 **실패를 어떻게 알려 주는가**와 **일부러 안 지은 것**을 밝힌다. 요지: 실패는 전부
`none` 한 가지이고, 모드 인자를 붙인 만능 op 은 만들지 않는다.

**잘못된 입력은 값으로 답한다** — `none` 하나다: 홀수 길이 hex · hex 아닌 글자 · base64
아닌 글자 · 어긋난 패딩 · **모자란 출력 버퍼** 전부. 트랩(프로그램을 그 자리에서 멈추는
실행 중단)도 잘림도 아니다 — 잘라 주면 그
뒤의 모든 층이 "다 썼다"는 거짓 전제 위에 선다. 성공은 `some <쓴 바이트 수>` — 호출자가
`subslice`(슬라이스의 일부를 잘라 내는 op)로 정확한 결과를 얻는다.

확정된 것:

- hex 인코딩은 **소문자**를 낸다. 디코딩은 대소 둘 다 받는다 — **관대한 수신, 보수적 송신**.
- base64 는 **표준 알파벳**(`A–Z a–z 0–9 + /`)과 `=` 패딩이다.

**정직하게 안 지은 것**: url-safe 변형(`-_`) · 개행 접기. 필요가 생기면 그때 **별도 op**
으로 짓는다 — 한 op 에 모드 인자를 다는 것이 곧 엔트로피다.

## 자료구조

이 절은 **출력 자리를 얼마나 잡아야 하는가**를 알려 준다. 새로 외울 타입은 없고, 표 하나가
전부다.

새 자료구조는 없다. 입력도 출력도 `slice u8`(바이트 여러 개를 가리키는 창)이고, 규약은
**출력 버퍼 크기 공식**이다. 이 공식보다 작은 `dst` 를 주면 결과는 항상 `none` 이다:

| op | 필요한 dst 크기 | 성공 반환 |
|---|---|---|
| `hex_enc` | `2 × len src` | `some (2 × len src)` |
| `hex_dec` | `len src / 2` | `some (len src / 2)` |
| `b64_enc` | `4 × ⌈len src / 3⌉` | `some (4 × ⌈len src / 3⌉)` |
| `b64_dec` | `3 × (len src / 4) − 패딩 수` | `some <쓴 바이트 수>` |

dst 가 공식보다 크면 상관없다 — 앞에서부터 쓰고, 쓴 수를 돌려준다. 빈 입력은 성공이다:
`hex_enc ""`/`b64_enc ""` → `some 0`, `b64_dec ""` → `some 0`.

## op 한눈에

이 절은 여덟 개 op 을 한 표로 훑는다. `fn` 은 값 하나를 계산해 내는 순수 함수, `proc` 은
호출자의 버퍼에 쓰는 프로시저다. 보통은 `hex_enc`/`hex_dec`/`b64_enc`/`b64_dec` 넷만 쓰면
되고, 나머지 넷(`hex_digit`·`hex_val`·`b64_digit`·`b64_val`)은 글자 하나짜리 부품이다.

| op | 종류 | 시그니처 요약 | 실패 시 |
|---|---|---|---|
| `hex_digit` | fn | `v u64 → u8` | 실패 없음(0~15 전제) |
| `hex_val` | fn | `c u8 → option u64` | `0-9 a-f A-F` 밖 = `none` |
| `hex_enc` | proc | `src slice u8, dst mut slice u8 → option u64` | dst 부족 = `none` |
| `hex_dec` | proc | `src slice u8, dst mut slice u8 → option u64` | 홀수 길이·hex 아닌 글자·dst 부족 = `none` |
| `b64_digit` | fn | `v u64 → u8` | 실패 없음(0~63 전제) |
| `b64_val` | fn | `c u8 → option u64` | 알파벳 밖 = `none` (`=` 도 `none`) |
| `b64_enc` | proc | `src slice u8, dst mut slice u8 → option u64` | dst 부족 = `none` |
| `b64_dec` | proc | `src slice u8, dst mut slice u8 → option u64` | 길이 4의 배수 아님·알파벳 밖·어긋난 패딩·dst 부족 = `none` |

## op 상세

**매개변수를 왜 받나 — 이 모듈의 규약.** 모든 변환이 `src`(읽을 바이트)와 `dst`(쓸 자리)를
따로 받는다. 제자리 변환을 안 하는 이유는 hex 는 커지고 base64 도 커져서 원본을 덮으면 아직 안
읽은 바이트를 밟기 때문이다. `dst` 크기는 호출자가 공식대로 마련하고, 모자라면 **한 바이트도
쓰지 않고** `none` 이 온다. 반환값이 "쓴 바이트 수" 인 것은 `dst` 가 더 클 수 있어서다 —
`subslice dst 0 n` 이 정확한 결과다.


이 절은 op 하나씩을 뜯어본다. 먼저 네 개의 큰 op 이 공통으로 받는 매개변수 둘이 **왜**
필요한지부터 밝힌다.

**`src` 가 필요한 이유** — 변환할 원본이다. 중요한 것은 **`src` 의 길이가 곧 입력의
전부**라는 점이다. 이 op 들은 종료 표식(`\0` 같은 것)을 찾지 않고 `len src` 만 믿는다.
그래서 큰 버퍼에 든 결과를 다시 넘길 때는 `subslice` 로 정확히 잘라 줘야 한다.

**`dst` 가 필요한 이유** — 결과를 쓸 자리다. 이 모듈이 스스로 메모리를 잡지 않기 때문에
호출자가 댄다. 그래야 **숨은 할당이 0** 이 되고(`effects none`), 스택·아레나·힙 중 무엇을
쓸지를 호출자가 고를 수 있다. `mut`(쓰기 가능) 표시가 붙은 이유가 이것이다. 결과의 길이는
`dst` 의 길이가 아니라 **반환된 `some n` 의 `n`** 이다.

**반환이 `option u64` 인 이유** — 성공/실패와 "몇 바이트 썼는가" 를 한 값에 담기 위해서다.
`none` 하나로 모든 실패를 덮는 대신, 성공이면 곧바로 `subslice dst 0 n` 을 만들 수 있다.

- `hex_digit v` — 한 니블(nibble — 4비트, 즉 0~15 범위의 반 바이트)을 **소문자** hex
  글자로. `v < 10` 이면 `'0'+v`, 아니면
  `'a'+(v−10)`. 15 를 넘는 값의 결과는 의미 없다 — 호출자가 니블을 보장한다.
  - `v` 가 필요한 이유: 바꿀 니블 값 자체다. 검사를 안 하는 대신 **호출자가 범위를
    보장**하는 거래다(그래서 실패가 없다).
- `hex_val c` — hex 글자 하나의 값. `0-9 a-f A-F` 를 받는다(대소 둘 다). 밖이면 `none`.
  - `c` 가 필요한 이유: 값으로 되돌릴 글자 하나다. `hex_digit` 의 반대 방향이다.
- `hex_enc src dst` — `src` 를 소문자 hex 로 `dst` 에 쓴다. 먼저 `2×len src ≤ len dst` 를
  검사하고, 모자라면 아무것도 쓰지 않고 `none`. 성공 = `some (2×len src)`.
- `hex_dec src dst` — hex 를 바이트로. 조건: `len src` 짝수 · 모든 글자가 hex ·
  `len src / 2 ≤ len dst`. 성공 = `some (len src / 2)`. 실패 = `none` — 단, hex 아닌
  글자는 **훑다가** 발견되므로 그 앞까지의 바이트는 이미 `dst` 에 쓰였을 수 있다. `none`
  이면 `dst` 내용은 미정으로 취급하라(성공 `some n` 일 때만 `dst[0..n)` 이 유효하다).
- `b64_digit v` — 표준 알파벳의 `v`(0~63)번째 글자. 0~25=`A-Z`, 26~51=`a-z`, 52~61=`0-9`,
  62=`+`, 63=`/`.
  - `v` 가 필요한 이유: 6비트 값 하나다. base64 는 바이트(8비트)가 아니라 **6비트 조각**을
    글자에 대응시키기 때문에 0~63 이 단위가 된다.
- `b64_val c` — base64 글자 하나의 값. 알파벳 밖이면 `none`. **`=` 도 `none`** — 패딩은
  글자가 아니라 디코더 본문이 다루는 구조다.
- `b64_enc src dst` — `src` 를 base64 로 쓴다(`=` 패딩 포함). 필요 크기
  `4×⌈len src/3⌉` 를 먼저 검사한다. 꼬리 1바이트 = `XX==`, 꼬리 2바이트 = `XXX=`.
  성공 = `some (4×⌈len src/3⌉)`.
- `b64_dec src dst` — base64 를 바이트로. 조건: `len src` 가 4의 배수 · 모든 글자가 알파벳
  또는 규칙에 맞는 패딩 · dst 충분. 패딩 규칙: `=` 는 **마지막 그룹**에만 올 수 있고,
  셋째 자리가 `=` 면 넷째도 `=` 여야 한다(`X===` 꼴은 없다 — 셋째 검사에서 걸린다).
  성공 = `some <쓴 바이트 수>` (패딩만큼 줄어든 정확한 길이). `hex_dec` 와 마찬가지로
  `none` 이면 `dst` 내용은 미정이다.

## 사용법과 예제

이 절은 실제로 돌아가는 왕복(인코딩 후 다시 디코딩) 예제 둘이다. 두 예제 모두 **버퍼 크기를
먼저 확인하고 → 변환하고 → 반환된 개수로 잘라 쓴다** 는 같은 리듬이다.

짧은 별칭 관례: `use codec as c .` (from-생략 std 해소).

```lowent
module ex_codec .

use codec as c .

rem "abc" → "616263" → "abc" 왕복. 성공 = 42.
proc hex_roundtrip output u64 . input enc mut slice u8 . . input dec mut slice u8 . . effects none . do
  rem 출력 자리를 먼저 확인한다 — 여기서 걸러야 아래 none 이 "버퍼 탓" 인지 헷갈리지 않는다.
  guard ge (len enc) 6 . else return 90 .    rem hex 는 정확히 2배: 3바이트 → 6글자
  guard ge (len dec) 3 . else return 91 .    rem 되돌리면 6글자 → 3바이트
  rem ① 인코딩: "abc" 의 바이트를 소문자 hex 글자로 enc 에 쓴다.
  let en option u64 . be c.hex_enc "abc" enc .
  guard is_some en . else return 1 .         rem none = 자리 부족(enc 를 안 건드린 상태)
  guard eq (some_value en) 6 . else return 2 .   rem 쓴 바이트 수 = 6
  rem ② 정확한 결과는 subslice 로 자른다 — 쓴 수가 곧 경계다.
  rem    enc 통째로 넘기면 뒤의 쓰레기 바이트까지 입력이 되어 none 이 난다.
  let dn option u64 . be c.hex_dec (subslice enc 0 6) dec .
  guard is_some dn . else return 3 .
  guard eq (some_value dn) 3 . else return 4 .   rem 6글자 → 3바이트
  guard eq (index dec 0) 97 . else return 5 .      rem 'a'
  rem ③ 대문자도 받는다(관대한 수신): "4A" → 74. 반대로 인코딩은 늘 소문자만 낸다.
  let up option u64 . be c.hex_dec "4A" dec .
  guard is_some up . else return 6 .
  guard eq (index dec 0) 74 . else return 7 .
  return 42 .
end

rem base64: "hi"(꼬리 2) → "aGk=" → "hi".
proc b64_roundtrip output u64 . input enc mut slice u8 . . input dec mut slice u8 . . effects none . do
  rem 2바이트는 3바이트 묶음을 못 채운다 → 한 묶음(4글자)이 나오고 끝에 = 하나가 붙는다.
  guard ge (len enc) 4 . else return 90 .
  guard ge (len dec) 2 . else return 91 .
  let e option u64 . be c.b64_enc "hi" enc .
  guard is_some e . else return 1 .
  guard eq (some_value e) 4 . else return 2 .      rem "aGk=" 네 바이트
  rem 디코딩 입력도 정확히 4글자만 넘긴다 — 길이가 4의 배수가 아니면 none 이다.
  let d option u64 . be c.b64_dec (subslice enc 0 4) dec .
  guard is_some d . else return 3 .
  guard eq (some_value d) 2 . else return 4 .      rem 패딩(=)만큼 줄어든 정확한 길이
  rem 이 시점에 dec[0..2) 가 "hi" 다. dec 의 나머지는 손대지 않은 그대로다.
  return 42 .
end
```

## 반례 — 이렇게 쓰면 안 된다

이 절은 자주 틀리는 여섯 가지와 그때 **무엇이 보이는가**(증상)를 짝지어 놓았다. 여기서는
전부 트랩이 아니라 `none` 이므로, 증상은 늘 "결과가 `none` 이고 `guard` 가 else 가지로
빠지는 것" 이다 — 화면이 깨지거나 프로그램이 멈추지는 않는다.

```lowent
rem ⓐ 홀수 길이 hex — 니블 반쪽이 남는다.
rem    증상: none. dst 는 손대지 않은 그대로다(길이 검사에서 먼저 걸린다).
c.hex_dec "abc" dst          rem → none

rem ⓑ hex 아닌 글자.
rem    증상: none. 단, 훑다가 발견되므로 dst 앞부분은 이미 덮였을 수 있다 → 버려라.
c.hex_dec "zz" dst           rem → none

rem ⓒ 모자란 출력 버퍼 — 잘라 주지 않는다.
rem    증상: none, 그리고 dst 는 한 글자도 안 바뀐다. "일부만 채워졌겠지" 는 틀린 짐작이다.
c.hex_enc "abcdefgh" dst3    rem dst3 은 3바이트, 필요는 16 → none, 한 바이트도 안 씀

rem ⓓ 길이가 4의 배수가 아닌 base64.
rem    증상: none. 흔한 원인은 enc 버퍼를 subslice 로 안 자르고 통째로 넘긴 것이다.
c.b64_dec "abc" dst          rem → none

rem ⓔ 알파벳 밖 글자.
rem    증상: none. url-safe 의 `-`/`_` 나 개행이 섞여 들어온 경우가 대부분이다.
c.b64_dec "a?cd" dst         rem → none

rem ⓕ 가운데 패딩 — `=` 는 마지막 그룹에만 온다.
rem    증상: none. 두 base64 문자열을 그냥 이어 붙였을 때 이 꼴이 된다.
c.b64_dec "aG==YWJj" dst     rem → none (첫 그룹의 == 가 마지막이 아니다)
```

전부 트랩이 아니라 **값**(`none`)이다. `guard is_some … else …` 로 받으면 된다.

## 주의사항

이 절은 초보자가 실제로 자주 밟는 함정들이다. 요약하면 셋이다 — **버퍼를 공식대로 잡아라 ·
`none` 이면 `dst` 를 결과로 쓰지 마라 · 다시 디코드할 땐 `subslice` 로 정확히 잘라라.**

- **`none` 만 계속 나오면 먼저 버퍼 크기를 의심하라.** 초보자가 가장 자주 겪는 증상이
  "코드는 맞는데 늘 `none`" 인데, 원인은 거의 항상 `dst` 를 «자료구조» 절의 공식보다 작게
  잡은 것이다. hex 인코딩은 **정확히 2배**, base64 인코딩은 **4×⌈len/3⌉** 이 필요하다.
  넉넉히 잡는 것은 손해가 없다 — 남는 자리는 손대지 않는다.
- 성능은 전부 입력 길이에 선형이고, 상태가 없으니 **재진입은 공짜**다(`effects none`).
  같은 op 을 여러 곳에서 동시에 불러도 서로 간섭하지 않는다 — 각자 자기 `dst` 만 쓴다.
- 인코더(`hex_enc`/`b64_enc`)는 크기를 **먼저** 검사한다 — 실패하면 `dst` 는 손대지 않은
  그대로다. 디코더(`hex_dec`/`b64_dec`)는 크기·형태 검사 뒤 훑으면서 쓰므로, 글자 오류로
  `none` 이 나면 `dst` 앞부분이 이미 덮였을 수 있다. **`none` 이면 `dst` 를 결과로 쓰지
  마라** — 성공 `some n` 의 `dst[0..n)` 만 결과다.
- **반환값을 버리고 `dst` 통째를 결과로 쓰지 마라.** `some n` 의 `n` 이 결과의 길이다.
  `dst` 를 그대로 다음 단계에 넘기면 뒤에 남은 옛 바이트까지 결과에 섞인다.
- `src` 의 **길이가 곧 입력의 전부**다. 버퍼에 담긴 인코딩 결과를 다시 디코드할 때는
  `subslice` 로 정확히 잘라 넘겨야 한다 — 통째로 넘기면 꼬리의 쓰레기 바이트까지 입력이
  된다. base64 라면 이 실수가 곧 "길이가 4의 배수 아님" → `none` 으로 나타난다.
- **인코딩과 디코딩의 버퍼를 같은 것으로 쓰지 마라.** `src` 와 `dst` 가 겹치면 아직 안 읽은
  입력을 출력이 덮어쓴다. 이 모듈은 겹침을 검사하지 않는다 — 결과가 조용히 틀린다.
- `b64_val` 에 `=` 를 물으면 `none` 이다. 패딩을 손으로 다루려 하지 말고 `b64_dec` 에
  맡겨라.
- url-safe base64(`-_`)를 이 op 들에 넣으면 `none` 이다 — 지원하지 않는 것이지 버그가
  아니다. 개행이 섞인 여러 줄 base64 도 마찬가지다(개행 접기는 안 지었다) — 넘기기 전에
  호출자가 개행을 걷어내야 한다.
