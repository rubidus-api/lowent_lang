# ed25519 — Ed25519 서명 검증

소스: `lib/ed25519.low` · 모듈명 `ed25519` (RFC 8032 §5.1.7 · RFC-0090 N7b⑤)

> ## ⚠ 무엇을 약속하고 무엇을 안 하나
>
> · **상수시간을 약속하지 않는다** · **감사받지 않았다** · **서명 생성 없음**.
> · `ed25519ph` · `ed25519ctx` · `ed448` 없음.
> · **공개 웹 HTTPS 서버에는 이 알고리즘을 쓸 수 없다** — 공개 CA 가 Ed25519 서버
>   인증서를 사실상 발급하지 않고 브라우저 지원도 제한적이다. 그쪽은 [p256](p256.md) 이다.
>   (이 모듈은 **상대의** 서명을 검증하는 데 쓴다.)

## 처음 쓰는 사람에게

**무엇을 하는 모듈인가.** Curve25519 와 **같은 소수** `p = 2^255 − 19` 위의 비틀린 에드워즈
곡선에서 서명을 검증한다.

**[x25519](x25519.md) 와 무슨 관계인가.** 소수가 같으므로 **체 산술을 그대로 재사용한다**
(16 조각 × 16 비트). 새 산술을 또 짓지 않았다 — *같은 소수면 같은 체다.*
다만 곡선 모양과 하는 일은 다르다: 그쪽은 키 합의, 여기는 서명 검증이다.

## ★ 에드워즈 덧셈은 완비(complete)다

확장 좌표 `(X:Y:Z:T)`, `xy = T/Z`. 에드워즈 덧셈 공식에는 **예외가 없다** —
몽고메리 사다리나 야코비와 달리 *"같은 점이면 다른 식"* 이 없다.

☞ [p256](p256.md) 의 `padd` 안에 있는 갈래가 **여기엔 아예 없다.** 갈래가 없으면 그 갈래에서
  틀릴 수도 없고, 그 갈래가 타이밍으로 새어 나갈 수도 없다. 이것이 Ed25519 가 상수시간
  구현에 유리한 이유이기도 하다 — 그럼에도 공개 웹에서 못 쓰는 것은 **수학이 아니라 생태계**다.

## ★ 애매한 입력은 거절하는 쪽을 골랐다

RFC 8032 는 **비-정규 인코딩**과 **작은 위수 점**을 어떻게 다룰지 구현마다 달라도 된다고 둔다.
여기서는 **거절한다**:

- `S < L` 을 강제한다 — 안 하면 **같은 메시지에 유효한 서명이 여럿** 생긴다(서명 가변성).
- 압축 해제가 실패하면 거절한다.

☞ 규격이 *"둘 다 된다"* 고 할 때 고른 쪽을 **적어 두는 것**이 문서의 일이다. 안 적으면
  상대 구현과 다르게 굴 때 그 이유를 아무도 못 찾는다.

## 표면

검증 하나(`verify`)를 쓰면 되고, 나머지는 그것을 이루는 부품이다.

| op | 하는 일 |
|---|---|
| **`verify`** | **서명 `sig` 가 공개키 `pub` 와 메시지 `msg` 에 맞는가** |
| `make_d` / `make_l` / `make_base` | 곡선 상수 `d` · 위수 `L` · 기저점 `B` 를 **계산으로** 낸다 |
| `eadd` / `esmul` | 점 덧셈 · 스칼라 곱 |
| `compress` / `decompress` | 점 ↔ 32 바이트 인코딩 |
| `fpow` / `feq` / `fbit0` | 체 거듭제곱 · 같은가 · 최하위 비트 |
| `pow2_minus` / `reduce_l` | `2^n − k` · `mod L` 축약 |

검증식: `[S]B = R + [k]A`, `k = SHA-512(R ‖ A ‖ M) mod L`.

## ★ 옮겨 적을 수밖에 없는 상수는 성질로 검사한다

`d` 와 `√(−1)` 과 기저점 `B` 는 **계산으로** 낸다 — 적을 것이 없다.
그런데 위수 `L` 은 유도되지 않아 **적어야 했다.**

⇒ 게이트가 **`[L]B` 가 항등원인지** 본다. 틀리게 적으면 그 검사가 깨진다.
  옮겨 적은 것을 *믿지 않고 재는* 방법이다.

## 오라클

RFC 8032 §7.1 양성 3 · **음성 6** · `[L]B = 항등원` 성질 검사. VM ≡ native.
