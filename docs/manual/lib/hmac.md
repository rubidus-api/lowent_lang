# hmac — HMAC-SHA256 과 HKDF

소스: `lib/hmac.low` · 모듈명 `hmac` (RFC 4231 · RFC 5869 · RFC-0090 N7a)

> ## ⚠ 무엇을 약속하고 무엇을 안 하나
>
> · **상수시간을 약속하지 않는다**(경계 검사와 트랩이 있다) · **감사받지 않았다**.
> · **MAC 비교는 부르는 쪽의 몫**이다 — 조기 반환 없이(바이트를 XOR 로 누적해) 비교하라.
>   먼저 다른 바이트에서 돌아오는 비교는 태그를 한 바이트씩 알아내게 해 준다.
> · `expand1` 은 **한 블록(≤32바이트)만** 낸다. 더 긴 출력이 필요하면 없는 것이다 — 아래 참조.

## 처음 쓰는 사람에게

**무엇을 하는 모듈인가.** 둘이다.
① **HMAC** — 키를 아는 사람만 만들 수 있는 증표(`mac`). *"누가 보냈는가"* 를 답한다.
② **HKDF** — 하나의 비밀에서 **여러 키를 갈라내는** 표준 방법(`extract` + `expand1`).

**왜 해시로는 안 되나.** [hash](hash.md) 의 `digest`(SHA-256)는 *"내용이 그대로인가"* 만 답한다.
누구나 다시 계산할 수 있으므로 **누가 보냈는지는 답하지 못한다.** 키가 들어가야 그 물음이 열리고,
그 자리가 이 모듈이다.

**뒷받침은 호출자가 든다**(RFC-0043 D1) — `scratch` 를 넘긴다. 크기 요구가 문서가 아니라
**가드**로 박혀 있어서, 모자라면 0 을 답하고 아무것도 안 쓴다.

## 표면

| op | 하는 일 | 요구 |
|---|---|---|
| `mac` | `HMAC-SHA256(key, msg)` → `out` 32 바이트 | `out ≥ 32` · `scratch ≥ 64 + len(msg)` |
| `key_block` | K′(64 바이트로 맞춘 키)를 만든다 | `pad ≥ 64`. 64 보다 긴 키는 **해시로 줄인다** |
| `extract` | HKDF-Extract: `PRK = HMAC(salt, ikm)` | `mac` 과 같다 |
| `expand1` | HKDF-Expand 의 **첫 블록**: `T(1) = HMAC(prk, info ‖ 0x01)` | `scratch ≥ 130 + len(info)` · **`len(info) ≤ 60`** |

## 왜 `expand1` 은 한 블록뿐인가 (그리고 왜 60 에서 자르나)

TLS 1.3 의 `HKDF-Expand-Label` 은 32 바이트 **이하**만 쓴다(키·IV·finished 전부). 그래서 T(2) 를
잇는 루프를 **안 지었다** — 필요해지면 그때 붙인다.

`len(info) ≤ 60` 가드는 더 재미있는 이유다: `msg` 가 `scratch` 안(128 부터)에 살고 `mac` 이
`scratch[0 .. 64+len(msg)]` 를 덮어쓰므로, `info` 가 길면 **그 둘이 겹친다** — 해시가 자기 입력을
밟는다. 겹치는 순간을 **가드가 거절**한다. **조용히 틀리느니 거절한다.**

## 오라클

RFC 4231(HMAC) · RFC 5869(HKDF) 표준 벡터. VM ≡ native.

## 안 지은 것 (정직히)

상수시간 보장 · MAC 비교 op · 여러 블록 HKDF-Expand(L > 32) · SHA-256 외의 해시 ·
스트리밍 MAC(조각으로 이어 먹이기).
