# tls13 — TLS 1.3 의 부품들

소스: `lib/tls13.low` · 모듈명 `tls13` (RFC 8446 · RFC-0090 N7b)

> ## ⚠ 무엇을 약속하고 무엇을 안 하나
>
> · **이것은 TLS 구현이 아니다.** 상태 기계가 **없다** — 핸드셰이크를 구동하지 않는다.
>   여기 있는 것은 규격이 요구하는 **계산들**이고, 그것을 순서대로 부르는 사람이 아직 없다.
> · **전송이 없다.** 소켓도, 재조립도, 재협상도 없다.
> · **PSK · 0-RTT · exporter/resumption 비밀 없음** — **1-RTT 한 갈래**만 지었다.
> · **PKI 없음**([der](der.md) 참조) · **상수시간 약속 없음** · **감사받지 않았다.**
> · 스위트는 **둘뿐**이고 모르는 스위트는 **거절한다.**

## 처음 쓰는 사람에게

**무엇을 하는 모듈인가.** TLS 1.3 이 요구하는 순수 계산 넷이다:

1. **키 스케줄** — 공유 비밀과 전사 해시에서 트래픽 키를 유도한다 (§7.1)
2. **레코드 계층** — 레코드를 봉하고 연다 (§5)
3. **전사 해시** — 지금까지 오간 메시지 전부의 해시 (§4.4.1)
4. **Finished** — 핸드셰이크가 중간에 안 바뀌었음을 증명한다 (§4.4.4)

**왜 이 순서로 지었나.** 전부 **순수**해서 전송 없이 지을 수 있고, 오라클 안에 있기
때문이다 — RFC-0090 §N6 이 HTTP 에 쓴 *"파서를 먼저, 전송을 나중에"* 와 같은 순서다.

## ★ 키 스케줄의 뼈대 (§7.1)

```
0 ─HKDF-Extract(PSK)→ Early Secret ─Derive-Secret("derived","")→ ┐
ECDHE ─HKDF-Extract────────────────→ Handshake Secret ←──────────┘
  ├─ Derive-Secret("c hs traffic", CH..SH)   클라이언트 핸드셰이크 비밀
  └─ Derive-Secret("s hs traffic", CH..SH)   서버 핸드셰이크 비밀
─Derive-Secret("derived","")→ ┐
0 ─HKDF-Extract──────────────→ Master Secret
  ├─ Derive-Secret("c ap traffic", CH..서버 Finished)
  └─ Derive-Secret("s ap traffic", …)
```

각 비밀에서 레코드 키가 나온다: `key = Expand-Label(비밀,"key","",32)` ·
`iv = Expand-Label(비밀,"iv","",12)`.

## 표면

### 키 스케줄

| op | 하는 일 |
|---|---|
| `build_label` | HkdfLabel 구조체를 바이트로 |
| `expand_label` | `HKDF-Expand-Label` |
| `derive_secret` | `Derive-Secret(비밀, 라벨, 전사해시)` |
| `advance` | 사다리 **한 칸** — 위 그림의 화살표 하나 |
| `traffic_key` / `traffic_iv` | 비밀 → 레코드 키 · IV |
| `finished_key` / `verify_data` | Finished 의 키와 값 |

### 레코드 계층

| op | 하는 일 |
|---|---|
| `record_header` | 5 바이트 헤더 `23 ‖ 0x0303 ‖ 길이` |
| `record_nonce` | IV 와 시퀀스 번호 → 논스 |
| `record_seal` / `record_open` | 레코드 봉하기 · 열기 |
| `inner_type` | 속 평문의 **끝**에서 진짜 내용 타입을 읽는다 |

### 전사와 Finished

| op | 하는 일 |
|---|---|
| `transcript` | 이어 붙인 메시지 버퍼의 해시 |
| `hs_type` / `hs_size` / `hs_count` | 핸드셰이크 메시지 걷기 |
| `check_finished` | 서버 Finished 를 **다시 계산해** 맞춰 본다 |

## ★ 레코드는 겉과 속이 다르다

겉은 **언제나** `23 ‖ 0x0303 ‖ 길이` 다 — 내용이 핸드셰이크든 응용 데이터든 똑같이 보인다.
**진짜 내용 타입은 속 평문의 끝**에 있다(`inner_type`). 관찰자에게 감추려고 그렇게 짰다.

그리고 **AAD 는 그 5 바이트 헤더 자체**다 — TLS 1.2 처럼 따로 만들지 않는다.

## ★ 스위트가 둘이라 협상이 뜻을 갖는다

```
suite 1 = TLS_AES_128_GCM_SHA256        (RFC 8446 §9.1 MUST) → gcm
suite 2 = TLS_CHACHA20_POLY1305_SHA256  (SHOULD)             → aead
```

☞ 하나만 지었을 때 이 자리는 **죽은 분기**였다. 둘이 되어야 고르는 일이 생긴다.
  모르는 스위트는 **거절한다** — 조용히 하나를 고르지 않는다.

☞ **처리량 주의**: 우리에겐 AES-NI 가 없다. 상대가 고르게 두되, 우리가 **선호를 정할 수
  있다면** ChaCha20 쪽이 유리할 가능성이 크다. (아직 안 쟀다 — 재고 나서 확정한다.)

## ★ 전사 해시가 핸드셰이크의 뼈대다

키도 Finished 도 전부 *"지금까지 오간 메시지 전부"* 의 해시 위에 선다 ⇒ 중간자가 **한
바이트라도** 바꾸면 **양쪽 키가 갈린다.**

**전사를 어디서 자르는지가 규격의 절반이다.** RFC 8448 은 각 Derive-Secret 의 `hash` 로
그 자리를 적어 두었고, 게이트가 세 자리를 전부 맞댄다: `CH…SH` · `CH…서버Finished` ·
`CH…클라Finished`.

☞ `sha256` 이 한 번에 하는 리프라(스트리밍이 없다) 전사는 **호출자가 이어 붙인 버퍼** 위에서
  잰다 — 라이브러리가 버퍼를 몰래 잡지 않는다.

☞ 메시지 걷기(`hs_size`·`hs_count`)는 **길이 필드를 믿지 않는다**: 버퍼를 넘는 길이가 적혀
  있으면 거기서 멈춘다. **길이는 상대가 쓴 것이다.**

## ★ `check_finished` 의 비교는 조기 반환이 없다

32 바이트를 XOR 로 **누적**해 마지막에 한 번 본다. 먼저 다른 바이트에서 돌아오는 비교는
태그를 한 바이트씩 알아내게 해 준다. ([hmac](hmac.md) 이 *"MAC 비교는 부르는 쪽의 몫"* 이라
적어 둔 그 일을, 여기서는 이 모듈이 한다.)

## ★ 작업 공간을 둘로 묶는 이유

파라미터 상한이 **16** 이라 스위트마다 버퍼를 늘어놓으면 금방 넘는다(`lockbox` 에서 이미
밟았다). 그래서 바이트 `w` 와 u64 `u` 둘로 묶고 자리를 **주석에 적어** 나눠 쓴다:

```
w: 0..12 nonce · 12..44 otk · 44..108 ks · 108..124 pad · 124..140 want · 140..460 gcm
u: 0..10 poly 상태 · 10..26 chacha 상태 · 26..42 chacha 작업
```

☞ 예쁘지 않다. **언어의 상한이 만든 모양**이고, 그 사실을 감추지 않는 편이 낫다.

## 오라클 — 두 겹이다

1. **두 번째 구현**: 파이썬 `hashlib`/`hmac` 로 §7.1 을 독립 구현해 바이트 대조(13 자리).
2. **정본 추적**: `docs/vectors/rfc8448-s3.tsv`(103 값)를 `scripts/extract-rfc8448.py` 가
   정본에서 **기계로** 뽑는다. 게이트 28 이 **96 자리**를 본다.

★★★ **그리고 정본이 결함을 하나 잡았다.** `traffic_key` 가 키 길이를 **32 로 박아**
두었는데, 그 길이는 HkdfLabel 안에 들어가므로 AES-128-GCM(16) 을 쓰는 상대와는 **키가
통째로 달라진다.** 두 번째 구현으로는 안 잡혔다 — 참조도 같은 사람이 썼고 같이 32 를
썼기 때문이다.

☞ **두 번째 구현은 정본이 아니다.** 같은 오해는 두 번 해도 같은 답을 낸다.
