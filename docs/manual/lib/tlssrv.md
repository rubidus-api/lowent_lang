# tlssrv — TLS 1.3 서버 핸드셰이크 (메시지 층과 상태)

소스: `lib/tlssrv.low` · 모듈명 `tlssrv` (RFC 8446 · RFC-0090 §N7b)

> ## ⚠ 무엇을 약속하고 무엇을 안 하나
>
> · **이것만으로는 TLS 서버가 아니다.** 핸드셰이크를 양방향으로 엮고 **응용 데이터
>   레코드를 봉하고 연다** — 그러나 **전송이 없고**, 키 갱신(KeyUpdate) · 레코드 패딩 ·
>   재조립(레코드 경계는 부르는 쪽이 정한다)은 아직 없다.
> · 인증서 **체인이 여럿이면 `build_cert` 로는 안 된다**(하나만 담는다) — 그때 지으라고 적어 둔다.
> · **전송이 없다.** 소켓도 재조립도 재협상도 없다 — 바이트열은 부르는 쪽이 모아 온다.
> · HelloRetryRequest · PSK/0-RTT · 클라이언트 인증서 요구 · 세션 재개 **없음**.
> · 확장은 **찾아만** 준다(SNI·ALPN 해석은 부르는 쪽) · **감사받지 않았다.**

## 처음 쓰는 사람에게

**무엇을 하는 모듈인가.** [tls13](tls13.md) 이 규격의 **계산**(키 스케줄·레코드·전사·Finished)을
갖고 있다. 이 모듈은 그것을 **순서대로 부르는 층**의 첫 칸이다.

**모든 실패는 `0` 이다** — 예외가 아니라 값이다. 그리고 op 은 **자리**를 낸다; 자르는 것은
부르는 쪽이 `subslice` 로 한다([http](http.md)·[der](der.md) 와 같은 모양이다).

## ★★★ ClientHello 는 이 저장소에서 **가장 적대적인 입력**이다

아직 **아무것도 인증되지 않은** 바이트열이고, 길이 필드는 전부 상대가 썼다. 그래서:

1. 어떤 자리도 버퍼를 넘으면 **즉시 실패**한다.
2. 확장 걷기는 **재귀를 안 하고**, 걸음 수를 버퍼 크기로 묶는다 — 길이 0 짜리 확장이
   이어지면 안 묶은 루프는 **안 끝난다.**
3. 길이가 안 맞으면 **고쳐 읽지 않는다.** `ch_ok` 는 선언된 길이가 버퍼와 **정확히** 같기를
   요구하고, `ch_ext_len` 은 확장이 **끝까지** 맞기를 요구한다.

## 표면

### 상태

| op | |
|---|---|
| `st_start`·`st_recvd_ch`·`st_negotiated`·`st_wait_flight2`·`st_wait_finished`·`st_connected` | 상태 번호 |
| `hs_client_hello`·`hs_server_hello`·… | 메시지 종류 번호 |
| **`next_ok`** | **지금 이 메시지를 받아도 되는가** |
| `step` | 상태를 옮긴다. 못 옮기면 **같은 상태를 그대로** 낸다 |

### ClientHello 읽기

| op | |
|---|---|
| `ch_ok` | 종류와 길이가 버퍼와 맞는가 |
| `ch_random_off` · `ch_sid_off`/`ch_sid_len` | 랜덤 · session_id |
| `ch_suites_off`/`ch_suites_len` · `ch_has_suite` | 제안된 스위트 |
| `ch_ext_off`/`ch_ext_len` · `ch_ext_find`/`ch_ext_find_len` | 확장 블록 · 종류로 찾기 |
| **`ch_x25519_off`** | key_share 안의 **x25519 공개키 자리** |
| `be16` | 빅엔디언 2 바이트 |

### 메시지 짓기

| op | |
|---|---|
| **`build_sh`** | 랜덤 · session_id · 스위트 · 우리 공개키 → ServerHello |
| **`build_ee`** | 확장 블록 → EncryptedExtensions (무엇을 넣을지는 **정책**이라 부르는 쪽이) |
| **`build_cert`** | DER 인증서 **하나** → Certificate |
| **`cv_content`** | **CertificateVerify 가 서명하는 130 바이트** (아래 ★) |
| **`build_cv`** | 알고리즘 · 서명 → CertificateVerify |
| **`build_fin`** | verify_data 32 → Finished |

넷 다 **틀이 같다**(`<종류 1> <길이 3> <본문>`) — 그래서 틀을 **한 번만** 적었다.
네 곳에 같은 산술을 되풀이하면 **한 곳만 고치는 날**이 온다.

## ★★★ `cv_content` — 공백 64 개는 장식이 아니다

RFC 8446 §4.4.3 이 서명 대상을 이렇게 정한다:

```
0x20 × 64  ‖  "TLS 1.3, server CertificateVerify"  ‖  0x00  ‖  전사해시
```

그 앞머리가 **없으면 이 서명이 다른 문맥의 서명으로 재활용될 수 있다** — 인증서 서명이나
클라이언트 쪽 서명과 **같은 바이트**가 되어 버린다. `0x00` 구분자도 마찬가지다:
문자열과 해시가 붙으면 경계가 흐려진다.

☞ 규격에서 *"왜 이런 게 있지"* 싶은 상수는 대개 **이미 일어난 공격**의 흔적이다.

## ★ 순서는 규격의 절반이다

`next_ok` 는 **받아들이는 자리를 열거한다** — 그리고 열거하는 것이 곧 나머지를 거절하는 것이다.
안 보면 중간자가 Finished 를 **앞당기거나** ClientHello 를 **두 번** 보낼 수 있다.

`step` 은 못 옮기면 **같은 자리에 머문다.** 조용히 건너뛰지 않는다.

## ★★ `session_id` 를 그대로 되울린다

TLS 1.3 은 그 필드를 **쓰지 않는다.** 그런데 되울리지 않으면 **실제 망에서 끊긴다** —
중간상자에게 1.2 처럼 보이게 하려는 호환 장치이기 때문이다(RFC 8446 §4.1.3).

☞ 규격이 *"쓰지 않는다"* 고 한 필드를 지우면 안 되는 자리다. **세상이 그것을 본다.**

## 오라클

**RFC 8448 §3 의 실제 핸드셰이크.** 정본의 ClientHello 를 읽어 필드를 확인하고, 메시지 다섯을
지어 **정본과 바이트로 맞댄다** — ServerHello **90** · EncryptedExtensions **40** ·
Certificate **445** · CertificateVerify **136** · Finished **36**.

★★ 그리고 **끝까지 엮어서** 본다: 정본의 서버 개인키와 클라이언트 공개키로 **ECDHE 를
우리가 내고**(`8bd4054f…`), 거기서 키 스케줄을 올려 **서버 Finished 를 정본과 맞춘다**
(`9b9b141d…`). 이 한 수가 전사 자르는 자리·키 스케줄·finished_key·verify_data 를
**한꺼번에** 건다.
다르면 검사가 **어디서 갈렸는지 자리를 말한다.**

☞ 정본의 CertificateVerify 는 **RSA-PSS**(0x0804)이고 우리 서명기는 ECDSA(0x0403)다.
  **틀은 같으므로** 여기서 재는 것은 틀이고, 서명 자체는 [ecdsa](ecdsa.md) 가 RFC 6979
  벡터로 따로 잰다.

☞ 필드를 눈으로 확인하는 검사는 검사가 아니다. **지어서 정본과 같은지**가 검사다
  ([der](der.md) 이 파싱 결과를 서명 검증까지 써 보는 것과 같은 이유다.)

## ★★★★★ `server_finished` — 부품을 한 줄로 엮는다

```
ECDHE ─ 키 스케줄(early → handshake) ─ Derive-Secret("s hs traffic", H(CH‖SH))
      └─ finished_key ─ verify_data(H(CH‖SH‖EE‖Cert‖CV)) ─ Finished
```

**전사를 어디서 자르는지가 규격의 절반이다.** `s hs traffic` 은 **CH‖SH 까지**의 해시 위에
서고, Finished 의 verify_data 는 **CV 까지**의 해시 위에 선다 — **같은 비밀, 다른 전사**다.

☞ 이 둘을 헷갈리면 **키는 맞는데 Finished 만 틀리고**, 그 증상은 *"상대가 거절한다"* 뿐이다.
  그래서 이 한 op 을 정본과 맞대는 것이 이 층에서 가장 값나가는 검사다.

☞ 메시지는 **호출자가 이어 붙여 온다** — 이 모듈이 버퍼를 몰래 잡지 않는다
  (`sha256` 이 한 번에 하는 리프라 전사는 이어 붙인 버퍼 위에서 잰다).

## ★★★ 전사는 이 층에서 **세 번** 잘린다

| 무엇 | 전사 |
|---|---|
| `s hs traffic` | CH‖SH |
| 서버 Finished | CH‖…‖**CertificateVerify** |
| 응용 트래픽 비밀 · **클라이언트 Finished** | CH‖…‖**서버 Finished** |

마지막 둘이 **같다**는 것이 헷갈리기 쉽다 — 클라이언트 Finished 는 **자기 자신을 포함하지
않는다**(당연하지만, 이어 붙이는 코드는 자연히 포함시키게 된다).

☞ 그리고 클라이언트 Finished 의 verify_data 는 **클라이언트** 핸드셰이크 비밀에서 나온다 —
  같은 전사, **다른 비밀**. 서버 것을 쓰면 **언제나 거절**하게 되고, 증상은
  *"클라이언트가 이상하다"* 로 보인다.

| op | |
|---|---|
| `app_secrets` | master 로 올라가 c/s 응용 트래픽 비밀(64 B) |
| `check_client_finished` | 상대의 Finished 를 **다시 계산해** 맞춘다 (1 = 맞음) |

비교는 [tls13](tls13.md) 의 `check_finished` 가 한다 — **조기 반환 없이** XOR 로 누적한다.

## ★★★ 응용 데이터 레코드

| op | |
|---|---|
| `traffic_keys` | 비밀 → **키 ‖ IV**(28 B). **한 방향씩** 만든다 |
| `seal_app` | 평문 → 레코드 (속 끝에 타입 23 을 붙인다) |
| `open_app` | 레코드 → 속 평문 (타입은 [tls13](tls13.md) 의 `inner_type` 이 읽는다) |

**방향마다 다른 비밀·다른 시퀀스**다. 서버 쓰기(`s ap traffic`)와 서버 읽기(`c ap traffic`)는
키도 IV도 시퀀스도 따로 간다 — 하나를 공유하면 **논스가 겹치고**, AEAD 에서 논스가 겹치는
것은 [gcm](gcm.md) 이 적어 둔 대로 **평문과 인증키를 함께 잃는 일**이다.
그래서 이 모듈은 키뭉치를 **한 방향씩** 만든다: 한 번에 둘을 주면 섞어 쓰게 된다.

☞ **시퀀스는 레코드마다** 오르고 **키 세대마다 0 부터**다 — *"내가 보낸 데이터"* 를 세는 게
  아니다. 정본의 서버 응용 키 시퀀스는 NewSessionTicket 0 · 응용 데이터 1 · 경보 2 이고,
  0·1 로 적었다가 안 열렸다.

☞☞ **출력 버퍼는 32 바이트여야 한다 — 키가 16 이어도.** `expand_label` 은 HMAC 한 블록을
  쓰므로 **언제나 32 를 쓰고** 낸 값만 16 이다. *반환 길이와 쓰는 길이가 다르다.*

### 경보도 같은 레코드다

겉은 응용 데이터와 **구별이 안 된다**(그것이 설계다). 속 타입이 **21** 이라 말하고,
**그것을 안 보면 경보를 데이터로 읽는다.**
