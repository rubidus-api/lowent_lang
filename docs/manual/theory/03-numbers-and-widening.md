# 03. 수와 안전한 확대

> **근거**: `docs/proofs/coq/NumericLattice.v` — **Theorem 29 · Lemma 7 · 479줄**, 전부 `Qed`
> (Coq 이 받아들였다는 표시).

## ① 5분 요약

C 에서 이 코드는 **경고도 없이** 값을 바꾼다:

```c
unsigned char small = 300;   /* 300 이 44 가 된다. 아무도 안 알려 준다 */
int  a = -1;
unsigned int b = a;          /* −1 이 4294967295 가 된다 */
```

Lowent 는 **값이 보존되는 확대만** 암묵적으로 허용한다. 그 외에는 컴파일러가 거절하고,
잃어도 괜찮다면 프로그래머가 **어떻게 잃을지 골라** 적어야 한다(`narrow_wrap`·`narrow_sat`·
`narrow_try`).

그 "값이 보존되는 확대" 를 수학으로 정의하고, 그것이 정말 안전한지 기계로 증명한 것이 이 장이다.

## ② 필요한 수학

2장의 **부분 순서**와 **join** 이면 된다. 하나만 더 붙인다.

정수 타입은 두 정보로 정해진다: **폭**(8·16·32·64비트)과 **부호 있음/없음**. 각 타입이 담는
범위는 2의 보수로 정해진다:

| 타입 | 최솟값 | 최댓값 |
|---|---:|---:|
| `u8` | 0 | 255 |
| `i8` | −128 | 127 |
| `u32` | 0 | 4,294,967,295 |
| `i32` | −2,147,483,648 | 2,147,483,647 |

수식으로: 부호 없는 `uN` 은 `[0, 2^N − 1]`, 부호 있는 `iN` 은 `[−2^(N−1), 2^(N−1) − 1]`.

## ③ 정의와 정리

### 정의 — 안전 확대 관계 `⊑`

`t ⊑ u` 는 "타입 t 의 어떤 값이든 타입 u 에 **값이 변하지 않고** 들어간다" 로 읽는다.
Lowent 는 이것을 **네 줄**로 정의한다:

| 왼쪽 | 오른쪽 | 조건 | 왜 |
|---|---|---|---|
| `uN` | `uM` | N ≤ M | 부호 없음끼리는 폭만 넓으면 된다 |
| `iN` | `iM` | N ≤ M | 부호 있음끼리도 같다 |
| `uN` | `iM` | **N < M** (엄격!) | `u8`(255)은 `i8`(127)에 안 들어간다 → 폭이 **더** 커야 한다 |
| `iN` | `uM` | **절대 안 됨** | 음수를 담을 곳이 없다 |

세 번째 줄의 `<` 가 요점이다. `≤` 로 적었다면 `u8 ⊑ i8` 이 허용되고 **255 가 −1 로** 바뀐다.
이 한 글자가 값의 안전을 가른다 — 그리고 사람이 이런 걸 틀린다.

### 정리 1 — `⊑` 는 값을 보존한다 (`sub_preserves`)

> **평서문**: `t ⊑ u` 이고 값 `v` 가 `t` 의 범위에 있으면, `v` 는 `u` 의 범위에도 있다.

이 한 줄이 "암묵 확대는 안전하다" 라는 주장의 **전부**다. 이게 참이면 확대할 때 값 검사가
필요 없고(공짜다), 거짓이면 언어가 조용히 값을 바꾼다.

**막는 버그**: `let big u32 be small .` 에서 `small` 이 `u8` 이면 검사 없이 통과한다.
그런데 이 정리가 없으면 `u8 → i8` 같은 잘못된 쌍이 표에 섞여 들어가도 아무도 모른다.

### 정리 2 — `⊑` 는 부분 순서다 (`sub_refl` · `sub_trans` · `sub_antisym`)

> **평서문**: 자기 자신에는 항상 들어가고(반사), 징검다리로 이어지고(추이), 서로 들어가면
> 같은 타입이다(반대칭).

**막는 버그**: 추이성이 깨지면 `u8 → u16` 과 `u16 → u32` 는 되는데 `u8 → u32` 는 안 되는
언어가 된다. 사용자는 왜 안 되는지 영영 모른다. (그리고 이런 표를 손으로 관리하면 실제로
그런 구멍이 생긴다.)

### 정리 3 — join 은 둘 다를 안전히 담는다 (`join_sound`)

> **평서문**: 두 타입 `t`, `u` 가 비교 가능하면 `t ⊔ u` 는 **둘 다**의 모든 값을 담는다.

이건 갈래가 합쳐지는 자리에서 쓰인다:

```lowent
rem 두 갈래가 다른 타입을 주면 컴파일러는 둘을 다 담는 타입을 골라야 한다
if cond . do set x a . end       rem u8
if cond . do set x b . end       rem u16
rem  x 의 타입은 u8 ⊔ u16 = u16
```

**막는 버그**: join 표를 손으로 적다가 `u8 ⊔ i8 = i8` 이라 쓰면 255 가 −1 이 된다.
증명이 있으면 그런 표를 **쓸 수가 없다** — Coq 이 거절한다.

### 정리 4 — join 은 두 피연산자 중 하나다 (`join_is_an_operand`)

> **평서문**: `t ⊔ u` 는 항상 `t` 이거나 `u` 다. 새 타입을 만들어 내지 않는다.

**막는 버그**: 이게 없으면 join 이 "어디선가 나온 제3의 타입" 을 낼 수 있고, 그러면 프로그래머가
소스에서 볼 수 없는 타입이 코드에 생긴다. 비용이 안 보이게 되는 것이다(P2 위반).

### 정리 5 — 축소는 조건이 정확히 하나다 (`fits_iff` · `narrow_ok_iff`)

> **평서문**: 값 `v` 를 타입 `u` 로 좁히는 것이 성공하는 **필요충분조건**은 `v` 가 `u` 의 범위에
> 있는 것이다.

"필요충분" 이 중요하다. 성공 조건이 **정확히** 범위 안이라는 뜻 — 더 관대하지도, 더 엄하지도 않다.

**막는 버그**: `narrow_try u8 300` 이 조용히 성공해 44 를 주는 것. 이 정리 덕분에 그것은
`none` 이다(실패가 **값**이다).

### 정리 6 — 확대는 절대 실패하지 않는다 (`widen_never_fails`)

> **평서문**: `t ⊑ u` 이면 `t` 의 값을 `u` 로 넣는 것은 **언제나** 성공한다.

**막는 버그**: 확대 자리에 런타임 검사를 남기는 낭비. 실패할 수 없음이 증명됐으므로 검사가 없다 —
그게 **공짜인 이유**다.

### 정리 7~12 — 나눗셈과 나머지 (`div_*` · `rem_*` · `mod_*`)

나눗셈은 이 언어에서 유별나게 조심하는 자리다. 증명된 것:

| 정리 | 평서문 | 막는 버그 |
|---|---|---|
| `div_unsigned_total` | 부호 없는 나눗셈은 0 으로 나누지 않으면 **항상** 성공한다 | 불필요한 검사 |
| `div_signed_failure_is_only_min_neg1` | 부호 있는 나눗셈이 실패하는 경우는 **`MIN / −1` 하나뿐**이다 | 이 한 경우를 놓쳐 UB 가 되는 것(C 의 실제 함정) |
| `rem_sign_follows_dividend` | `rem` 의 부호는 **나뉘는 수**를 따른다 | −7 rem 3 이 2 인지 −1 인지 헷갈리는 것 |
| `mod_sign_follows_divisor` | `mod` 의 부호는 **나누는 수**를 따른다 | 위와 같은 혼동 — 둘을 **다른 낱말**로 갈라 뒀다 |
| **`mod_is_a_safe_index`** | `mod i (len s)` 는 **항상 유효한 인덱스**다(0 ≤ 결과 < len) | 해시 테이블의 `index s (mod h n)` 에서 경계 검사가 남는 낭비 |

마지막 것이 실전에서 값이 크다. 해시맵은 늘 `mod` 로 슬롯을 고르는데, 그 결과가 범위 안임이
**증명**되므로 검사가 사라진다. `len s = 0` 이면? 0 으로 나누는 것이므로 **먼저 트랩한다** —
그래서 값이 나온 경로에서는 `len s > 0` 이 보장된다. 논증에 빈틈이 없다.

### 정리 13~20 — `range` 타입 (`rsub_*` · `radd_*` · `idx_no_check`)

Lowent 는 타입에 **범위**를 붙일 수 있다(`u8 range 0 .. 100`). 그러면 위의 이야기가 한 겹 더
정밀해진다:

| 정리 | 평서문 |
|---|---|
| `rsub_preserves` | 범위끼리의 확대도 값을 보존한다 |
| `radd_sound` | 두 범위를 더한 결과는 계산된 범위 안에 있다 |
| **`radd_no_check`** | 결과 범위가 타입 안에 들어가면 **오버플로 검사가 필요 없다** |
| **`idx_no_check`** | 인덱스 범위가 길이 안이면 **경계 검사가 필요 없다** |
| `rdisj_no_value` | 서로소인 두 범위는 **공통 값이 없다**(그래서 분기 하나가 죽는다) |
| `derive_minimal` | 도출된 범위는 **가장 작은** 것이다(필요 이상으로 넓지 않다) |

`radd_no_check` 와 `idx_no_check` 는 05장에서 실제 성능 숫자와 함께 다시 나온다. 검사를 없애는
최적화의 **정당성이 바로 이 두 정리**다.

## ④ 증명의 전략

전부 **정의를 펼쳐 부등식으로 만들고, 그 부등식을 계산**하는 방식이다. 예컨대 정리 1은:

```
t ⊑ u 이고 lo(t) ≤ v ≤ hi(t) 일 때  lo(u) ≤ v ≤ hi(u) 를 보인다.

`⊑` 의 네 경우로 나눈다(부호 조합 4가지).
경우 uN ⊑ uM (N ≤ M):
    lo(t) = lo(u) = 0            → 아래쪽은 자명
    hi(t) = 2^N − 1 ≤ 2^M − 1 = hi(u)   ← 2의 거듭제곱이 단조라는 사실만 쓴다
경우 uN ⊑ iM (N < M):
    hi(t) = 2^N − 1,  hi(u) = 2^(M−1) − 1,  그리고 N < M 이므로 N ≤ M−1
    → 2^N − 1 ≤ 2^(M−1) − 1 ✓
경우 iN ⊑ iM · iN ⋢ uM: 같은 방식(마지막은 정의상 거짓이라 할 일이 없다)
```

핵심 보조정리는 `pow2_le` — *"a ≤ b 면 2^a ≤ 2^b"*. 고등학교 지수법칙이다. **증명 전체가
고등학교 수학 위에 서 있다.** 어려운 것은 논증이 아니라 **경우를 하나도 빠뜨리지 않는 것**이고,
그것이 기계에게 맡기는 이유다.

## ⑤ 이것이 막는 버그 — 실제 코드로

```lowent
rem ① 조용한 절단이 없다
let big u32 be 300 .
let small u8 be big .              rem ✘ 컴파일 거절 — u32 ⋢ u8
let small2 u8 be narrow_wrap u8 big .   rem ✔ "잘려도 좋다" 를 **내가** 적었다(44)
let small3 option u8 . be narrow_try u8 big .  rem ✔ 실패를 **값으로** 받는다(none)

rem ② 부호가 조용히 뒤집히지 않는다
let neg i32 be 0 .
let u u32 be neg .                 rem ✘ 컴파일 거절 — i32 ⋢ u32 (음수를 담을 곳이 없다)

rem ③ 폭이 같아도 부호가 다르면 확대가 아니다
let a u8 be 200 .
let b i8 be a .                    rem ✘ 컴파일 거절 — u8 ⋢ i8 (200 > 127)
let c i16 be a .                   rem ✔ u8 ⊑ i16 (폭이 더 크다)
```

C 라면 ①②③ 전부 **경고 없이 통과**하고 값이 바뀐다. 이 언어에서 통과하지 않는 근거가
정리 1(값 보존)과 `⊑` 정의의 세 번째 줄(`N < M`)이다.

## ⑥ 증명하지 않은 것

- **부동소수(f32·f64)는 이 격자에 없다.** 정수만 다뤘다. 부동소수의 확대(`f32 → f64`)는
  값을 보존하지만, 반대와 혼합 연산은 별도 규칙이며 여기서 증명되지 않았다.
- **폭은 8·16·32·64 네 개**로 고정했다. 임의 폭 정수(`u7` 같은)는 모델에 없다.
- **`u128`** 은 post-v1 이다(모델·구현 모두 없다).
- 이 정리들은 **타입 규칙**에 대한 것이다. 컴파일러가 그 규칙을 정확히 구현했는지는 별개이며,
  그것은 시험과 두 백엔드 대조가 확인한다(15장).

**타입 규칙 쪽은 한 층 더 깊이 증명돼 있다**(`LowentType.v`): 폭·부호가 붙은
수치 식에 **묶는 자(let)·분기·비교·좁히기·검사된 산술·감싸는 산술**을 얹고 세 정리를 증명했다.

> `progress` — 타입이 붙은 닫힌 식은 **값이거나 · 덫이거나 · 한 걸음 간다**(막히지 않는다).
> `preservation` — 한 걸음 가도 **타입이 변하지 않는다**.
> `values_fit` — 실행이 값에 닿으면 그 값은 **언제나 그 타입의 폭 안에** 있다.

세 번째가 이 언어에서 특별하다: `u8` 이라고 적힌 자리에 8비트를 넘는 값이 들어오면
`--emit-c` 가 낸 C 코드가 조용히 다른 일을 한다. 그래서 **범위를 타입 규칙 안에 넣고**
(값에 타입을 붙이려면 범위 증거가 있어야 한다) 실행 내내 보존됨을 증명했다.

그리고 **덫을 정직하게 모델링했다.** 검사된 산술은 넘치면 값을 내지 않고 **멈춘다**
(그것을 컴파일 시각에 막는 것이 정상 경로 — 05장의 계약과 증명서가 그 일을 한다).
덫을 값에 넣으면 정리가 거짓말이 되고, 덫을 빼면 정리가 거짓이 된다. 그래서 결론이 **셋**이다.
