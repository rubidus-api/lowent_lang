# 04. 구간 분석 — 돌리지 않고 값의 범위를 알기

> **근거**: RFC-0053(구간 분석) · `NumericLattice.v` 의 `radd_no_check`·`idx_no_check`.
> 구현: `impl/src/low_ir.c` 의 추상해석 패스. 이 장의 모든 숫자는 **실제로 재서** 넣었다.

## ① 5분 요약

이 언어는 정수 연산이 넘치면 **트랩**한다(조용히 감싸지 않는다). 그러면 곱셈마다 검사가 붙어
느려질 것 같다. 그런데 대부분의 검사는 **컴파일 시각에 사라진다** — 넘칠 수 없음이 증명되기
때문이다.

실측 예:

```lowent
export proc small_sum output u16 . input a u8 . input b u8 . effects none .
  requires le a 100 .
  requires le b 100 .
do
  return add (widen u16 a) (widen u16 b) .
end
```

```
$ lowentc --ir small_sum.low
-- runtime checks (interval analysis: overflow · division · narrowing) --
   4 / 4 removed  (100%)
```

계약이 `a ≤ 100`, `b ≤ 100` 을 말했으므로 합은 최대 200 이고 `u16`(65535)에 넘치지 않는다 —
검사가 **하나도 남지 않는다**. 계약을 지우면 같은 코드에서 검사가 남는다.

## ② 필요한 수학

2장의 **추상해석**과 **고정점**. 요점만 다시:

- 값 하나 대신 **구간** `[lo, hi]` 로 계산한다.
- 규칙은 **넓게** 잡아야 한다(실제 가능한 값을 전부 포함). 넓으면 손해만 보고, 좁으면 **틀린다**.
- 루프는 **위드닝**으로 유한 번에 고정점에 닿는다.

구간 연산의 예:

```
a ∈ [0, 100],  b ∈ [0, 100]
a + b ∈ [0, 200]        ← lo+lo, hi+hi
a − b ∈ [−100, 100]     ← lo−hi, hi−lo   (★ 뺄셈은 뒤집힌다 — 흔한 실수 자리)
a * b ∈ [0, 10000]      ← 부호가 섞이면 네 곱 중 최소·최대를 봐야 한다
```

## ③ 정리와 그 뜻

이 장에 관한 기계 검증 정리는 03장에서 이미 나왔다. 다시 짚으면:

### `radd_no_check` — 결과가 타입 안이면 검사가 필요 없다

> **평서문**: 두 값의 구간을 더한 결과 구간이 선언 타입의 범위 안에 들어가면, 그 덧셈은
> **절대 넘치지 않는다** — 그러므로 런타임 검사를 지워도 된다.

**막는 버그**: 검사를 "감으로" 지우는 것. 감으로 지우면 **조용히 틀린 값**이 나온다. 정리는
지워도 되는 조건을 정확히 준다: *결과 구간 ⊆ 타입 범위*.

### `idx_no_check` — 인덱스가 길이 안이면 경계 검사가 필요 없다

> **평서문**: `i ≥ 0` 이고 `i < len(s)` 임이 알려지면 `index s i` 는 안전하다.

이것이 05장의 출발점이다.

### 건전성의 방향 — 왜 "넓게" 인가

정리들은 모두 한 방향이다: **"안전하다고 말한 자리는 정말 안전하다."** 그 반대(안전한데
안전하다고 말하지 못함)는 정리가 보장하지 않는다 — 그건 **성능 손해**일 뿐이다.

```
분석이 넓게 잡음  →  검사가 남는다        →  느리다 (안전)
분석이 좁게 잡음  →  검사가 사라진다      →  ★ 틀린 메모리 접근 (위험)
```

그래서 규칙 하나를 추가할 때마다 물어야 하는 것은 늘 같다: *"이 규칙이 실제보다 좁게 잡을 수
있는가?"*

## ④ 증명의 전략 — 그리고 기계가 스스로를 고발하는 장치

분석의 건전성은 **정리로** 뒷받침되지만, 구현이 그 정리를 정확히 따라가는지는 별개다.
그래서 VM 에 **자기 고발 장치**가 있다:

```
E-VM-ANALYSIS: index bounds check was eliminated but the index is OUT OF BOUNDS
               — the interval/relational analysis is UNSOUND (this is a compiler bug)
```

인터프리터는 검사를 **지우지 않는다**. 컴파일러가 "여긴 지워도 된다" 고 표시한 자리를 실행해
보고, 실제로 범위를 벗어나면 **그 자리에서 컴파일러를 고발한다**. 즉:

- 네이티브 빌드: 검사가 없다(빠르다).
- VM: 검사가 있고, **표시가 거짓이면 알려 준다**.
- 차분 오라클이 둘을 같은 입력으로 돌린다(15장).

★ 이 장치가 실제로 일했다. 2026-07-30 에 필자가 행우선 인덱스 규칙(05장)을 넣으면서 계약을
"검사되는 것" 으로 착각했는데 — 그 계약에는 런타임 검사가 없었다 — 바로 이 진단이 떴다.
**증명을 신뢰하되, 신뢰를 검사로 받친다.**

## ⑤ 이것이 막는 버그 — 그리고 실측

### 실측 1 — 계약이 검사를 지운다

| 프로그램 | 검사 제거 |
|---|---|
| `small_sum`(계약 `a ≤ 100`·`b ≤ 100`) | **4 / 4 (100%)** |
| `small_sum_nocontract`(같은 코드, 계약 없음) | 2 / 2 (100%)* |

\* 두 번째는 `widen` 이 실패할 수 없음(정리 6)으로 이미 증명돼 검사 대상 자체가 2개뿐이다.
계약이 있는 쪽은 **덧셈까지** 증명되어 4개 전부 사라진다.

### 실측 2 — 못 지우는 것도 정직하게 보고한다

```
$ lowentc --ir bench_sieve.low
   1 / 11 removed  (9%)
   sieve: 7 check(s) remain — the interval domain could not prove the range here.
     · a `range`/`requires` bound on the inputs may close it
```

"9% 제거" 를 자랑이 아니라 **사실**로 적는다. 그리고 무엇을 하면 닫히는지(범위·계약) 말해 준다.

### 실측 3 — 도구는 멈추지 않아야 한다 (이 문서를 쓰면서 고친 결함)

이 장의 예제를 만들다가 다음을 발견했다:

```lowent
export proc loop1 output u64 . input n u64 . effects none . do
  var i u64 be 0 .   var s u64 be 0 .
  while lt i n . do  set s (wrap_add s i) .  set i (add i 1) .  end
  return s .
end
```

`--check` 는 즉시 끝나는데 `--ir` 이 **60초를 넘겨도 안 끝났다**. 원인: `--ir` 은 계약 오라클을
돌리는데, 그 오라클이 경계값을 먹여 op 을 **실제로 실행**한다 — `n = 2^64 − 1` 이면 그 루프는
사람의 수명 안에 끝나지 않는다.

⇒ 오라클 실행에 **걸음 예산**(2천만 걸음)을 넣고, 예산에 걸린 케이스는 **건너뛰며 센다**:

```
     ★ 2 case(s) SKIPPED by the step budget — the op's trip count is an INPUT,
       so a boundary value (2^64-1) would never finish. Skipped, not silently passed:
       the oracle says what it did not check
```

**조용히 통과시키지 않는 것**이 요점이다. 검증하지 않은 것을 검증했다고 말하면 그 오라클은
그 순간부터 거짓말이 된다. (사용자 실행 `--run` 에는 예산이 없다 — 오래 도는 프로그램을
도구가 끊는 것은 옳지 않다. 끊어도 되는 것은 **우리가 만든 테스트**다.)

## ⑥ 증명하지 않은 것

- **구간은 변수 사이의 관계를 모른다.** `x ≤ y` 같은 사실은 구간으로 표현할 수 없다
  (`x ∈ [0,10]`, `y ∈ [0,10]` 로는 `x ≤ y` 를 알 수 없다). 그래서 **관계 영역**을 따로 둔다 — 05장.
- **비선형(곱)을 일반적으로 못 다룬다.** `i * n` 의 범위는 구간으로 계산되지만, `i*n + k < n*n`
  같은 **상징적 비교**는 못 한다. 05장에서 그 한 조각만 특별히 증명한다.
- **위드닝은 정보를 버린다.** 고정점에 빨리 닿기 위해 일부러 넓게 잡으므로, 실제로는 안전한
  자리에서도 검사가 남을 수 있다. 이것은 **손해이고 위험이 아니다**.
- **부동소수 구간은 다루지 않는다.**
