# 05. 경계 증명 — 배열 검사를 증명으로 없애기

> **근거**: RFC-0055 D5(경계 검사 제거) · `NumericLattice.v` 의 `idx_no_check` · `mod_is_a_safe_index`
> · RFC-0084(제네릭). 구현: `impl/src/low_ir.c` 의 관계 영역. 숫자는 전부 실측이다.

## ① 5분 요약

`s[i]` 를 읽을 때마다 "i 가 범위 안인가" 를 확인하면 안전하지만 느리다. C 는 확인하지 않아
빠르지만 **범위를 벗어나면 남의 메모리를 읽는다**(모든 보안 사고의 절반이 여기서 나온다).

Lowent 는 셋째 길을 쓴다: **확인을 하되, 확인할 필요가 없음이 증명되면 그 자리에서 지운다.**

이 장은 그 "증명" 이 어떻게 생겼는지 보인다. 네 단계로 점점 세진다:

| 단계 | 아는 사실 | 예 |
|---|---|---|
| 1 | `i < len(s)` 를 직접 봤다 | `while lt i (len s) . do … index s i … end` |
| 2 | 길이를 지역에 담았다 | `let n be len s . while lt i n .` |
| 3 | 계약이 용량을 말한다 | `requires ge (len s) cap .` + `while lt j cap .` |
| 4 | **비선형** — 행우선 주소 | `requires ge (len a) (mul n n) .` + `index a (add (mul i n) k)` |

## ② 필요한 수학

### 관계 영역 — 구간이 못 하는 것

구간은 변수를 **따로따로** 본다. `i ∈ [0, 100]`, `n ∈ [0, 100]` 을 알아도 `i < n` 인지는 모른다.
그런데 배열 안전성이 필요한 사실이 바로 그것이다.

그래서 구간 **옆에** 한 칸짜리 관계를 둔다:

```
lenlt[i] = s     "지역 i 는 len(지역 s) 보다 작다"
lerel[i] = n     "지역 i 는 지역 n 보다 작다(또는 작거나 같다)"
```

이 사실들이 어디서 오는가? **분기 조건**에서 온다. `while lt i n` 의 몸통 안에서는 `i < n` 이
참이다 — 그것을 기록해 두는 것이다. 조건이 거짓인 갈래에서는 `i ≥ n` 이 참이다(그것도 사실이다).

### 왜 이것으로 충분한가

실제 코드가 그 모양이기 때문이다. 배열을 훑는 코드는 거의 항상 이렇게 생겼다:

```lowent
while lt i (len s) . do  … index s i …  end
```

정교한 이론보다 **실제 코드의 모양**을 정확히 담는 것이 값이 크다. 그래서 이 언어는 무거운
관계 영역(팔각형·다면체 같은) 대신 **한 칸**을 두고, 그 한 칸으로 실제 코드의 대부분을 닫는다.

## ③ 정리와 그 뜻 — 단계별로

### 단계 1 · 2 — 선형: `i < len(s)`

> **정리**(`idx_no_check`): `i ≥ 0` 이고 `i < len(s)` 이면 `index s i` 는 안전하다.

증명은 자명해 보이지만, 요점은 **그 두 사실을 컴파일러가 실제로 갖고 있는가**다.

**실측으로 찾은 구멍**: 단계 1은 되고 **단계 2가 안 됐다.**

```lowent
while lt i (len s) . do … end       rem 검사 없음  ✔ (되고 있었다)
let n u64 be len s .
while lt i n . do … end             rem 검사 남음  ✘ (아주 흔한 관용구인데!)
```

이유: "이 값은 `len s` 다" 라는 사실이 **스택 값**의 속성이었고, 지역에 담는 순간 사라졌다.
⇒ 지역에도 그 사실을 싣도록 고쳤다(2026-07-30). 그 루프의 검사가 **1 → 0** 이 됐다.

**막는 버그**: 없다 — 이것은 **성능** 수정이다. 정직하게 적으면: 안전성은 처음부터 있었고
(검사가 있었으니), 사라진 것은 낭비다.

### 단계 3 — 계약이 주는 용량

배열 크기와 루프 상한이 **다른 변수**일 때가 많다:

```lowent
export proc lru_bench input keys mut slice u64 . input cap u64 . … .
  requires ge (len keys) cap .        rem ★ 계약: 배열이 cap 개 이상이다
do
  while lt j cap . do  set (index keys j) 0 .  … end
end
```

논증: `j < cap` (루프 조건) 이고 `len keys ≥ cap` (계약) 이므로 `j < len keys` ✓.

**실측**: lru 벤치마크의 경계 검사가 **10 → 4**, 시간은 ×2.40 → **×1.69**(C 대비).

### 단계 4 — 비선형: 행우선 주소 (이 장의 핵심)

행렬 곱셈은 `a[i*n + k]` 처럼 **계산된 인덱스**를 쓴다. 구간도 한 칸 관계도 이것을 못 한다 —
`i*n` 은 곱이기 때문이다.

그런데 실제 코드가 쓰는 모양은 **하나**다: 행우선(row-major) 주소 계산. 그리고 그 모양에는
**정확한 증명**이 있다:

```
전제 F1:  len(s) ≥ p·q          (계약)
전제 F2:  i < p                 (바깥 루프 조건)
전제 F3:  k < q                 (안쪽 루프 조건)
계산:     주소 = i·q + k        (트랩 곱·트랩 합으로 계산됨)

i ≤ p−1  이므로   i·q ≤ (p−1)·q = p·q − q
k ≤ q−1  이므로   i·q + k ≤ p·q − q + q − 1 = p·q − 1
따라서            주소 ≤ p·q − 1 < p·q ≤ len(s)     ∎
```

고등학교 수학이다. 부등식 두 개를 더한 것뿐이다. 그런데 **전제가 하나라도 빠지면 무너진다** —
그래서 게이트가 그 경계를 지킨다:

| 무엇을 뺐나 | 검사가 |
|---|---|
| 전부 있음 | **사라진다** (0개) |
| 계약(F1)을 뺀다 | 남는다 |
| `i` 를 **다른 변수**로 묶는다(`while lt i m`) | 남는다 |
| 주소를 **`wrap_mul`** 로 계산한다 | 남는다 |

★ 마지막 줄이 가장 미묘하다. `wrap_mul` 은 넘칠 때 **조용히 감싼다**. 그러면 `i·q ≤ (p−1)q`
라는 단계가 깨진다(감싼 값은 작아질 수 있다). 같은 수식인데 **트랩이 아니면 사실이 아니다.**

또 하나: `p·q` 자체가 넘치면? 계약의 곱셈이 **트랩 곱**이고 계약 검사는 **절대 제거되지 않으므로**,
본문에 도달했다면 `p·q` 는 넘치지 않았다. 논증에 빈틈이 없다.

**실측**: matmul 의 경계 검사 **6 → 1**(남은 하나는 `return index c 0` — `n ≥ 1` 이 계약에 없다).
시간은 ×3.84 → **×2.60**.

### 보너스 — `mod` 는 언제나 안전한 인덱스다

> **정리**(`mod_is_a_safe_index`): `mod i (len s)` 는 항상 `0 ≤ 결과 < len(s)` 다.

해시맵이 늘 쓰는 모양이라 값이 크다. `len s = 0` 이면 0 으로 나누는 것이므로 **먼저 트랩한다** —
값이 나온 경로에서는 `len s > 0` 이 보장된다.

## ④ 증명의 전략

세 조각이다.

1. **사실을 어디서 얻는가** — 분기 narrowing. `lt i n` 이 참인 갈래에 `i < n` 을 심고, 거짓인
   갈래에서는 그 사실을 **지운다**(보수적이 아니라 정확하게).
2. **사실을 어떻게 나르는가** — 대입을 따라간다. `var x be j` 에서 `j < cap` 이면 `x < cap` 이다.
   그리고 **합류(merge)에서는 두 경로가 같을 때만 살린다** — 한쪽에서만 참인 것은 사실이 아니다.
3. **사실이 죽는 자리** — 관련 변수가 바뀌면 그 사실을 **양방향으로** 죽인다. 슬라이스가 다시
   묶이면 그 길이에 대한 사실 전부가 죽는다.

★ 3번이 안전의 핵이다. 사실을 **오래 살려 두면** 그것이 곧 잘못된 검사 제거다. 그래서 죽이는
쪽이 늘 더 공격적이다.

## ⑤ 이것이 막는 버그

```lowent
rem ① 계약 없이 계산된 인덱스 — 검사가 남는다(느리지만 안전하다)
proc f input a slice u64 . input n u64 . output u64 . effects none . do
  return index a (add (mul 2 n) 1) .   rem 검사 있음 — n 을 아무도 묶지 않았다
end

rem ② 계약을 어긴 호출 — **진입에서** 막힌다
proc g input a slice u64 . input n u64 . output u64 . effects none .
  requires ge (len a) (mul n n) .
do … end
rem 호출자가 작은 배열을 주면 그 자리에서 트랩한다:
rem   VM:     E-VM-CONTRACT
rem   native: panic
```

②가 중요하다. 경계 검사를 없앤 자리에서 **유일한 방벽**이 계약 검사다. 그래서 계약 검사는
**절대 제거되지 않는다** — 모드로도, 최적화로도.

★ 이 문서를 쓰기 직전에 실제로 그 구멍을 만들었다: `requires ge (len a) (mul n n)` 형태를
컴파일러가 **읽지 못해** 계약이 "문서" 였고 검사가 없었다. 그 상태로 규칙이 계약을 믿자
VM 의 자기 고발(`E-VM-ANALYSIS`)이 떴다. **믿을 것은 검사되는 것뿐이다.**

## ⑥ 증명하지 않은 것

정직하게 — 계약을 붙여도 **안 빠지는** 검사가 남는다. 실측한 것:

| 남은 자리 | 왜 못 하나 |
|---|---|
| matmul 의 `index c 0` | `n ≥ 1` 이 계약에 없다(추가하면 닫힌다) |
| lru 의 `index keys lru_idx` | `lru_idx` 는 `0` 과 `j` 가 **합류**한 값이라 관계 사실이 meet 에서 죽는다 |
| sieve 의 `index s i` (`while lt (mul i i) n`) | `i·i < n ⟹ i < n`(i ≥ 1)은 **또 다른 비선형** 모양이다 — 실제 코드에 드물어 규칙을 만들지 않았다 |
| sort 의 파티션 인덱스 | `hi ≤ len s` 를 **비엄격**으로 나르는 자리가 없다(지금 관계는 엄격 전용) |

그리고 **성능에 대한 정직한 관찰**: 검사를 없앤다고 늘 빨라지지 않는다. sched 벤치는 검사
**7 → 0** 인데 시간이 그대로였다 — 그 분기들은 한 번도 안 걸려 **늘 맞게 예측**되므로 사실상
공짜였다. 검사가 비싼 것은 matmul 처럼 **자동 벡터화를 막는** 자리다.

> **"검사 개수" 는 비용의 대리 지표가 아니다.** 이 문서는 개수를 줄인 것을 성과로 세지 않는다.
