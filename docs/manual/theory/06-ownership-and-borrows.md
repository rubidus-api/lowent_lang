# 06. 소유와 차용 — 이 언어의 중심 정리

> **근거**: `LowentEXCL.v` 의 `Theorem agreement` 와 따름정리 `no_violation_in_green`
> · RFC-0005(참조 EXCL) · `docs/proofs/lambda-lowent-core-agreement.md`(종이 증명).
> 구현: `impl/src/low_region.c`(정적) · `impl/src/low_ir.c` 의 `bstk_*`(동적).

## ① 5분 요약

같은 메모리 자리를 **두 이름**으로 동시에 만지면 버그가 난다. 한쪽이 고치고 다른 쪽이 낡은
값을 읽거나, 둘이 서로를 밟는다. C 는 이것을 막지 않는다. 그래서 이 언어는 규칙을 둔다:

> **한 자리를 고칠 수 있는 이름은 한 번에 하나뿐이다.** 읽기만 하는 이름은 여러 개 괜찮다.

핵심 질문은 이것이다. 컴파일러가 "괜찮다" 고 통과시킨 프로그램이 **정말** 괜찮은가?
이 장의 정리가 그것을 말한다.

```lowent
var x u64 be 1 .
var r mut_ref u64 be borrow x .   rem 배타 차용 — 고칠 수 있는 이름
set x 5 .                          rem ✘ 컴파일 거절: r 이 아직 살아 있다
```

## ② 필요한 수학

### 두 개의 기계

이 언어에는 같은 규칙을 보는 **기계가 둘** 있다.

| | 이름 | 언제 도나 | 무엇을 보나 |
|---|---|---|---|
| 정적 | **살아 있는 차용 목록** | 컴파일 시각 | 겹치는 차용을 만들려 하면 **거절** |
| 동적 | **차용 스택** | 실행 중(VM) | 무효화된 차용을 쓰면 **트랩** |

둘은 다른 자료구조다. 정적 쪽은 그냥 목록이고, 동적 쪽은 **지역마다 스택**을 둔다
(나중 차용이 위에 쌓인다).

이 장의 정리는 **둘이 서로 어긋나지 않는다**는 것이다.

### 이벤트라는 언어

증명을 위해 프로그램을 세 종류의 **이벤트 나열**로 줄인다. 이것이 증명의 첫 기술이다 —
어려운 대상(전체 언어)을 다루는 대신, 본질만 남긴 작은 대상을 만든다.

```
Create t x mut     차용을 만든다. 태그 t, 대상 지역 x, mut=고칠 수 있나
Use    t wr        차용 t 를 통해 접근한다. wr=쓰기인가
Own    x wr        지역 x 를 소유자가 직접 접근한다
```

정말 이 셋뿐이다. 그리고 규칙 다섯 개(D1~D5)로 동적 기계를 정의한다:

| 규칙 | 무슨 일 | 스택에 무슨 일 |
|---|---|---|
| D1 | 차용 생성 | 태그를 **위에 쌓는다** |
| D2 | 차용으로 **읽기** | 그 위의 **배타 항목만** 버린다(공유는 남는다) |
| D3 | 차용으로 **쓰기** | 그 위를 **전부** 버린다 |
| D4 | 소유자가 **읽기** | 배타 항목을 **전부** 무효화(오류가 아니다) |
| D5 | 소유자가 **쓰기** | 스택을 **비운다** |

★ D2 와 D3 의 차이가 요점이다. 읽기는 **공유 차용을 죽이지 않는다** — 여러 독자가 공존해도
아무 문제가 없기 때문이다. 쓰기는 위를 전부 버린다 — 그 위의 이름들은 이제 낡은 값을 보게
되므로 **더는 쓸 수 없어야** 한다.

그리고 D4·D5 가 "소유자가 다시 손대면 차용은 끝난다" 를 말한다. **오류로 만들지 않은 것**이
설계 선택이다: 소유자가 읽는 것은 나쁜 일이 아니고, 그 뒤에 죽은 차용을 **쓰려 할 때** 잡는다.

## ③ 정리와 그 뜻

### 정리 A — 합의(agreement)

> **Coq 원문**: `Theorem agreement : forall evs, wf evs -> static_green evs = true -> dyn_clean evs = true.`

> **평서문**: 정적 검사를 통과한(green) 프로그램은 실행해도 차용 위반이 일어나지 않는다.
> **모든** 이벤트 나열에 대해서.

이것이 이 언어의 **중심 정리**다. 왜 중요한가? 정적 검사의 존재 이유가 바로 이 문장이기
때문이다. 이 문장이 없으면 컴파일러의 "통과" 는 아무 뜻이 없다.

### 따름정리 — 대우

> **Coq 원문**: `Corollary no_violation_in_green : ... dyn_clean evs = false -> static_green evs = false.`

> **평서문**: 실행 중에 차용 위반이 났다면, 정적 검사는 **반드시** 그 프로그램을 거절했다.

같은 말을 뒤집은 것이다("A ⟹ B" 와 "¬B ⟹ ¬A" 는 같은 문장이다 — 2장의 대우). 그런데 뒤집으면
실용적 의미가 선명해진다: **런타임에 차용 위반을 보는 일은 컴파일러를 통과한 코드에서는
있을 수 없다.**

**막는 버그**: "컴파일은 됐는데 실행하니 메모리가 깨진다" — 그 조합 자체가 불가능하다
(이 모델 안에서. ⑥ 참조).

### 정리 B — 방향은 한쪽뿐이다

반대 방향(`dyn_clean ⟹ static_green`)은 **참이 아니고, 참일 필요도 없다**. 정적 검사는
**보수적**이다 — 실제로는 안전한 프로그램도 거절할 수 있다.

```
정적이 거절 · 동적으로 안전    →  손해 (다시 쓰면 된다)
정적이 통과 · 동적으로 위험    →  ★ 이것이 없음을 정리 A 가 말한다
```

04장에서 본 것과 **같은 비대칭**이다. 안전 쪽으로 틀리는 것은 불편이고, 위험 쪽으로 틀리는
것은 재앙이다.

## ④ 증명의 전략 — 불변식 두 개

증명은 01장의 **전략 1(불변식 보존)** 이다. 도미노를 세우려면 "한 걸음 갈 때 유지되는 성질" 을
찾아야 한다. 여기서는 **두 개**가 필요했다.

### 불변식 INV — 두 기계가 같은 것을 본다

> 정적으로 **살아 있는** 차용은 동적 스택에도 **있고**, 대상 지역과 mut 여부가 **일치한다**.

이것이 있으면 `Use t` 를 만났을 때 정적 기계가 통과시켰다면 동적 기계도 그 태그를 스택에서
찾는다 — 즉 트랩하지 않는다.

### 불변식 SINV — 겹친 차용은 전부 공유다

> 같은 지역에 살아 있는 **서로 다른** 차용 둘은 **모두 공유(shr)** 다.

왜 이것이 필요했나? 증명을 하다 보면 걸리는 자리가 있다. D3(차용으로 쓰기)은 그 위를 **전부**
버린다. 그런데 버려진 것 중에 **정적으로는 아직 살아 있는** 차용이 있으면? INV 가 깨진다.

SINV 가 그 구멍을 막는다. 정적 쪽 규칙 S1(`has_conflict`)이 배타 차용의 겹침을 애초에 거절하므로,
같은 지역에 공존하는 차용은 전부 공유다. 그리고 **쓰기는 배타 차용만 할 수 있으므로**, 쓰기를
하는 태그와 같은 지역에 살아 있는 다른 차용은 **존재하지 않는다**. 그러니 pop_above 가 지운
것은 정적으로도 죽은 것들뿐이다.

★ 이것이 증명에서 **실제로 배우는** 부분이다. "배타는 하나뿐" 이라는 규칙이 왜 필요한지
직관으로는 "겹치면 위험하니까" 라고 말하지만, 증명은 더 정확한 이유를 준다:
**그 규칙이 없으면 두 기계의 대응이 무너진다.** 규칙을 하나 느슨하게 하면 정확히 어디가
깨지는지 증명이 가리켜 준다.

### 나머지 — 자료구조 보조정리

`get_set_same`("담은 자리에서 꺼내면 담은 것이 나온다"), `get_set_other`("다른 자리는 안 바뀐다"),
`in_pop_above`("t 는 t 위를 버려도 남는다") 같은 지루한 사실들이 증명의 대부분이다.
증명이 길어지는 곳은 늘 흥미로운 곳이 아니라 이런 곳이다.

## ④′ 모델을 두 번 키웠다 — 그리고 한 번은 구현이 틀렸다

위 정리 A 의 모델은 지역을 **평평한 번호**로 봤다. 실제 언어는 그보다 복잡하다. 모델을 두 번
키웠고(`LowentPlace.v`·`LowentLaunder.v`), 두 번 다 정리 A 를 **다시** 증명했다.

### 확장 1 — place: `x.a` 와 `x.b` 는 다른 자리다

평평한 모델에서는 `x.a` 와 `x.b` 가 **둘 다 그냥 x** 다. 그러면 서로 다른 필드의 배타 차용 둘이
충돌하는 것으로 나온다 — **실제 언어는 통과시키고, 구현도 그렇다.** 증명이 구현을 못 따라가면
그 증명은 다른 언어에 대한 것이다.

그래서 지역을 **place**(경로)로 일반화했다:

```
place = 밑바탕 :: 필드들
   [0]        통째로 x
   [0;1]      x.f1
   [0;1;2]    x.f1.f2
```

그리고 지역 **동등성**(=)을 **겹침**(overlaps)으로 바꿨다:

> 두 place 가 겹친다 ⟺ **한쪽이 다른 쪽의 접두사다.**

`x.f1` 과 `x.f2` 는 서로의 접두사가 아니므로 겹치지 않는다 ✓.
`x` 와 `x.f1` 은 겹친다(전자가 후자의 접두사) ✓ — 통째로 빌리면 필드도 못 빌린다. 옳다.

★ 배울 점: **동등성을 겹침으로 바꾸는 것**이 확장의 전부였다. 정리와 불변식의 구조는 그대로다.
좋은 추상을 골랐으면 확장이 이렇게 국소적으로 끝난다.

### 확장 2 — op 경계: 차용을 함수로 "세탁" 하기

정리 A 의 이벤트 언어에는 **호출이 없었다.** 그래서 이 패턴이 모델 밖에 있었다:

```lowent
let r  be borrow x .   rem 차용 t1
let r2 be call f r .   rem ★ op 이 인자 차용을 "세탁해" 참조를 돌려준다
set x 1 .              rem 소유자 쓰기 — t1 이 죽는다
… r2 를 쓴다 …          rem ⚡ r2 는 사실 t1 과 **같은 차용**이다
```

구현이 이것을 실제로 겪었다. 정적 검사가 `r2` 를 차용으로 **알아보지 못해 통과시켰다.**
`UNPROVEN.md` 가 "열린 갭 D3(op 경계)" 로 기록했고, 결과를 **인자 차용의 별칭으로 등록**해
고쳤다(`low_region.c` 의 `alias[]`).

그리고 그 이야기를 **정리로 바꿨다**:

> **Coq 원문**:
> ```coq
> Theorem old_rule_is_unsound : wf laundered_escape /\
>   static_green_bad laundered_escape = true /\   (* 정적 검사가 통과시킨다 *)
>   dyn_clean laundered_escape = false.           (* 그런데 실행하면 위반 *)
> Theorem new_rule_catches_it : static_green laundered_escape = false.
> ```

> **평서문**: **고치기 전의 규칙은 건전하지 않았다** — 통과시키는데 실행하면 깨지는 프로그램이
> 존재한다. 그리고 **고친 규칙은 그것을 잡는다.**

★★ 이것이 이 저장소에서 증명이 하는 가장 값진 일이다. 그때까지 그것은 *"우리가 겪었다"* 는
**이야기**였다. 이야기는 잊히고, 리팩터링에 지워진다. 이제 그것은 **정리**다 —
누가 그 검사를 지우면 증명이 깨진다.

그리고 **과잉 거부가 아님**도 함께 증명했다(`honest_laundering` 은 여전히 통과한다).
고친 규칙이 정상적인 코드를 막지 않는다는 것 — 이것을 증명하지 않으면 "전부 거절" 도 정답이 된다.

## ⑤ 이것이 막는 버그

```lowent
rem ① 배타 차용이 살아 있는데 소유자가 쓴다
var x u64 be 1 .
var r mut_ref u64 be borrow x .
set x 5 .                    rem ✘ 거절 (D5 가 r 을 죽이므로 r 의 이후 사용이 위반)
set (deref r) 7 .

rem ② 배타 차용을 두 개 만든다
var a mut_ref u64 be borrow x .
var b mut_ref u64 be borrow x .   rem ✘ 거절: S1 — 같은 지역, 어느 쪽이 배타
set (deref a) 1 .

rem ③ 공유 차용으로 쓴다
var s ref u64 be borrow x .
set (deref s) 1 .            rem ✘ 거절 (E-TYPE-REF): 공유는 읽기만

rem ④ 공유 차용 여러 개 — 이것은 **통과한다**
var p ref u64 be borrow x .
var q ref u64 be borrow x .
let sum u64 be add (deref p) (deref q) .   rem ✔ 위험이 없다
```

이것들은 실제 진단 코드로 나온다:

| 상황 | 컴파일 시각 | VM 실행 중 |
|---|---|---|
| 겹친 배타 차용 | `E-REGION-EXCL` | — (컴파일에서 걸린다) |
| 공유로 쓰기 | `E-TYPE-REF` | — |
| 무효화된 차용 사용 | `E-REGION-EXCL` | `E-VM-EXCL`(모델 검사용 경로) |

## ⑥ 증명하지 않은 것

정직하게 적는다. 이 정리가 강한 만큼 경계도 분명하다.

1. **모델은 직선 이벤트 나열이다.** 분기와 루프가 없다. 실제 컴파일러는 제어 흐름을 따라
   차용의 생사를 계산한다(그것이 07장). 정리 A 는 그 계산이 옳다는 것을 **말하지 않는다**.
2. **태그는 신선하다고 가정한다**(`wf`). 구현이 태그를 재사용하면 가정이 깨진다. 구현은
   재사용하지 않지만, 그 사실 자체는 증명 밖에 있다.
3. **구현과의 1:1 대응은 전수 검사로 받친다.** 정리는 종이 위 두 기계에 대한 것이다.
   그 기계가 `low_region.c`/`low_ir.c` 와 같은지는 **유계 전수 모델 검사**가 확인한다 —
   지역 2개·태그 ≤4개·길이 ≤7 의 **10,490,024 시퀀스 전수, 위반 0**.

   ★ 이것은 "증명됨" 이 아니라 **"전수 검사됨"** 이다. 다만 봉투를 **재 보니 넓힐 수 있었다**
   (2026-07-31, `make test` 전체 시간으로 실측):

   | 길이 | 시퀀스 | 시간 | 위반 |
   |---:|---:|---:|---:|
   | 6 | 920,918 | 4.3 초 | 0 |
   | **7** | **10,490,024** | **5.0 초** | 0 | ← **지금 기본** |
   | 8 | 119,892,870 | 13.4 초 | 0 | ← 옵트인 |
   | 9 | **1,366,571,808** | 99 초 | 0 | ← 옵트인 |

   봉투를 **11배** 넓히는 값이 **0.7 초**였다. ⇒ *"비싸서 못 한다"* 고 적기 전에 **재 봐야 한다.**
   옵트인은 `make OPT="-O2 -DMC_N=9" test` — **13억 시퀀스에서 위반 0**.
   그래도 길이 10 이상은 **모른다**(그리고 그것을 적는 것이 이 절의 일이다).
4. **메모리 자체를 모델링하지 않았다.** 이벤트 모델은 "누가 접근할 권리가 있나" 만 본다.
   그 권리 체계가 실제 메모리 안전(해제 후 사용 등)으로 이어지는 단계는 별도이며, 일부는
   여전히 스케치다 — 16장 목록에 있다.
