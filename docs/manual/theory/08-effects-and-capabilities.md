# 08. 효과와 능력 — "무엇을 할 수 있나" 를 타입에 적기

> **근거**: 정본 §7(효과와 권한) · `LowentEffect.v` · `LowentOpt.v`.
> 구현: `impl/src/low_check.c` 의 `effect_of_word`·`decl_effect`.

## ① 5분 요약

여기까지(03~07장)는 **"메모리를 어떻게 만지나"** 였다. 이 장은 **"무엇을 할 수 있나"** 다.

모든 op(함수·프로시저)은 자기가 하는 일을 **선언**해야 한다:

```lowent
proc write_log input out cap io . input msg slice u8 . output u64 . effects io . do … end
fn   add2     input a u64 . output u64 . do … end        rem fn 은 effects 를 적지 않는다 — 언제나 none
```

`effects none` 은 강한 약속이다: **아무 것도 건드리지 않는다.** 전역을 읽지도, 할당하지도,
화면에 쓰지도, 대기하지도 않는다. 이 약속을 어기면 컴파일이 안 된다.

왜 유용한가? `effects none` 인 op 은 **몇 번 불러도 같은 값이 나오고, 순서를 바꿔도 된다**.
그것이 최적화의 근거이고, 동시에 **읽는 사람의 근거**다.

## ② 필요한 수학

### 멱집합 격자 — 2장의 격자가 여기서 다시

효과는 **원자의 집합**이다. 지금 있는 원자(`none` 과 원자 15개, 그중 아홉에 원시 연산이 있다):

```
none  alloc  heap  io  wait  lock  atomic  unsafe  device
page_fault  blocking  cancel  detach  panic  state  concurrent
```

`{io, alloc}` 처럼 **여러 개**를 가질 수 있다. 그러면 자연스러운 순서가 하나 있다:

```
ε₁ ⊑ ε₂   ⟺   ε₁ ⊆ ε₂          "ε₁ 은 ε₂ 보다 적게 한다"
```

이것이 **부분 순서**고(2장), 집합의 부분집합 관계는 **격자**를 이룬다. join 은 합집합이다:

```
{io} ⊔ {alloc} = {io, alloc}
{} (= none) 이 최소 원소 ⊥
```

그리고 격자 하나로 필요한 **두 가지**가 다 된다:

| 무엇 | 격자 연산 | 뜻 |
|---|---|---|
| **전파**(propagation) | **⊔**(합집합) | 내가 부르는 것들의 효과를 다 모으면 내 효과다 |
| **게이팅**(gating) | **⊆**(부분집합) | 선언한 것보다 **적게** 하는 것은 괜찮다 |

이것이 03장의 타입 격자와 **같은 형태**다. 다른 문제인데 같은 수학이 답한다 — 격자를 한 번
배워 두면 두 곳에서 쓴다. 그래서 2장을 먼저 놓았다.

### 왜 계층이 아니라 평면인가

`io` 를 `{read, write}` 로 쪼개는 **계층 격자**도 가능하다. 이 언어는 지금 **평면**을 쓴다.
이유: 계층으로 얻는 정밀도는 능력(capability) 쪽에서 이미 얻을 수 있고, 평면은 ⊆ 판정이
간단해 **비용이 보인다**. 정밀도를 두 곳에서 표현하면 그 둘이 어긋나기 시작한다.

## ③ 규칙과 그 뜻

효과 쪽에도 기계 증명이 **생겼다**(`LowentEffect.v` — 아래 ⑥). 먼저 컴파일러가 실제로 **강제하는
규칙**을 보고, 그 규칙들이 무엇을 보장하는지 본다.

### 규칙 1 — 전파: 선언은 실제보다 작을 수 없다

> `f` 가 `g` 를 부르면 `effects(f) ⊇ effects(g)` 여야 한다. 아니면 **`E-EFFECT`**(`fn` 이면 `E-EFFECT-CALC`).

**막는 버그**: `effects none` 이라 적힌 op 이 몰래 파일을 쓰는 것. 그 op 을 최적화기가 재정렬
하거나 지워도 된다고 믿으면 **관측 가능한 동작이 사라진다**.

### 규칙 2 — 순수성: 순수 op 은 남의 것을 고칠 수 없다

> `fn`(순수 함수)이 호출자의 버퍼를 쓰면 **`E-EFFECT-PURITY`**.

`fn` 과 `proc` 의 구별이 여기 걸려 있다. `fn` 은 값을 계산하고, `proc` 은 일을 한다.

실측한 구멍: 액터의 `on` 핸들러가 **이 검사를 우회**했다. IR 이 순수성을 `kw != proc` 로
판단했으므로 `on` 이 순수로 세어졌고, **액터 상태를 고치는 핸들러가 `effects none` 을 선언해도
아무도 반대하지 않았다**(맨 `op` 기본값을 없애면서 드러났다).
같은 죄인데 `fn` 은 잡히고 `on` 은 안 잡혔다 — **판정 기준이 낱말의 모양이었기 때문**이다.

### 규칙 3 — `effects` 절은 원자의 **목록**이다

> `effects io alloc .` 은 두 원자를 선언한 것이다.

당연해 보이지만, 구현이 **첫 낱말 하나만** 읽고 있던 때가 있었다. 그 상태에서는
`effects io alloc` 이 **io 로만** 등록되고, 두 번째 원자부터는 **선언해도 없는 것과 같았다** —
그러면 그 op 은 alloc 을 "선언 안 한 효과" 로 잡히거나(거짓 양성), 반대로 놓친다.

교훈: **선언을 읽는 코드의 버그는 선언 체계 전체를 무력화한다.** 규칙이 아무리 옳아도
입력을 잘못 읽으면 그 규칙은 없는 것이다.

### 규칙 4 — 트랩은 효과가 아니다 (경계선 결정)

이것이 이 장에서 가장 생각할 거리다. `index s i` 는 범위를 벗어나면 트랩한다. 그러면 `index` 는
`panic` 효과를 가져야 하나?

**아니다.** 결정과 그 근거:

> `panic` 은 **명시적 `panic "…"`** 만 산입한다. `index` 는 `effects none` 으로 통과한다.

왜? **트랩 가능성은 계약이 말하는 것이고 효과가 말하는 것이 아니다.**

```
index 의 위험      →  requires lt i (len s) 로 **없앨 수 있다**  (05장이 실제로 검사를 지운다)
효과 표시          →  **지워지지 않는다**
```

없앨 수 있는 것을 효과로 표시하면 그 표시는 영원히 남는다. 그러면 **거의 모든 op 이 panic 을
갖게 되어** 표시가 무의미해진다.

> **효과 = "이 op 이 무엇을 하는가"** · **계약 = "언제 안전한가"** — 둘을 섞지 않는다.

경계를 이렇게 그은 덕에 `panic` 표시가 여전히 정보를 가진다: `panic` 이 붙어 있으면 그 op 은
**의도적으로** 프로그램을 끝낼 수 있다는 뜻이다.

### 능력(capability) — 효과의 짝

효과가 *"무슨 종류의 일을 하나"* 라면, 능력은 *"그 일을 할 **권한**을 어디서 받았나"* 다.

```lowent
proc main input out cap io . output u8 . effects io . do
  return narrow u8 (write_out out 1 "hi\n") .
end
```

`cap io` 를 **인자로 받아야** 화면에 쓸 수 있다. 아무 데서나 전역으로 꺼내 쓰지 못한다.
이것이 객체-능력(object-capability) 모형이고, 두 가지를 준다:

1. **감쇠(attenuation)** — 받은 능력을 좁혀서 넘길 수 있다(읽기 전용 파일 능력 등).
   평면 효과 격자로 못 하는 정밀도를 여기서 얻는다.
2. **국소적 감사** — op 의 서명만 보면 그것이 무엇에 손댈 수 있는지 **전부** 보인다.
   숨은 전역 통로가 없다는 것이 요점이다.

## ④ 왜 이것이 "안전" 인가

효과 체계는 메모리 안전을 주지 않는다(그건 06장이다). 대신 **다른 종류**의 안전을 준다:

| 주는 것 | 어떻게 |
|---|---|
| 최적화의 정당성 | `effects none` 이면 재정렬·CSE·삭제가 관측 동작을 바꾸지 않는다 |
| 감사 가능성 | `io` 를 하는 코드를 **찾을 수 있다**(선언에 적혀 있으므로) |
| 프로파일 게이팅 | 임베디드 하한선에서 `alloc` 하는 op 을 **빌드 오류로** 막는다 |
| 놀람의 부재 | 순수하다고 적힌 것이 정말 순수하다 |

세 번째가 실제로 값이 크다. 힙이 없는 기계(ATtiny 급 하한선)에서는 `alloc` 하는 코드가
**컴파일되면 안 된다.** 효과 선언이 있으면 그 판정이 `⊆` 한 번이다.

## ⑤ 이것이 막는 버그

```lowent
rem ① 순수하다고 선언하고 일을 한다
fn f input out cap io . input a slice u8 . output u64 . do
  return write_log out a .         rem ✘ E-EFFECT-CALC: write_log 는 io 다
end

rem ② 순수 함수가 남의 버퍼를 고친다
fn g input b mut slice u8 . . output u64 . do
  set (index b 0) 1 .              rem ✘ E-EFFECT-PURITY
  return 0 .
end

rem ③ 없는 원자를 선언한다
proc h … effects netwrok . do … end   rem ✘ E-EFFECT-UNDEF (오타를 잡는다)

rem ④ 같은 원자를 두 번
proc i … effects io io . do … end     rem ✘ E-EFFECT-DUP

rem ⑤ 순수 op 이 실제로는 효과를 계산한다
fn j … do … end        rem ✘ E-EFFECT-CALC
```

⑤의 진단(`E-EFFECT-CALC`)에는 **뼈아픈 이야기**가 붙어 있다. 파라미터 이름을 `raw` 로 쓰면
이 진단이 떴다 — `raw` 가 원시 포인터 낱말이라 효과 추론이 **조용히 오염**됐기 때문이다.

```lowent
fn f input raw u64 . output u64 . do return add raw 1 . end
rem → E-EFFECT-CALC: "순수하다고 선언했는데 효과를 수행한다"   오진이다
```

진짜 이유는 *"예약된 낱말을 이름으로 썼다"* 인데 진단은 **순수성**을 가리켰다. 프로그래머를
엉뚱한 곳으로 보내는 진단이 가장 나쁘다. 그래서 그 낱말들도 `E-NAME-BUILTIN` 으로 넘겨
**같은 죄에 하나의 진단**만 남겼다.

이 문서가 진단 이야기를 계속 하는 이유: **증명이 정하는 것은 "무엇을 거절하나" 이고,
사람이 만나는 것은 "왜 거절했나" 다.** 후자가 틀리면 전자의 값이 절반으로 줄어든다.

## ⑤′ 기계 증명 — `LowentEffect.v`

> **Coq 원문**: `Theorem effect_sound : prog_ok P = true -> lookup P f = Some (d, b) ->
> performs P (ECall f) a -> In a d.`

> **평서문**: 검사를 통과한 프로그램에서 op `f` 를 부르면, **실제로 일어나는 모든 효과는
> f 가 선언한 것 안에 있다.** 호출 깊이와 무관하게.

### 왜 이것이 순환이 아닌가 — 이 증명의 요점

구현은 호출 지점에서 **피호출자의 본문을 다시 걷지 않는다.** 피호출자의 **선언**을 쓴다.
언뜻 순환처럼 보인다: 선언이 선언을 믿는다. 그런데 **모든 op 이 검사되면** 순환이 아니다.

그 이유를 증명이 정확히 말해 준다: **귀납이 프로그램이 아니라 실행에 대한 것**이기 때문이다.
효과가 하나 *일어나면* 그것은 어떤 유한한 호출 깊이에서 일어나고, 그 깊이에 대한 귀납이 닫힌다.
⇒ **재귀도, 상호 재귀도, 무한 재귀도 따로 다룰 것이 없다.** (그래서 `rec_prog` 예제가 있다:
자기를 부르는 op 이 검사를 통과하고, `io` 가 실제로 일어나며, `alloc` 은 **일어날 수 없다.**)

### 최적화 적법성 — 절반을 갚았다

> `pure_calls_commute` — 순수한 조각은 **자리를 바꿔도** 일어나는 효과가 같다.
> `dropping_pure_is_legal` — 순수한 조각은 **지워도** 일어나는 효과가 같다.

재정렬·죽은 코드 제거·CSE 가 기대는 문장의 **효과 층**이 이것이다. **값 층은 아직 아니다** —
*"같은 값을 준다"* 는 별개의 정리이고 값 의미론을 요구한다(⑥ 2번).

## ⑥ 증명하지 않은 것

1. 효과 건전성은 증명했다(⑤′). 다만 **구현이 그 모델과 같다**는 것은 시험과 두 백엔드 대조가
   받치는 경험적 대응이다(16장 ⑤). 그리고 `task_group` 이 `concurrent` 를 **흡수하는** 규칙은
   ⊆ 규율이 아니라 **요구의 해소**라 모델 밖이다.
2. 효과 기반 최적화의 적법성은 값 층까지 증명했다(`LowentOpt.v`): 값·상태·**출력 열**을 가진 모델에서 **재정렬 · CSE ·
   memoize · 죽은 코드 제거**가 넷 다 적법함을 증명했다. 열쇠는 한 줄이다 —
   **값은 읽는 칸에만 달렸다**(`value_depends_only_on_reads`).
   그리고 **전제가 장식이 아님**을 반례로 보였다: 효과 있는 조각을 재정렬하면 값이
   14 에서 7 로 **바뀌고**, `print` 를 지우면 출력이 준다. 남은 것은 **호출 경계**
   (이 파일의 순수 판정을 op 경계로 올리는 일)와 **트랩 시점**이다.
3. **평면 격자의 정밀도 한계.** `io ⊑ {read, write}` 같은 정련은 하지 않았다(deferred).
   지금은 능력 감쇠로 대체하는데, 그 둘이 같은 정밀도를 준다는 논증은 **없다**.
4. **effect-row 다형성이 없다.** "호출자의 효과를 그대로 물려받는 op" 을 쓸 수 없어,
   고차 함수를 쓰면 효과를 가장 넓게 선언해야 한다.
5. **일부 원자는 어휘만 있고 원시 연산이 없다**(`page_fault`·`blocking`·`cancel`·`detach`·`lock`·
   `device` 중 일부). 선언할 수는 있어도 그것을 **발생시키는** 연산이 아직 없으므로,
   그 원자에 대한 전파는 실전 검증이 얇다.
