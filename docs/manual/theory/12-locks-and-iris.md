# 12. 락과 분리논리 — 무거운 도구가 실제로 필요한 유일한 자리

> **근거**: `LowentLock.v` — `locked_exclusive`·`newlock_spec`·`try_acquire_spec`·`acquire_spec`
> ·`release_spec`·`incr_spec`·`two_threads_spec` (전부 Qed, **Iris** 필요).
> 10개 증명 파일 중 **Iris 가 필요한 것은 이 하나뿐이다.**

## ① 5분 요약

09장에서 본 규율(disjoint·액터 격리)은 **같은 자리를 두 스레드가 만지는 일을 아예 없앤다.**
그러면 어려운 추론이 필요 없다.

그런데 **락 자체는** 그럴 수 없다. 스핀락의 동작이 바로 그것이기 때문이다:

```
두 스레드가 **같은 자리**(락 워드)를 **실제로 동시에 두드린다.**
```

여기서는 규율이 안전을 줄 수 없다. 대신 **불변식(invariant)** 이 안전을 지킨다. 그 추론이
**동시성 분리논리**의 일이고, 그것이 **Iris** 다.

이 장이 증명하는 것: 설계가 정한 *"lock/rwlock 은 atomic CAS 위의 라이브러리다"* 가
**정말인가.** CAS 하나로 세운 스핀락이 진짜로 상호배제를 주는가.

## ② 필요한 수학

### 분리논리 — `∗` 라는 새 접속사

보통의 논리에서 `A ∧ B` 는 "둘 다 참" 이다. 분리논리는 접속사를 하나 더 둔다:

```
A ∗ B      "A 와 B 가 참이고, **서로 다른 메모리 조각**에 대한 것이다"
```

이 한 글자가 왜 중요한가? 메모리에 대한 주장은 **소유권**을 함의해야 하기 때문이다.

```
x ↦ 3      "x 가 3 을 담고 있다" 가 아니라
           "나는 x 를 **소유하고 있고** 그 값이 3 이다"
```

`x ↦ 3 ∗ y ↦ 4` 는 x 와 y 가 **다른 자리**임을 말한다. 그래서 x 에 쓰는 것이 y 에 대한 주장을
망가뜨리지 않는다 — 그것이 국소적 추론(local reasoning)이고, 06장의 배타 차용과 **같은 발상**이다.

실은 순서가 반대다. Rust 의 차용 검사기가 분리논리의 발상을 타입 체계로 옮긴 것이고,
이 언어의 EXCL 규칙도 그 계보에 있다. **06장은 이 장의 아이디어를 컴파일 시각으로 내린 것**이다.

### 호어 삼중항 — 명세를 적는 방법

```
{{{ 사전조건 }}}  프로그램  {{{ 결과, 사후조건 }}}
```

*"사전조건을 만족하는 상태에서 이 프로그램을 돌리면, 끝났을 때 사후조건이 성립한다."*

### 불변식 — 여러 스레드가 공유하는 약속

```
lock_inv γ lk R  :=  (lk ↦ false ∗ R)  ∨  (lk ↦ true)
```

읽는 법: **락이 열려 있으면**(`false`) 보호 자원 `R` 이 **불변식 안에 들어 있다.**
**잠겨 있으면**(`true`) `R` 은 어디 있나? — **잠근 스레드가 갖고 있다.**

이 한 줄이 락의 전부다. `R` 이 두 곳에 동시에 있을 수 없으므로, `R` 을 가진 스레드는 하나뿐이다.

### 유령 상태(ghost state) — 증명에만 있는 토큰

```
locked γ  :=  own γ (Excl ())
```

`Excl` 은 "배타적" 이라는 뜻의 대수 원소다. 이것은 **런타임에 존재하지 않는다** — 컴파일된
코드에 이런 토큰은 없다. 순수하게 **증명 안에서만** 도는 회계 장치다.

## ③ 정리와 그 뜻

### 정리 F0 — 토큰은 둘일 수 없다

> **Coq 원문**: `Lemma locked_exclusive γ : locked γ -∗ locked γ -∗ False.`

> **평서문**: `locked` 토큰을 **두 개** 가졌다고 가정하면 **모순**이다.

이것이 상호배제의 기계적 심장이다. 나머지 정리들이 "락을 잡으면 토큰을 받는다" 를 말하므로,
두 스레드가 동시에 락을 잡았다면 토큰이 둘이고 — 그것은 거짓이다.

### 정리 F1 — 락 만들기

> **Coq 원문**: `Lemma newlock_spec (R : iProp Σ) : {{{ R }}} newlock #() {{{ lk γ, RET lk; is_lock γ lk R }}}.`

> **평서문**: 보호할 자원 `R` 을 **넘겨주면** 락을 얻는다.

사전조건이 `R` 인 것에 주의. 락을 만드는 대가로 **자원을 포기한다**. 이제 그 자원에 닿는
유일한 길은 락을 잡는 것이다. "자원을 락 안에 넣는다" 는 말이 증명에서는 소유권 이전이다.

### 정리 F2 — 잡기

> **Coq 원문**: `Lemma acquire_spec γ lk R : {{{ is_lock γ lk R }}} acquire lk {{{ RET #(); locked γ ∗ R }}}.`

> **평서문**: 락을 잡으면 **토큰과 자원을 둘 다** 받는다(`locked γ ∗ R`).

`∗` 가 여기서 일한다 — 받은 자원은 **내 것**이고, 다른 누구의 것과 겹치지 않는다.
그래서 그 뒤로는 **단일 스레드처럼** 추론할 수 있다.

### 정리 F3 — 놓기

> **Coq 원문**: `Lemma release_spec γ lk R : {{{ is_lock γ lk R ∗ locked γ ∗ R }}} release lk {{{ RET #(); True }}}.`

> **평서문**: 놓으려면 **토큰과 자원을 둘 다 반납**해야 한다. 놓은 뒤에는 아무것도 남지 않는다
> (`True`).

이 명세가 두 가지 버그를 **타입 수준에서** 막는다:

```
락을 안 잡고 놓는다        → locked γ 가 없어 사전조건을 못 맞춘다
놓은 뒤에도 자원을 쓴다     → R 을 반납했으므로 손에 없다
```

### 정리 F4 — 실전 예: 두 스레드의 증가

> **Coq 원문**:
> ```coq
> Lemma incr_spec γ lk c : {{{ is_lock γ lk (∃ n : Z, c ↦ #n) }}} incr lk #c {{{ RET #(); True }}}.
> Lemma two_threads_spec : {{{ True }}} two_threads #() {{{ (n : Z), RET #n; True }}}.
> ```

증명한 프로그램:

```
두 스레드가 동시에  acquire ; c ← !c + 1 ; release  를 돈다.
```

> **평서문**: 두 스레드가 동시에 증가시켜도 **경합 없이** 끝나고, 프로그램은 값을 하나 낸다.

**막는 버그**: 락 없는 `c ← !c + 1` — 고전적인 lost update. 여기서는 `c ↦ n` 을 락에서 받아야만
쓸 수 있으므로 락을 건너뛰는 코드는 증명이 되지 않는다.

정직하게: `two_threads_spec` 은 **결과가 정확히 2 라고 말하지 않는다.** "값이 나온다" 만
말한다. 정확한 합계를 말하려면 유령 카운팅이 더 필요하다. 이 파일의 목표는 **락이 자원을
지킨다**는 것이었고, 그것은 F0~F3 에서 증명됐다.

## ④ 증명의 전략 — 그리고 왜 여기만 Iris 인가

증명들의 공통 모양:

```
① 불변식을 연다      iInv nroot as (b) "[Hl HR]"
② CAS 를 실행한다    (성공/실패로 갈린다)
③ 불변식을 닫는다    (성공했으면 R 을 들고 나오고, 실패했으면 그대로 둔다)
```

②의 **원자적 순간**에만 불변식을 열 수 있다는 것이 Iris 의 규칙이다. 그 규칙 덕에
"불변식이 잠깐 깨진 상태를 다른 스레드가 볼 수 없다" 가 보장된다.

### 도구 선택의 기록

이 저장소는 도구를 **필요한 만큼만** 썼다:

| 파일 | 도구 | 왜 |
|---|---|---|
| EXCL·Loop·DRF·Par·RC11·Block·Place·Launder·NumericLattice | **순수 Coq** | 규율·집합론·격자·그래프 판정이면 된다 |
| **Lock** | **Iris** | 두 스레드가 **같은 자리를 실제로** 두드린다 |

09장에서 본 판단을 다시 적으면: *"동시성이니까 분리논리가 필요하다" 는 반사적 판단이 틀렸다.*
9개 파일이 그것 없이 갔고, **정말 필요한 한 곳**에서만 무거운 도구를 들었다.

그리고 이것이 Coq 을 고른 이유다. Iris 는 Coq 전용이고 Lean 에는 성숙한 대응물이 없다.
**언젠가 필요할 도구가 어디 있는지**가 증명 언어 선택을 정했다.

## ⑤ 이것이 막는 버그

```
① 락 없이 공유 카운터 증가        → 자원을 손에 넣을 길이 없다 (F2 를 안 거쳤다)
② 락을 잡지 않고 release          → locked γ 가 없다 (F3 사전조건)
③ release 뒤에도 자원 사용         → R 을 반납했다 (F3 사전조건)
④ 두 스레드가 동시에 임계구역      → locked γ 가 둘 (F0 이 모순을 낸다)
⑤ 락을 두 번 잡고 한 번 놓음      → 두 번째 acquire 가 영원히 못 온다(교착 — ⑥ 참조)
```

⑤가 경계다. **교착(deadlock)은 이 증명이 막지 않는다.** 명세가 "잡으면 자원을 받는다" 이고
"반드시 잡힌다" 가 아니기 때문이다.

## ⑥ 증명하지 않은 것

정직하게 — 락은 이 문서에서 **경계가 가장 많은** 주제다.

1. **모델은 순차 일관성(SC)이다.** `heap_lang`(Iris 의 언어)은 SC 모델이고, RC11 의 약한
   ordering(relaxed·acquire·release)은 **여기서 다루지 않는다.**

   그런데 그것으로 **충분하다**: 이 언어의 기본 ordering 이 `seq_cst` 이므로(11장 E1),
   기본값으로 쓰는 level-3 코드는 정확히 SC 모델 안에 있다. **약한 ordering 을 명시해서 SC 를
   벗어난 코드만** iGPS/Cosmo 의 몫으로 남고, 그것은 **감사 대상**이다(설계가 그렇게 정해 뒀다).
   가둠이 여기서도 성립한다.
2. **교착 자유(deadlock freedom)를 증명하지 않았다.** 위 ⑤. 락 순서 규율은 별개 문제다.
3. **공정성(fairness)·굶주림 없음을 증명하지 않았다.** 스핀락이 **언젠가** 잡힌다는 보장이 없다.
4. **`two_threads_spec` 은 정확한 합계를 말하지 않는다.** 위 ③ 참조.
5. **구현이 이 스핀락이라는 보장이 없다.** 증명한 것은 `heap_lang` 으로 쓴 CAS 스핀락이고,
   실제 런타임의 락이 그것과 같은지는 **검증되지 않았다**. 이것이 이 파일과 구현 사이의
   가장 큰 간극이다.
6. **rwlock 도 다룬다**(`LowentRWLock.v`).
   한 워드에 세 뜻을 담는 고전적 rwlock(0=빔 · n>0=독자 n · −1=쓰기잠금)에서
   **쓰기 잠금의 배타성**을 증명했다(`wlocked_exclusive`·`wlock_spec`·`wunlock_spec`).
   CAS 가 **0 에서만** 성공하므로 *"독자가 있는데 쓰기가 들어간다"* 가 막힌다 — 실제 rwlock
   버그의 대부분이 그것이다.
   **읽기 쪽도 채웠다**(같은 파일 §5): 그 "분수 소유권" 이 바로
   Iris 가 이미 갖고 있는 것이었다 — `iris.heap_lang.lib.rw_lock` 이 인터페이스를 분수 술어
   `Φ : Qp → iProp` 로 적고 `rw_spin_lock` 이 **검증된 인스턴스**다.

   > `rw_reader_gets_a_fraction` — 독자는 **분수**(`Φ q`)를 받는다(여럿이 동시에)
   > `rw_writer_and_reader_exclusive` — 쓰기와 읽기는 **동시에 있을 수 없다** ← rwlock 의 심장
   > `rw_writer_gets_everything` — 쓰기는 **전부**(`Φ 1`)를 받는다

   값진 것은 ②가 **같은 문장의 다른 증명**이라는 점이다: 우리 것은 *"CAS 가 0 에서만
   성공한다"* 로(구현에 가깝다), 빌린 것은 **유령 상태**로(일반적이고 분수까지 다룬다).
   ⇒ 15장의 원리("두 방법으로 만들고 맞대 본다")가 **증명 층에서도** 한 번 더 성립한다.
   **빌렸다**: TCB 에 `rw_spin_lock` 이 추가된다(16장 ④). 다시 짓지 않은 이유는 하나다 —
   **같은 것을 두 벌 두면 갈린다.**
6-bis. **교착 자유와 굶주림 없음도 증명했다.**

   > `no_deadlock`(`LowentDeadlock.v`): 모든 스레드가 잠금을 **오름차순으로만** 잡으면,
   > 어떤 상태에서도 **진행할 수 있는 스레드가 반드시 있다** — 전원이 동시에 막히지 않는다.

   증명의 씨앗은 한 문장이다: **가장 큰 잠금을 원하는 스레드**를 보라. 그것이 막혔다면 그
   잠금을 쥔 남이 있고, 규율에 의해 그 남이 원하는 것은 **더 크다** — 최대성에 모순이다.
   그리고 규율을 어기면 **실제로 교착이 난다**는 상태를 계산으로 보였다(`violating_the_order_deadlocks`).
   ☞ 정직하게: **도구가 이 규율을 강제하지 않는다.** 그래서 이것은 *"이렇게 쓰면 안전하다"*
     이지 *"컴파일러가 막아 준다"* 가 아니다. 검사로 만들려면 잠금에 **정적 순서**를 붙여야 한다.

   > `no_starvation`(`LowentFair.v`): T0 협력 스케줄러(라운드로빈)에서 준비된 태스크는
   > **자기 앞의 수 + 1 걸음 안에** 반드시 돈다. *"언젠가"* 가 아니라 **유계**다.

   귀납의 측정치가 **길이가 아니라 자리**인 것이 요점이다 — 회전은 길이를 보존하므로.
   그리고 **회전이 없으면 굶는다**는 것도 증명했다(둘째 태스크가 영원히 안 돈다).
   ☞ 한계: 협력형은 **양보를 가정**한다. `yield` 없이 무한 루프를 돌면 스케줄러가 할 수
     있는 것이 없다. 우선순위·차단은 이 모델 밖이다.

7. **약한 메모리에서의 프로그램 논리.** 필요한 것은 **iRC11/gpfsl**(RC11 위의 Iris 논리)이고,
   gpfsl 은 Iris **개발판**과 Rocq 9.x 를 요구한다. 그래서 증명은 **두 도구**로 확인한다:
   Rocq 9.2(Iris 개발판·gpfsl 포함)는 전부를, Coq 8.20.1 은 gpfsl 이 필요한 둘을 뺀 나머지를 돌린다.
   같은 증명을 두 도구가 받아들인다는 것 자체가 값이다(⑥-8).
   `LowentIRC11.v` 가 그 위에서 **약한 메모리 프로그램 논리**의 첫 정리를 세운다:

   > `lowent_release_acquire_delivers_the_data`(Qed · `Print Assumptions` = **Closed under the
   > global context**): release 쓰기 · acquire 읽기로 짠 **메시지 전달 프로그램**은 **RC11 에서**
   > 읽는 쪽이 **반드시 데이터를 본다**(42). **SC 를 가정하지 않는다.**

   ⇒ *"약한 ordering 을 명시하면 동기화된다"* 가 **실행 하나**(11장 E4)에서 **프로그램 전체**로
   올라갔다. 이 장의 ⑥-1 이 적은 한계(heap_lang = SC 모델)를 **넘은 첫 자리**다.
   정직하게: **증명을 빌렸다.** `mp_instance_gen_inv` 는 gpfsl 의 것이고, 이 파일이 한 것은
   *"그 명세가 우리 설계 결정이 필요로 하는 바로 그 문장"* 임을 진술하고 잇는 것이다 —
   그러면 **TCB 에 gpfsl 과 iris dev 가 추가된다**(16장 ④). 그리고 우리 컴파일러가 그 프로그램을
   낸다는 보장은 여전히 없다(⑥-5 와 같은 간극).
   **그리고 그 도구로 라이브러리를 하나 세웠다**(`lib/spsc.low` · `LowentSPSC.v`):
   단일 생산자·단일 소비자 **링버퍼**다. 잠금이 없다 — 대신 `order` 를 **손으로 적는다**.

   ```lowent
   rem 생산자(spsc_push): 칸을 **먼저** 채우고, 그다음에 색인을 공개한다
   set (index buf ti) v .
   atomic_store ctl 1 nx order release .        rem 위의 쓰기를 **밀어낸다**

   rem 소비자(spsc_pop): 그 색인을 acquire 로 읽으면 그 앞의 쓰기가 **보인다**
   let t u64 be atomic_load ctl 1 order acquire .
   set (index out 0) (index buf hi) .
   ```

   > `lowent_spsc_push_is_correct` · `lowent_spsc_pop_is_correct` — 이 짝이
   > **RC11 에서** 옳다(가득/빔 판정 포함). SC 를 가정하지 않는다.

   **또 빌렸다**: 알고리즘 수준 증명은 gpfsl 의 `circ_buff` 다. 이 파일이 하는 일은
   *"우리가 방출하는 ordering 이 그 명세가 요구하는 바로 그것"* 임을 잇는 것이다.
   ⇒ 그래서 **하나만** 넣었다. MPSC·MPMC·seqlock 은 **빌릴 근거가 없고**, 근거 없이 넣으면
   `std.*` 가 *"검증됐다고 적혀 있으나 아무도 검증하지 않은 것"* 의 창고가 된다.
   교훈 하나: *"무겁다"* 로 적어 둔 것을 **실제로 재 보니** 대부분이 툴체인 조립이었고,
   진짜 위험(14 파일 재검증)은 **0** 이었다. **재 보기 전에는 비용을 모른다.**
8. **두 도구에서 검증된다** — Coq 8.20.1 · Rocq 9.2. 정리는 **모델**에 대한 것이지만 그 모델을
   확인하는 것은 **프로그램**이다. 서로 다른 두 확인기가 같은 답을 내면 **확인기 자체의 결함
   가능성**이 준다(그 가능성은 04장 TCB 표의 첫 줄이다).
