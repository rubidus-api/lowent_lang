# 13. 문법은 대수다 — 어느 닫개로 닫아도 같은 나무

> **근거**: `LowentBlock.v` — `one_form_is_a_block`·`body_is_one_thing`·`block_assoc`
> ·`nested_block_flattens`·`closers_agree`·`comma_does_not_close`·`three_reasons_one_rule`
> ·`no_fourth_spelling_is_needed`·`paren_does_not_leak_inward/outward` (전부 Qed) · PRINCIPLES.md §0.

## ① 5분 요약

여기까지(03~12장)는 **의미론**이었다 — 프로그램이 무엇을 하나. 이 장은 **표면**이다 —
프로그램이 어떻게 생겼나.

문법에 증명이 왜 필요한가? 실제로 겪은 일이기 때문이다:

> **파서와 그 뒤 단계가 서로 다른 문법을 믿고 있었다.** 파서가 `.` 로 form 을 조각내고,
> 뒤 단계가 말없이 다시 붙이고 있었다.

두 층이 다른 문법을 믿으면 그 차이는 **버그로 나온다**(PRINCIPLES.md §0). 그래서 문법의 세 성질을
기계로 못 박았다:

| | 성질 |
|---|---|
| ① | **한 문장은 한 문장짜리 블록이다** — `S ≡ do S end` |
| ② | **닫개는 결정적이다** — `.` · `end` · `)` 가 **같은 것**을 한다(개행은 닫개가 아니다 — 공백이다) |
| ③ | **블록은 결합적이다** — 블록 안의 블록은 자기 자리에서 펼쳐진다 |

## ② 필요한 수학

### 대수 구조 — 항등원과 결합법칙

10장에서 결합법칙을 봤다. 여기서는 그것을 **문법**에 쓴다.

```
결합적:   블록을 이어 붙이는 것이 순서와 무관하다
항등원:   빈 블록은 아무것도 아니다  (0 이 덧셈에서 하는 일)
```

이 두 성질을 갖는 구조를 **모노이드**라 한다. 목록을 이어 붙이는 것이 대표적인 모노이드다.
그리고 프로그램의 **문장 나열**이 정확히 그 구조다.

### 뜻함수(denotation) — 서로 다른 표기가 같은 뜻인지 보는 법

두 표기가 "같은지" 를 말하려면 기준이 필요하다. 각 나무를 **평평한 문장 나열**로 보내는
함수 `denote` 를 두고, 그 결과가 같으면 같다고 한다.

```
denote(do S end) = [S] = denote(S)     ⇒  둘은 같다
```

★ 이것이 이 장의 유일한 기술이다. **"같다" 의 뜻을 함수로 정하고, 등식을 계산으로 확인한다.**

## ③ 정리와 그 뜻

### 정리 G1 — 한 문장은 한 문장짜리 블록이다

> **Coq 원문**: `Theorem one_form_is_a_block : forall s, denote (wrap s) = denote s.`

> **평서문**: 문장 하나를 블록으로 감싸도 뜻이 같다.

파서는 제어 머리의 본체를 이렇게 **탈설탕**한다:

```
if c . S .      ↦      if c . do S end
```

이 정리가 그 탈설탕이 **의미를 바꾸지 않음**을 말한다.

> **따름정리**(`body_is_one_thing`): 본체 자리에 **문장을 쓰든 블록을 쓰든** 같다.

★ 이것이 언어 설계 결정 하나를 정당화한다. **C 는 문장(statement)과 복합문(compound
statement)을 다른 종류로 갈라 놓았다.** 그래서 C 에는 `if (c) x = 1;` 과 `if (c) { x = 1; }` 가
문법적으로 다른 것이고, 유명한 함정(`goto fail;`)이 그 틈에서 나왔다.

**이 언어는 가르지 않는다.** 이 정리가 그것을 기계로 못 박는다.

### 정리 G2 — 닫개들은 같은 일을 한다

> **Coq 원문**: `Theorem closers_agree : forall c1 c2 h ops, close c1 h ops = close c2 h ops.`

> **평서문**: `.` · `end` · `)` 중 **어느 것으로 닫아도 같은 나무**가 나온다.
> 셋 다 "열려 있는 가장 안쪽 form 을 닫는다" 를 한다.

> ★ **개행은 이제 닫개가 아니다**(2026-08-27, RFC-0103). 예전에는 네 번째 철자로 개행이 있었고, 그것도
> 같은 일을 한다는 것이 이 정리로 증명돼 있었다 — 증명은 옳았다. 없앤 이유는 다른 데 있다: 개행이 닫으면
> **줄바꿈이 의미가 되어** 긴 줄을 되감는 것만으로 프로그램이 바뀐다. *"같은 뜻이다" 가 증명됐다고 그 철자를
> 두어야 하는 것은 아니다.*

★ 왜 이것을 증명하나? 두 철자가 다른 나무를 만들면 그것이 곧 **"하나의 뜻에 두 표현"** 이고,
이 언어의 규약(SPEC §2.5 동의어 금지)을 어기는 것이다. 증명이 그 규약을 지키는 장치다.

### 정리 G3 — ~~쉼표는 형제이지 자식이 아니다~~ (없앴다)

> **없앤 정리**: `Theorem comma_does_not_close : forall h a b c, comma_form h [a;b;c] = Form h [a;b;c].`

> **평서문이었던 것**: `,` 는 form 을 **닫지 않는다.** 같은 form 안에서 **다음 인자**를
> 시작한다. `print a, b, c .` 는 form 하나이고 인자가 셋이다.

**2026-08-27(RFC-0103), `,` 를 어휘에서 없앴다.** 정리가 틀려서가 아니다 — Qed 였고 지금도
참이다. 없앤 이유는 **아무도 안 썼기 때문**이다: 저장소 전체에서 COMMA 토큰이 셋뿐이었고
셋 다 줄잇기(개행 닫힘과 함께 죽은 역할)였다. 인자 구분자로 쓴 자리는 한 곳도 없었고,
그 셋에서 `,` 를 지워도 **def 해시가 그대로**였다.

★ **파싱되는데 아무 효과가 없는 낱말은 조용한 함정이다.** 그래서 지금 `,` 는
`E-VOCAB-REMOVED` 로 말한다. (`;` 가 같은 이유로 먼저 죽었다.)

★★ 이 정리에 붙어 있던 **실패담**은 남길 값이 있다. 닫개와 쉼표를 섞었더니 `.` 이 뜻을
잃어 이런 모순이 생겼었다:

```lowent
if c . return 1 .              rem 파스 오류였다
guard c . else return 1 .      rem 그런데 이건 통과했다      ★ 같은 모양인데?
```

같은 구조인데 하나는 되고 하나는 안 됐다. 원인은 제어 머리 안에서 `.` 을 "건너뛰기" 로
특별 취급한 것이었다. **직교성이 깨지면 사용자가 예측할 수 없다.**

### 정리 G4·G5 — ~~줄잇기~~ · ~~괄호와 개행~~ (없앴다)

> **없앤 정리**: `three_reasons_one_rule` · `no_fourth_spelling_is_needed` · `paren_does_not_leak_inward` ·
> `paren_does_not_leak_outward` · `paren_continues_inside`

**2026-08-27(RFC-0103), 개행이 닫개에서 빠지면서 이 정리들이 다룰 규칙이 없어졌다.** 다섯 다 Qed 였고
지금도 참이다 — 그러나 개행이 공백이므로 *"개행이 닫느냐"* 를 물을 자리가 없고, *"줄을 어떻게 잇나"* 도
물을 자리가 없다. 여러 줄에 걸쳐 쓰는 데 아무 표시도 필요 없다: form 은 자기 닫개(`.`·`end`·`)`)에서 끝난다.

★ 참인 정리를 지우는 것은 아깝지만, 죽은 규칙을 모형화한 정리를 남겨 두면 **증명된 문서가 거짓말을 하는**
자리가 된다. 남길 값이 있는 교훈 하나: 전엔 괄호 **깊이**를 봤고 효과가 양쪽으로 샜다 — **깊이가 아니라
스택의 맨 위**를 보는 것이 답이었다. *중첩된 것을 다룰 때 깊이는 맨 위의 근사일 뿐이다.*

## ④ 증명의 전략

전부 **계산으로 끝난다**(`reflexivity`). 나무를 만드는 함수와 뜻함수를 정의해 두면, 등식이
양변을 계산해서 확인된다.

그래서 이 파일의 값은 증명의 어려움이 아니라 **명제를 골라 적었다**는 것에 있다:

```
"닫개들이 같은 일을 한다" 를 **적어 두면** 누가 하나를 특별 취급했을 때 증명이 깨진다.
```

문법은 조용히 표류하는 층이다("여기만 예외를 두면 편한데"). 정리가 그 표류를 잡는다.

## ⑤ 이것이 막는 버그

```lowent
rem ① 블록과 문장을 섞어 쓴다 — 둘이 같으므로 문제가 없다 (G1)
if c . set x 1 .
if c . do set x 1 . set y 2 . end     rem 같은 자리, 같은 규칙

rem ② 어느 닫개로 닫아도 같은 나무 (G2)
set x (add x 1) .                      rem `)` 가 안쪽 form 을, `.` 이 바깥 form 을 닫는다

rem ③ 인자를 여러 줄에 — 아무 표시가 필요 없다 (개행은 공백이다)
set total (add
             total
             x) .
```

막는 것은 **사용자의 버그가 아니라 컴파일러의 버그**다. 이 성질들이 깨지면 사용자는
"왜 여기서는 되고 저기서는 안 되나" 를 만난다 — 언어에서 가장 나쁜 경험이다.

## ⑥ 증명하지 않은 것

1. **실제 파서가 이 모델이라는 보장이 없다.** 모델은 나무를 만드는 작은 함수들이고,
   `low_cst.c` 는 그보다 훨씬 크다. 대응은 **골든 테스트**(1,328 검사)가 받친다.
2. **`denote` 는 평평한 나열이다.** 위치 정보·주석·오류 복구를 모델링하지 않았다.
   그러니 "같은 나무" 는 **구조가 같다**는 뜻이고 진단 품질까지 같다는 뜻이 아니다.
3. **연산자 우선순위가 없다**(이 언어에 우선순위가 없으므로 — 전위 표기다).
   그래서 이 장이 다룰 것이 적었다. 설계가 증명을 쉽게 만든 사례다.
4. **어휘(렉서) 층은 별도다.** 토큰이 이 모델의 닫개 셋으로 정확히 나뉘는지는 렉서 테스트의 몫이다.
