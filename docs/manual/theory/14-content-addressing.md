# 14. 내용 주소화 — 이름이 아니라 내용으로 부르기

> **근거**: RFC-0012(canonical IR · 내용 주소화, 구현: 부분) · SPEC §12.2/§12.3 · BLAKE3-256.
> 구현: `impl/src/low_ir.c` 의 `ir_iface_hash`·SCC Merkle def-hash · `impl/src/low_blake3.c`.
> 이 장의 해시 값은 **실제로 찍어서** 넣었다.

## ① 5분 요약

보통의 빌드 시스템은 **파일 이름과 시각**으로 캐시를 판단한다. 그래서 유명한 문제가 있다:

```
파일을 만졌지만 내용은 같다        → 쓸데없이 다시 빌드한다      (손해)
내용이 바뀌었지만 시각이 같다      → ★ 낡은 결과를 쓴다          (위험)
```

내용 주소화는 이름을 버리고 **내용의 해시**로 부른다.

```
$ lowentc --emit-db twice.low
fn twice/1 iface:501eba9b550c4bbb def:a7b798a14a05b8f1
```

두 개의 해시가 있는 것이 요점이다. **def**(정의 전체)와 **iface**(관찰 가능한 표면).

## ② 필요한 수학

### 해시 함수 — 지문

```
BLAKE3-256:  임의 길이 바이트 → 32바이트
```

성질 하나만 필요하다: **다른 입력이 같은 출력을 내는 짝을 찾을 수 없다**(충돌 저항).
그래서 "해시가 같다" 를 "내용이 같다" 로 **써도 된다.**

★ 이것은 **가정**이다. 수학적으로 증명된 것이 아니다(16장의 신뢰 기반 목록에 있다).
그러나 실용적으로는 다른 어떤 가정보다 튼튼하다.

### Merkle DAG — 해시가 해시를 담는다

```
hash(def) = BLAKE3-256( 정규 인코딩(def) )
그리고 그 인코딩은 **의존성을 그들의 해시로** 임베드한다.
```

그러면 좋은 성질이 자동으로 생긴다:

> **어떤 정의의 해시는 그것이 의존하는 모든 것의 내용을 반영한다.**

깊이 다섯 단계 아래의 함수 하나가 바뀌면 위쪽 해시가 전부 바뀐다. 별도의 "의존성 추적"
장치가 필요 없다 — **해시 자체가 추적이다.**

### 순환 의존 — 고정점이 또 필요하다

상호재귀 함수는 서로를 참조한다. `hash(A)` 가 `hash(B)` 를 담고 `hash(B)` 가 `hash(A)` 를 담으면
정의가 순환한다.

해법: 순환하는 것들을 **한 덩어리(SCC)** 로 묶는다.

```
① 이름 없는 예비 해시로 덩어리 안의 순서를 **정한다**(정규 순서).
② 덩어리 안의 호출은 이름/해시 대신 **그 순서의 번호**를 담는다.
③ 덩어리를 **한 번** 해싱한다.
④ 각 구성원의 해시 = (덩어리 해시, 자기 번호).
```

★ 순환을 없애는 표준 기술이다(강결합 요소로 축약하면 남는 것은 DAG 다).
2장의 고정점과 같은 발상이 또 나온 것이다.

## ③ 성질과 그 뜻

★★★ **이 장에도 정리가 생겼다**(2026-07-31, `LowentHash.v`) — 다만 **증명할 수 있는 것과
없는 것을 정확히 갈라서**다. 해시 함수(BLAKE3)의 충돌 저항성은 **암호 가정**이라 증명 대상이
아니다. 증명할 수 있는 것은 그 **앞**, 곧 **정규 인코딩이 무엇을 지우고 무엇을 남기나**이다:

> `H1_comments_are_irrelevant` · `H2_body_does_not_touch_iface` · `H3_effects_are_a_set`
> — 그리고 ★★ `encoding_is_injective`: **같은 인코딩이면 인터페이스의 모든 조각이 같다.**

마지막 줄이 값이다. *"해시는 같은데 인터페이스가 다르다"* 가 생긴다면 원인이 **하나로
좁혀진다** — 해시 함수의 충돌. 인코딩이 애매해서 생긴 것이 **아님**을 기계가 보증한다.

아래 해시는 실제 출력이고, 골든이 그것을 고정한다(정리는 모델 위의 것이고, 구현이 이
인코딩을 쓴다는 것은 여전히 골든이 받친다).

### 성질 H1 — 표면 무관: 주석은 아무것도 바꾸지 않는다

```lowent
export fn twice input a u64 . output u64 . do
  return add a a .
end
                              → iface:501eba9b550c4bbb  def:a7b798a14a05b8f1
```

```lowent
rem 주석을 넣어도 아무것도 안 바뀌어야 한다
export fn twice input a u64 . output u64 . do
  rem 여기도 주석
  return add a a .
end
                              → iface:501eba9b550c4bbb  def:a7b798a14a05b8f1   ★ 같다
```

**막는 버그**: 주석을 고쳤는데 프로젝트 전체가 다시 빌드되는 것. 그리고 그보다 중요한 것 —
**"같은 프로그램" 의 정의가 바이트가 아니라 의미**라는 것을 기계가 지킨다.

### 성질 H2 — 본문만 바뀌면 def 만 바뀐다

```lowent
  return mul a 2 .            rem add a a → mul a 2 (같은 값, 다른 코드)
                              → iface:501eba9b550c4bbb  def:d1c740232d879fc4
```

`iface` 는 **그대로**고 `def` 만 바뀌었다. 이것이 증분 빌드의 심장이다:

```
X 의 본문만 바뀜  →  X 의 iface 불변  →  X 를 쓰는 D 는 **재컴파일하되**
                                        D 의 iface 도 불변  →  D 의 의존자는 **캐시 적중**
```

전파가 **필요한 만큼만** 번진다. 시그니처가 바뀌면 사슬을 따라 확장되고, 본문만 바뀌면
한 단계에서 멈춘다.

### 성질 H3 — 효과는 **집합**이므로 정규화한다

```
effects io alloc   →   같은 해시
effects alloc io   →   같은 해시   (지금은)
```

★ 전에는 **달랐다.** 절의 **원문 텍스트**를 해싱했으므로 `io alloc` 과 `alloc io` 가 다른 해시를
냈다. 그러면 내용 주소화가 **의미가 아니라 철자**를 주소화한 것이다 — 그러면 캐시가 갈리고,
"같은 인터페이스" 라는 말이 아무것도 뜻하지 않는다.

⇒ 효과는 **정규화된 순서**(비트 오름차순)로 해싱한다. 문법이 그것을 **집합**이라고 말하기 때문이다.

## ④ 이 장을 쓰면서 찾은 구멍 — **계약도 인터페이스다**

이 장을 실측으로 쓰다가 다음을 발견했다(2026-07-30):

```lowent
export fn twice … . do return add a a . end
                              → iface:501eba9b550c4bbb

export fn twice … requires le a 100 . do return add a a . end
                              → iface:501eba9b550c4bbb      ★ **같다**

export fn twice … ensures ge ret a . do … end
                              → iface:501eba9b550c4bbb      ★ **같다**
```

**계약을 붙여도 iface 해시가 안 바뀌었다.** 그런데 RFC-0012 §477 의 정의는:

> `iface-hash = hash(시그니처 + 계약, 본문 제외)` = 정의의 *관찰 가능한 표면*

**구현이 시그니처만 해싱하고 있었다.**

### 왜 이것이 위험한가

RFC-0012 §484-492 의 증분 전파는 이 문장에 기댄다:

> *"의존자 D 가 callee X 를 타입검사·**계약검사**할 때 의존하는 것은 X 의 iface-hash 다."*

계약이 iface 에 없으면 **X 의 계약이 바뀌어도 D 가 캐시 적중**한다. D 는 **옛 계약을 믿은 채**
남는다. 그리고 05장을 떠올리면 그것이 왜 심각한지 보인다:

```
경계 검사를 지우는 **근거**가 계약이다.
그 계약이 바뀐 것을 의존자가 모른다.
⇒ **증명을 낡은 전제 위에 세운 것**이다.
```

증분 빌드의 캐시 적중이 곧 "증명을 재사용한다" 는 뜻이므로, 전제가 바뀌면 그 재사용은
**틀린 재사용**이다.

### 고친 뒤 (실측)

```
requires le a 100 을 붙임    → iface:7277a80a0342ee8d      ✔ 바뀐다
ensures ge ret a  을 붙임    → iface:882290e50e9bdcdc      ✔ 바뀐다
주석만 고침                   → iface:501eba9b550c4bbb      ✔ 안 바뀐다 (H1 유지)
본문만 고침                   → iface:501eba9b550c4bbb      ✔ 안 바뀐다 (H2 유지)
```

★ 그리고 **부정확의 방향**을 골랐다. 계약 절은 **소스 순서로** 해싱한다(효과처럼 정규화하지
않는다). 그러면 `requires A . requires B .` 와 `requires B . requires A .` 가 다른 해시를 낸다 —
같은 뜻인데 다른 해시다. 부정확하다. 그런데 **안전한 방향**이다:

```
같은 뜻 → 다른 해시    →  재빌드가 한 번 더 돈다        (손해)
다른 뜻 → 같은 해시    →  ★ 캐시가 거짓말을 한다        (위험)
```

04·06장에서 본 것과 **같은 비대칭**이다. 이 문서 전체를 관통하는 원칙이 여기서도 판단을 정했다:
**모르면 넓게 잡는다.**

## ⑤ 이것이 막는 버그

```
① 주석 고치고 전체 재빌드                → H1 이 막는다
② 본문 고쳤는데 의존자의 의존자까지 재빌드 → H2 가 막는다
③ effects 순서만 바꿨는데 캐시 미스        → H3 이 막는다
④ 계약을 고쳤는데 의존자가 캐시 적중       → ④의 수정이 막는다 (이 장에서 고쳤다)
⑤ 의존성이 조용히 바뀜                    → Merkle DAG 가 막는다 (해시가 내용을 담으므로)
⑥ 락파일의 의존성이 바뀜                  → `pkg.lock` 의 내용 해시가 거절한다
```

⑤·⑥이 **재현 가능한 빌드**의 근거다. "같은 소스가 같은 결과를 낸다" 를 **검사할 수 있는 형태**로
만든 것이 내용 주소화의 값이다 — 믿는 것이 아니라 **비교하는 것**이 된다.

## ⑥ 증명하지 않은 것

정직하게 — 이 장은 문서에서 **증명이 가장 얇은** 장 중 하나다(08장과 함께).

1. **Coq 정리가 없다.** H1·H2·H3 은 **골든 테스트가 고정하는 성질**이고 정리가 아니다.
   "모든 프로그램에 대해 주석이 해시를 바꾸지 않는다" 를 증명하지 않았다 — 몇 개의 예에서
   확인했다.
2. **정규화가 완전하지 않다.** 위 ④에서 적었듯 계약 절의 순서에 민감하다. 그리고 지역 변수
   이름·수 리터럴의 표기(`0x10` 대 `16`) 같은 것들이 어디까지 정규화되는지 전수 확인하지 않았다.
3. **해시 충돌 저항은 가정이다**(BLAKE3 를 믿는다). 16장의 신뢰 기반에 있다.
4. **SCC 그룹 해시가 최적인지 모른다.** 순환을 다루는 방법이 여럿 있고, 이것이 그중 하나다.
   같은 순환 구조에 대해 다른 도구가 같은 해시를 낼 것이라는 보장은 **없다** —
   즉 **다구현 호환**은 아직 명세 수준의 약속이다.
5. **`--emit-db` 는 사이드파일이다.** 해시가 빌드 결정에 **완전히** 쓰이고 있지는 않다
   (RFC-0012 의 상태가 "구현: 부분" 인 이유다). 증분 빌드는 방출된 C 의 내용 해시로 돈다.
