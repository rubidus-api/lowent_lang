1 Scope§

1.1 What this document specifies§

1 This document defines the Lowent programming language. It specifies the following four things.

2 a) The representation of programs written in Lowent — which characters, arranged how, form a program.

3 b) The syntax and constraints of Lowent programs — which arrangements are correct and which are not.

4 c) The semantic rules for interpreting Lowent programs — what a correct program does.

5 d) The conformance requirements that a processor which translates and executes Lowent programs shall meet.

In plain words

This document is the only document that answers “what is Lowent”. Someone learning the language and someone building a new Lowent processor both need to read only this one document. No place has been left where another document must be found and read.

1.2 What this document does not specify§

1 The following are outside the scope of this document. Outside the scope means “not specified here”, not “forbidden”.

2 a) How Lowent programs are made — how to use editors, build tools and package managers.

3 b) The internal structure of a particular processor — which intermediate representation it uses, how it optimises.

4 c) The complete list of the standard library — §9 specifies the rules a library shall follow, not the list of individual functions.

5 d) The behaviour of operating systems and hardware — this document states only what it requires of them (§5).

In plain words

“Not specified” and “forbidden” are easy to confuse. For example, this document does not specify an editor, but that does not mean you must not use one; it means it is not this document’s business.

1.3 The purpose of this language§

1 Lowent is a systems programming language designed to lower semantic entropy.

semantic entropy (의미 엔트로피)

The uncertainty that remains about a program’s actual behaviour after its whole source has been read. Put another way, the amount of information that must be brought in from outside the source to know what the code does.

2 Every rule of this language was chosen to reduce that uncertainty. Specifically, it removes the following four things.

3 a) Hidden behaviour — nothing happens that the source does not state. There is no invisible memory allocation, no invisible control flow and no invisible type conversion.

4 b) Hidden cost — how expensive a line is, is written on that line.

5 c) Hidden assumptions — what a function requires is written as a contract, and the processor checks it (§6.4).

6 d) Overlapping notation — the same meaning cannot be written in several ways. Different notation means different meaning.

7 Low semantic entropy does not mean that the source corresponds one-to-one to machine code. There are places where, for efficient implementation and optimisation, the processor must have a choice.

8 This language marks such places and isolates them from the rest. Every place where the processor chooses is marked (free choice, §4.3), and each place states the range it may choose from. The processor makes no choice at an unmarked place.

9 So the person writing a program can know what is fixed and what is open. At an open place they may choose for themselves whether to leave it to the processor or to rewrite it in a fixed form.

In plain words

Entropy is the amount of «what stays unknown». The mere existence of choices does not increase entropy — what increases it is not knowing where the choices are, and not knowing how far what can happen extends.

In plain words

A language close to the machine cannot tie the processor down so that it chooses nothing. Tied that way, it could not use a faster path even when it knew one. Conversely, if places of choice are scattered all over the language, every line read raises the question «does the processor choose something here too». That question is the entropy.

In plain words

So this language gathers the places of choice in one list (annex F), puts a mark at each such place in the text, and states the range of each. On a line without a mark the reader can trust that what is written happens as written; on a line with a mark they know exactly what is open. Even if some uncertainty remains, knowing its place and its size — that is what this language aims at.

Note (informative)

The name «Lowent» is short for low entropy. The name is the criterion — whether a feature goes in is decided by “does it increase semantic entropy”.

1.4 How to read this document§

1 This document distinguishes the normative from the informative.

normative (규범)

Text that defines the language. Processors and programs shall obey it. Unless marked otherwise, the whole body of this document is normative.

informative (참고)

Text that helps understanding. It does not define the language. Boxes marked «Note», «In plain words» and «Caution» are informative. Where the normative and the informative appear to disagree, the normative is right.

2 Clauses are numbered. A number is an address, and the meaning of a number once given does not change. When another document cites this one, it cites by number (for example §6.4.2).

2a A number is a sequence of integers joined by dots (annexes begin with a capital letter). No other form is used — in particular, numbers such as 3a are not made in order to insert something in between. If a clause must be inserted, the following numbers shall be shifted, and that can be done only before this document is widely cited.

Note (informative)

There really is “a last moment at which numbers can be shifted”. While this document is young, moving numbers is cheap, but once other documents and tools start pointing at these numbers it becomes expensive. That is why this rule is worth something only if it is kept now.

3 Paragraphs within each clause are numbered too (1, 2, 3 …). A precise citation gives the clause number and the paragraph number together (for example 6.4.2 paragraph 3).

4 A term is given with its English form in parentheses, and its meaning, where it first appears. The definitions of all terms are gathered in §3.

Caution — The meaning of the modal verbs used in this document

«shall» (Korean 「-하여야 한다」 · 「-이어야 한다」) is a requirement. Not meeting it means not conforming. «may» (「-할 수 있다」) is a permission. «should» (「-하는 것이 좋다」) is a recommendation; not following it still conforms. «shall not» (「-하지 아니한다」) is a prohibition.

1.5 Grammar notation and the frame of a clause§

1 This document writes its grammar as productions. There is one notation, the same throughout the document.

production (생성 규칙)

A statement of which sequence of units a unit of the grammar consists of. Its form is name ::= body.

Table 1 — Grammar notation

NotationMeaning
name ::= bodyname consists of body
A BA followed by B
A | BA or B
[ A ]A absent or once
{ A }A zero or more times
( A )grouping
"text"those characters, literally
"a" … "z"one of the characters from a to z

2 One or more is written A { A }. No other notation is used.

3 Production names are written in lowercase English letters and hyphens (if-statement). The same name refers to the same rule throughout the document.

3a The grammar has two layers. The lexical grammar specifies how a sequence of characters is divided into tokens (§6.1). The syntactic grammar specifies how a sequence of tokens is read as grammatical elements.

lexical grammar (어휘 문법)

The rules that divide a sequence of characters into a sequence of tokens. The terminal symbols of its productions are characters.

syntactic grammar (구문 문법)

The rules that read a sequence of tokens as grammatical elements. The terminal symbols of its productions are tokens.

3b "if" in the syntactic grammar means one token with that spelling. White space and comments between tokens are discarded at the lexical stage and do not appear in the syntactic grammar.

4 What a production specifies is form only — which sequence of words is read as that grammatical element. Which of the well-formed ones conform is not specified by productions but by constraints and static semantics.

5 A condition that cannot be written as a production is written as a numbered paragraph directly below that production.

6 A clause that specifies a construct of the language has the following sections in this order. A section with nothing to say is omitted.

Table 2 — The frame of a clause

SectionWhat it states

ConstraintsConditions a well-formed program shall meet to conform. A program that violates one does not conform

7 A constraint states only the requirement. The diagnostic identifier for violating it is given in the diagnostics section — the diagnostic identifier does not define the requirement.

8 Paragraph numbers do not restart in each section; they continue through the clause.

9 Some clauses have not yet been moved into this frame. Such clauses keep their earlier wording, and their normative force is the same.

Note (informative)

A «grammar shape» box is a form to see at a glance. The definition of the grammar is the productions in the syntax section; where the two appear to disagree, the production is right.

In plain words

The sections are separated because whom they speak to differs. Syntax speaks to the one who reads text as a tree (the parser), constraints and static semantics to the one who checks whether that tree is correct (the checker), and dynamic semantics to the one who runs the program. If the three are mixed in one paragraph, the reader has to separate them, and every reader separates them differently.

3 Terms and definitions§

1 In this document the following terms are used only in the meanings given here. They may differ from their everyday meanings or from their meanings in other languages; whenever a meaning is in doubt, this clause is the reference.

In plain words

A first-time reader need not read this clause from start to end. When an unknown word turns up in the text, come back here. Each term carries the number of the clause that actually uses it.

3.1 The parts of a program§

program (프로그램)

The set of Lowent source files that are translated together and form one unit of execution. The exact composition is specified by §5.1.

module (모듈)

One named source file. A module writes its own name on its first line and marks what it exports to other modules. A module name need not be the same as the file name.

op (op)

A unit of execution with a name and a contract. It corresponds to a «function» in other languages, but in Lowent its kind depends on whether it has side effects (§6.4.1): one that produces no effect at all is fn, one that produces effects is proc.

declaration (선언)

A construct that gives a name a meaning. It says what exists.

definition (정의)

A declaration that also supplies the entity itself. The definition of an op includes its body.

3.2 Values and types§

value (값)

What a computation produces. Every value has exactly one type.

type (타입)

A set of values together with the operations allowed on them. Every Lowent type has a fixed size and representation — there is no place the processor decides at will (§6.2).

width (폭)

The number of bits an integer type occupies. The width of u8 is 8. The width of a type with a number in its name is the same on every processor. Only usize · idiff are exceptions; their width is chosen by the implementation — at least 16 bits, usually the address width of the target machine (§6.2.2).

slice (슬라이스)

A reference to a range of values of the same type laid out contiguously. It carries a start position and a length together. Carrying the length is what makes it differ from a pointer, and is why its bounds can be checked (§6.2.6).

character literal (문자 리터럴)

One character in single quotes ('a'). Its value is that character’s code, an integer. What does not fit in one slot is not a character literal (§6.1.4).

string literal (문자열 리터럴)

A row of bytes in double quotes ("abc"). len gives the number of elements — the prefix decides what an element is.

escape (이스케이프)

A notation inside a character or string, starting with a backslash, that stands for one character (\n). There are only fourteen (§6.1.4).

prefix (접두사)

A word placed before a literal that decides what its elements mean. There are only two: u (UTF-16 code unit) · U (code point). Without a prefix the elements are bytes.

text literal (텍스트 리터럴)

A string that holds several lines as they are. A tag is written after text, and the literal ends at a line on which the same tag stands alone from the very first column. Escapes in the body are not processed. It corresponds to what other languages call a heredoc, nowdoc or delimited string.

floating-point literal (부동소수점 리터럴)

A number with a decimal point or an exponent written directly in the source (1.5 · 1e3 · 0x1p3). There shall be digits on both sides of the point — .5 and 1. are not floating-point literals (§6.1.4).

literal (리터럴)

A value written directly in the source. 42, true, "text" and the like.

enum (열거)

A value that is exactly one of a set of named variants. Each variant may carry a value. Since the variant name says what the value is, some bit patterns remain unused — so an enum has «trap representations».

trap representation (덫 표현)

A bit pattern that is not a value of its type. Reading such a bit pattern as a value of that type has no meaning, and this language does not allow such a read (§8.7.1). A scalar type with no trap representation at all is called plain.

brand (상표)

A name that separates storage. So that values with the same representation but from different storage do not mix, a type made with newtype is used as the name of that storage. One brand designates one storage (§6.2.9).

3.3 Contracts and verification§

contract (계약)

The promise an op writes for itself about its input and output. It consists of six clauses — requires (what shall be true on entry) · ensures (what is true on exit) · errors (when it fails) · effects (what effects it produces) · access (what it touches, and how) · tests (examples). The full definition is in §6.4.3.

precondition (사전 조건)

What the requires clause of a contract says. A condition that shall be true at the moment of entering the op.

postcondition (사후 조건)

What the ensures clause of a contract says. A condition that is true when the op ends normally.

check (검사)

Confirming during execution that a condition is true. If the processor proves that the condition is always true, it removes the check. If it cannot remove it, the check remains (§6.4.6).

trap (트랩)

Stopping the program at once when a condition is broken. Lowent does not continue computing in a wrong state — it stops rather than return a wrong answer.

undefined behaviour (미정의 동작)

Behaviour the source does not determine. There is none in the safe subset (§4.4) — within it, every situation this document does not define ends in a diagnostic (§5.4) or a trap. This is where it differs most from C.

safe subset (안전한 부분집합)

The set of programs that do not use unsafe and extern. Within this set there is no undefined behaviour.

build mode (빌드 모드)

The setting that decides whether contract checks that could not be proved stay during execution or are removed. It is written in the source as build <mode> . (§6.4.7).

trust boundary (신뢰 경계)

The place where the language’s guarantee ends and a person’s promise begins. unsafe and extern mark that place in the source (§6.9).

3.4 Effects and capabilities§

effect (효과)

An influence an op has on the outside world. Reading a file, looking at a clock, allocating memory, creating another flow of execution and the like are each an effect. An op shall write the effects it produces in its contract, and if it produces more effects than written, translation is refused (§7.1).

pure (순수)

Producing no effect at all. A pure op always gives the same result for the same input.

capability (권한)

A value that stands for the right to produce an effect. Lowent has no global capability anyone may use — to read a file, a file capability shall be handed over as an argument (§7.2).

3.5 Memory and ownership§

region (영역)

A section of memory where values live. For each value, the region it lives in is fixed together with its type (§8.1).

reference (참조)

Something that points at a value elsewhere. Read-only references and write references are distinguished, and for one value there can be only one write reference at a time (§8.4).

ownership (소유)

Who is responsible for destroying a value. Lowent tracks owners statically, so destroying twice or forgetting to destroy is refused at translation (§8.5).

escape (탈출)

A reference to a local value outliving that value. Lowent refuses this at translation (§8.4.1).

3.6 Processors and conformance§

processor (처리기)

The general name for whatever translates or executes Lowent programs. A compiler, an interpreter, and something that does both are all processors. This document does not specify their internals; it specifies only observable behaviour.

translation (번역)

Turning a source into a form that can be executed. Errors found during translation are reported as diagnostics.

diagnostic (진단)

A message by which a processor reports an error. It has a stable identifier (for example E-TYPE-INSTANCE), and the meaning of that identifier does not change across editions (§5.4).

conforming program (적합한 프로그램)

A program that keeps all the syntax and constraints of this document (§4.1).

conforming processor (적합한 처리기)

A processor that translates and executes conforming programs as this document specifies, and issues diagnostics for programs that do not conform (§4.2).

3.7 Source and notation§

Lowent (로우엔트)

The programming language this document defines. The name is short for low entropy.

token (토큰)

The smallest piece a source is divided into. Keywords, identifiers, literals and punctuation are tokens.

keyword (낱말)

A name whose meaning the language has fixed. It cannot be used with another meaning. The list is in annex A.

identifier (이름)

A name the author makes. It consists of ASCII letters, digits and underscores — it contains no dot. A dot is the mark that joins two names when choosing a field of a value or naming a module (§6.1.3).

comment (주석)

From rem to the end of the line. The processor treats it as absent.

form (폼)

One unit of prefix notation. A closer marks its end.

closer (닫개)

The mark that says a form has ended. It is one full stop .. A parenthesis ) also closes the forms opened inside it, and end closes only its own do (§6.1.6).

newline (개행)

The place where a line changes. It is treated exactly like a space and does not close a form (§6.1.6).

prefix notation (전위 표기)

A notation in which the name of an operation comes first and its arguments follow. There are no precedence rules.

infix notation (중위 표기)

A notation in which the operator symbol comes between its arguments. It can be used only inside an expr island.

island (섬)

The place where infix notation is switched on. It begins with expr.

byte order mark (BOM)

A mark some editors put at the start of a file (U+FEFF). It cannot appear in a Lowent source.

3.8 Computation and statements§

expression (식)

Something that produces a value.

statement (문장)

Something that is executed. An expression makes a value; a statement does work.

core op (기본 연산)

An operation whose meaning the language fixes and which is called anywhere by its name alone. It shares one namespace with the author’s names, so it cannot be hidden by them.

builtin op (빌트인 연산)

An operation whose meaning the language fixes and which is called only after call_builtin. It has its own namespace, so it does not collide with the author’s names. It is for building system libraries and processors; ordinary programs use the libraries that wrap it.

short-circuit (단락 평가)

Not computing the second part when the first part alone decides the result. and and or do this.

widening (넓히기)

A type conversion that loses no value. It may happen automatically.

narrowing (좁히기)

A type conversion that may lose a value. It shall be written in the source, and traps if the value does not fit.

trait (트레이트)

A list of ops a type shall provide. If a type is written as providing it, the processor checks. It makes no hierarchy among types — this language has no inheritance.

actor (액터)

A unit of execution with its own state. The state exists only inside the actor.

3.9 Environments and conformance§

translation environment (번역 환경)

The place where a source is turned into a form that can be executed.

execution environment (실행 환경)

The place where the result actually runs.

entry point (시작점)

The op at which an executed program starts. Its name is main.

exit status (종료 상태)

The value the entry point returns. 0 means success.

library module (라이브러리 모듈)

A translation unit without an entry point. Other programs take it and use it.

conformance (적합성)

Whether what this document specifies has been kept. Used of programs and of processors.

syntax (구문)

The rules about which arrangements of characters are programs.

constraints (제약)

Rules that shall be kept even when the syntax is right. Violating one produces a diagnostic.

semantic rules (의미 규칙)

The rules about what a correct program does.

representation (표현)

Which bits a value is laid out as inside the machine.

octet (옥텟)

8 bits. In this language a byte is always an octet.

two's complement (투스 컴플리먼트)

A way of representing signed integers. It is the only way this language requires.

place (자리)

Somewhere a value can be written. A local variable, a field of a struct, one slot of a row are places. What can stand on the left of set is exactly a place — something that can only be read is not a place.

qualification (한정)

Fixing which name is meant by putting in front of a name the place where it lives. In this language qualification is written with a dot attached to the name, and it has only three meanings: a module, a variant, and a declaration belonging to a type. Reading the inside of a value is not qualification.

destination (목적지)

The place where a value is made and put. If the three conditions of §8.3.1 hold, the value is made here directly, without an intermediate temporary.

temporary (임시값)

A value in a nameless place, made when there is no destination or the conditions do not hold. It lives in the smallest enclosing scope, and when the scope ends the temporaries are destroyed in the reverse order of their making.

garbage collector (가비지 컬렉터)

A mechanism that finds unused memory during execution and gives it back. This language has none.

stage (스테이지)

A place inside a pipe of §6.12 that takes one element and passes it on. The vocabulary is closed (seven), so no other operation can be a stage.

terminal (종결자)

The place that ends a pipe and gives its result. A pipe has exactly one terminal.

context (문맥)

A value attached with with to a stage or terminal of a pipe, computed once before the traversal and handed to the op as its last argument (§6.12 (7)). Only a value without references can be a context.

local op (로컬 op)

An op declared directly below an op body and visible only inside that op (§6.10.5). It does not see outer names, so it is not a closure.

optimisation (최적화)

The processor’s discretion to make a program faster or smaller without changing its meaning. Being discretion, a program shall not rely on it — a property that must be relied on is written as meaning, not as optimisation (the fusion of §6.12 is an example).

4 Conformance§

4.1 Conforming programs§

1 A conforming program is a program that keeps all the syntax (§6) and constraints (§6) of this document.

2 A conforming program does not rely on behaviour this document does not specify.

2a Diagnostics come in two kinds: those that stop translation (their names begin with E-) and those that do not (W- · NOTE-). Only the former decide conformance; a program can conform even if the latter are present.

2b That is, a conforming program is a program with no diagnostic that stops translation.

Example — a conforming program

Source

module ex_conform .

rem This program keeps everything this document specifies.
export fn clamp input n u32 . output u8 .
  requires le n. 255 . .
  ensures le ret. 255 . .
do
  return narrow u8 n. . .
end .

proc main output u8 . effects none .
do
  return 0 .
end .

In plain words

Called as clamp 200, the program above gives 200. Called as clamp 300 — since the contract said “at most 255” — it stops right there (E-VM-CONTRACT). Not returning a wrong answer is this language’s promise, and that promise is kept at execution.

Caution — Conforming and correct are different things

A conforming program can still give a wrong answer. Conformance is whether the rules of the language were kept, not whether it does what was intended. The latter is handled by contracts (§6.4.3) and tests.

4.2 Conforming processors§

1 A conforming processor shall satisfy all of the following.

2 a) It shall translate and execute conforming programs with the meaning this document specifies.

3 b) It shall issue at least one diagnostic for a program that does not conform. Whether translation continues after a diagnostic is decided by the processor.

4 c) Where it uses a diagnostic identifier this document specifies, it does not use it with a changed meaning.

5 d) Where it provides extensions this document does not specify, they do not change the meaning of a conforming program that does not use them.

Note (informative)

b) does not mean “it shall find every error”. For one non-conforming program, it is enough that at least one diagnostic is issued. Since Lowent’s principle is not to postpone checks, however, real processors usually collect and report all errors.

4.3 Implementation-defined behaviour and free choice§

1 The places where this document leaves discretion to the processor are of two kinds, and those places are explicitly marked.

implementation-defined (구현 정의)

Something the processor decides but shall document. Example: the maximum recursion depth. A program can ask for the value, and it may differ between processors.

free choice (자유 선택)

A place where the choice must be left free for the sake of optimisation or of the processor’s circumstances. The processor chooses one of two or more behaviours or results this document allows at that place. The processor need not document which it chose.

1a For each place of free choice this document states the range that may be chosen from. The processor chooses only within that range.

1b The processor may choose differently at the same place of the same program at each translation and each execution.

1c free choice is not something left unspecified. Whichever member of the range is chosen, it is behaviour this document specifies.

1d A place of free choice is marked in the text with a «free choice» box. Annex F gathers all of them, and a place not in annex F is not free choice. Adding a place or widening a range is a revision of this document.

1e A conforming program does not rely on which one the processor chooses at a free choice (§4.1 (2)).

1f There are places this document has not yet decided. Such places are not discretion — they are not a choice given to the processor but something this document must decide later. They are marked in the text with an «open issue» box and gathered in annex E.

open issue (모호)

A place this document has not yet decided and must decide later. The possible readings are written side by side. Once decided, it becomes a normative paragraph, or, if it is decided to leave it open, a free choice.

1g An open issue and a free choice are different. An open issue is undecided; a free choice is a decision — a decision to leave it open. A conforming program does not rely on the place of an open issue either (§4.1 (2)).

2 There is no discretion outside these two kinds. In the safe subset (§4.4) undefined behaviour does not exist — no program in it is executed in a state of «nobody knows what will happen».

In plain words

In plain words the two kinds are these. Implementation-defined is «it may differ between processors, but the processor writes down what it chose». Free choice is «any of these may be chosen, and the choice need not be written down».

In plain words

Free choice exists so that the processor can take a faster path. For example in add f x. . g y. . . the answer is the same whichever of f and g is computed first. If the order were nailed down, the processor could not use a faster order even when it knew one. So that order is left open.

In plain words

Leaving something open does not mean anything at all may happen. Each place states the range that may be chosen from, and nothing outside it happens. And such places are exactly the list in annex F — at a place not on the list the processor chooses nothing at will. Ranges are fixed narrowly, place by place.

In plain words

The one thing a person writing a program needs to remember: do not rely on which one is chosen. If the order matters, write it in a form whose order is fixed (the box in §6.3.1 says how).

4.4 The safe subset and trust boundaries§

1 The safe subset is the set of programs that do not use unsafe and extern. The guarantees of the previous clause are about this set.

2 unsafe and extern mark a trust boundary (§6.9). At that place the language’s guarantee ends and a promise written by a person begins.

3 If the promises beyond the boundary are true, the behaviour of the whole program is as this document specifies. If a promise is false, this document guarantees nothing — what happens then is not determined.

4 So boundaries shall be narrow. The wider they are, the larger the area this document’s guarantees do not reach.

In plain words

This clause exists for the sake of honesty. One cannot call a function written in another language and say “our language has no undefined behaviour” — this document does not know what that function will do. What can be said is where the language’s guarantee stops and where a person’s promise begins, and unsafe and extern leave that place in the source. Being able to find it later is as important as the guarantee.

4.5 Environmental limits§

1 A processor may have resource limits. But when it hits a limit it shall not silently truncate — it shall issue a diagnostic or trap.

2 A processor shall document the limits it supports (implementation-defined).

3 The diagnostics issued when a limit is hit are grouped into families — when a table inside the processor overflows, E-IR-… · E-TYPE-LIMIT · E-PARSE-LIMIT are issued; when a resource runs out during execution, E-VM-…. This document does not list them one by one; what is required is (1) and (2) — not truncating silently, and documenting the limits.

In plain words

The names of the diagnostics are not nailed into the norm one by one because they are the processor’s internal affairs. Splitting one table into two changes the names too, and if the norm had to be revised each time, that norm would be no more than a shadow following the processor. What the norm shall fix is what is promised, and the promise is two things: «say so when it overflows» and «write down how far it goes».

Caution —

Writing down a limit and keeping a limit are different. Writing it down but truncating silently on overflow violates (1); keeping it but not writing it down means the user learns it existed only after hitting it. Both are needed.

Note (informative)

“Not truncating silently” is the point of this clause. Every processor has limits. The problem is going past a limit and carrying on without a word; the program’s result then differs from what the source said — and that is semantic entropy (§1.3).

4.6 The edition of this document and the edition of the language§

1 This document has an edition number separate from the language. The «document edition» on the cover is this document’s edition, and the «language edition» is the edition of the language this document describes.

2 A rise in the last digit of the document edition means the text grew or was corrected, not that the language changed. When the language changes, the language edition rises, and the middle digit or higher of this document rises with it.

4.7 What is in this document but a processor cannot yet do§

1 There may be things this document specifies that a processor cannot do yet. Then the processor does not treat them as if they did not exist.

2 At such a place the processor shall say “this word is in the specification, and what cannot do it is the processor”. That is, it is not an error of the program.

3 This distinction is normative because what a person does next differs. Told “unknown name”, a person goes looking for a typo that is not there; told “not yet”, they look for another way or wait. One diagnostic decides half a person’s day.

4 A processor shall make such places countable — asked which ops passed every static check but cannot be lowered to execution, it shall answer.

In plain words

This is not a clause that «excuses incompleteness». It is the opposite — a clause that says show the incompleteness. Between a processor that silently cannot do something and one that says it cannot, there is a difference in trust.

5 Environment§

1 This clause specifies the place where Lowent programs are translated and executed. The grammar of the language is specified by §6 here the ground on which that grammar stands is specified.

5.1 The translation environment and the execution environment§

1 The translation environment is the place where a Lowent source is turned into a form that can be executed. The execution environment is the place where the result actually runs. The two may be the same machine or different machines.

translation unit (번역 단위)

One source file translated together. In Lowent a translation unit is exactly one module, and a module writes its own name on its first line.

program (프로그램)

The set of translation units bound together into one unit of execution. A program shall have exactly one entry point.

2 Execution environments are of two kinds.

hosted (호스티드)

An environment with an operating system. Files, clocks, standard input and output and the like can be received and used as capabilities.

freestanding (프리스탠딩)

An environment without an operating system. The language itself holds unchanged; only the capabilities the host gives (§7.2) cannot be received.

3 §6 to §8 of this document hold in both environments. What differs between environments is only which capabilities can be received.

In plain words

Put simply — a computation written in Lowent has the same grammar and meaning even on a small device without an operating system. What differs is only the part that touches the outside world, such as «can it read a file».

5.2 Representation of source files§

1 A Lowent source file shall be a Unicode string encoded in UTF-8. Other encodings do not conform, and the processor shall issue a diagnostic.

2 The end of a line is represented by the line feed character (U+000A). The processor may accept a carriage return (U+000D) in front of it, and then treats the two characters as one line end.

3 A byte order mark (byte order mark, U+FEFF) cannot appear anywhere in a source file. Even at the very start it is a lexical error, and the processor shall issue a diagnostic.

4 Only ASCII characters can be used in an identifier (§6.1.3). Unicode characters can be used freely in the contents of comments, strings and text literals.

5 The encoding in which the source is read (the bytes the processor reads) and the encoding of the values literals have (the bytes the program handles) are separate. The source is always UTF-8, and a literal may have as its value bytes that are not UTF-8.

Caution — Identifiers being ASCII is a decision, not a restriction

Allowing Unicode identifiers creates names that look the same but are different (the Greek letter Α and the Latin A, two Hangul spellings in different normal forms, and so on). A person reading the source then reaches a wrong conclusion, and that is the uncertainty this language sets out to remove (§1.3). So identifiers are fixed to ASCII, and text meant for people is written in Unicode in comments and strings.

In plain words

A function cannot be named in Hangul, but comments and strings can be written in Hangul as much as you like. The examples in this repository are in fact written that way.

5.3 Minimum requirements of the execution environment§

1 A conforming execution environment shall satisfy the following.

2 a) A byte (octet) shall be exactly 8 bits.

3 b) Integers shall be represented in two’s complement (two's complement).

4 c) The address width shall be 16 bits or more.

4a A pointer is not the same thing as an address. A pointer value may carry bounds or permissions in addition to an address, so its size may be larger than the address width. The size and alignment of a pointer value, and whether it is a capability (a value that cannot be made from an integer and is derived only from another valid pointer), are determined by the execution environment (implementation-defined). A program asks for these values at translation time with machine.addr_bits · machine.ptr_bytes · machine.ptr_align · machine.ptr_caps (machine.ptr_width is the same as machine.addr_bits).

capability (능력)

A pointer value that carries, together with an address, the range it may reach and what it may do (read · write · execute). The hardware separately remembers whether the value is valid, so it cannot be made or rewritten from an integer and is obtained only by narrowing another valid capability. Reaching outside the range stops execution.

4b Values of this language do not expose pointers as integers. What points is a slice · a reference · a capability, and no integer type can hold a pointer and bring it back to life. So even on a machine whose pointers are capabilities the meaning of a program does not change.

Note (informative)

Machines whose pointers are larger than their addresses really exist — capability-pointer machines (64-bit addresses · 128-bit pointers, or 32-bit addresses · 64-bit pointers) carry bounds and permissions in the pointer and make pointers that went through an integer unusable. There are also machines whose pointer size differs per address space (microcontrollers with separate program and data memory, the spaces of accelerators). (4a) · (4b) are written so that, on the day such a machine is met, the language’s promises do not break first.

4c The multiplier width is the widest width (8 · 16 · 32 · 64 bits) at which the product of two integers, up to its upper half, is produced by one instruction. It is determined by the execution environment (implementation-defined), and a program asks for it at translation time with machine.mul_bits. A translator may provide a means of changing that value for one translation. It may differ from the address width. The processor also fixes the limb width used for big-number arithmetic and answers it with machine.limb_bits (16 · 32 · 64 bits, implementation-defined) — the value measured and fixed on the machine if there is one, otherwise the multiplier width (16 bits if the multiplier width is narrower than 16 bits). A translator may provide a means of changing the limb width for one translation. The multiplier width is a fact of the machine and does not change.

Note (informative)

Big-number arithmetic splits numbers into limbs and multiplies limb by limb. Which limb width is fast is decided not by the address width but by the multiplier — some machines with 32-bit addresses cannot produce the upper half of a 32×32-bit product (Cortex-M0). But the measured result can differ from the multiplier width (on a 32-bit x86 build, 64-bit limbs were faster), so the chosen width is kept separately. The standard library’s big-number module bigint chooses its limb width with machine.limb_bits and gives the same answer at every width (RFC-0152).

5 d) For a program that uses floating-point numbers, the execution environment shall provide the IEEE 754 binary 32-bit or 64-bit format. A program that does not use floating-point numbers is unaffected by this requirement.

Note (informative)

Almost every machine in use today already satisfies a)–c). This document writes them down because otherwise «where does this language run» would become knowledge outside the source. Some signal-processing devices whose byte is not 8 bits are not targets of this language.

1 The processor shall issue a diagnostic for a program that does not conform.

2 A diagnostic shall have a stable identifier. Identifiers consist of capital letters and hyphens (for example E-TYPE-INSTANCE), and the meaning of an identifier, once fixed, does not change.

3 A diagnostic shall give the place (file · line) where the error occurred.

4 Diagnostic identifiers fall into the following kinds.

5.5 Program start and end§

1 A program that is executed shall have exactly one entry point. The entry point is the op named main.

1a A translation unit without an entry point also conforms — it is a library module other programs take and use. An entry point is needed when an executable result is made.

2 The value the entry point returns is the program’s exit status. 0 means success, and the meaning of other values is determined by the execution environment (implementation-defined).

2a What can be used as the output of the entry point: a small unsigned integer (u8 · u32 and the like) · void (success when it ends) · result (0 on success; on error, the status that error determines).

2b If the value is wider than the execution environment’s exit status, how it is narrowed is implementation-defined.

3 In a hosted environment the entry point may receive as arguments the capabilities the execution environment gives. Which capabilities it receives is written by the entry point in its own contract, and the execution environment hands over only what is written (§7.2).

4 When the entry point returns, the program ends. Resources open before the end shall already have been closed according to the ownership rules (§8.5); if a resource is left unclosed, the program is refused at translation.

Example — the entry point receives capabilities

Source

module ex_env .

use stdio .

rem A capability not received exists nowhere in this program.
proc main input out cap io . output u8 . effects io .
do
  let n usize stdio.write out. 1 "hello\n" . .
  return cast u8 n. . .
end .

Source

  return 0 .

In plain words

The last paragraph is where this language differs most from others. It is often said that «when a program ends, the operating system cleans up», but Lowent refuses at translation the very fact of having forgotten to clean up. So the same code holds even in an environment without an operating system.

3 A name not in this list matches no build and so is refused. If a name that does not match were accepted, the op would silently drop out or be silently built wrong — both are what this document sets out to prevent.

4 What a machine does not have cannot be used. The processor refuses it at translation.

In plain words

4a That is, «code that runs on embedded systems too» is something measured, not something hoped for — a program that uses a growing root or floating-point numbers stops translating the moment that machine is chosen.

In plain words

8 atmega328p and atmega2560 have meaning as far as emitting C source and running it. C int is 16 bits, so the processor emits 32-bit words as fixed-width C types. Atomic operations are emitted as read-and-write while interrupts are blocked — these chips have one core. 5.8 Building differently per build — build option and config§

1 A program may declare knobs. build option <name> <kind> … makes a knob, and its value is fixed where the program is built.

2 There are three kinds; anything else is refused (E-OPT-TYPE).

3 A knob may depend on another knob (depends). If the depending knob is a bool and is on while the knob it depends on is off, the build is refused (E-CONFIG-DEPENDS) — because such a build does not exist; without this check depends would be decoration.

6 Once the values are fixed, switched-off branches do not remain in the output. The cost is 0.

1 This clause specifies the grammar and meaning of Lowent. It first specifies which pieces a source is divided into (§6.1), and then, in turn, what those pieces mean.

2a Of the punctuation, a detached dot . closes a form and ( ) group a form (§6.1.5 · §6.1.6). An operator is an operator only inside an expr island (§6.3.2).

3 A run of letters, digits and underscores is read as one piece, without breaking it, and then its kind is decided. iffy is not something beginning with the keyword if but one name, and remark is a name, not a comment.

6.1.5 Dots and forms§

1 In the grammar of Lowent the full stop . is a closing mark. One dot closes the innermost open form.

2 A form is prefix notation — the name comes first and the arguments follow. A name in a use position opens a form, and a dot closes it. add a. b. . adds a and b: a. and b. are forms closed at once without arguments, that is, the values of those names, and the last dot closes add.

2a What is known to be a value from its characters alone — number · character · string literals and true · false · none — does not open a form and takes no dot.

2b A name in the following positions does not open a form and takes no dot: positions that make a name (the name of a declaration · the name of let · var · the name of an input · a loop variable · the name of a field), the position of a type, and the word positions fixed by core ops and statements (cast <type> … · field … <member> · send … <handler> · the words of pipe stages and the like). These positions are specified by the grammar of annex A.10 and the tables of annex D. The arguments of an op the user declares are all forms — even when a type is passed (max_of u64. a. b. .).

3 When a form comes inside a form, the inner form first closes with its own dot. add a. mul b. c. . . multiplies b and c and then adds a. So the start and end of a form are determined by the characters alone — the tree stands without knowing how many arguments an op takes. The number of arguments is compared with the declaration after the tree stands (E-IR-ARITY).

3a Parentheses ( … ) enclose one form. They do not change the meaning — they are written to group for readability or to make something stand out. A form inside parentheses closes with its own dot (add a. (mul b. c. .) .). Parentheses are not closers.

4 The number of dots is a checksum — if the number of open forms and the number of dots do not match, the processor issues a diagnostic. So a program with a missing dot is never silently read with a different meaning.

5 A dot attached after a name (a.) is a closing dot — the same text as one separated by a space (a .). A dot attached between names does not close but means qualification — and qualification has only three meanings: the name of a module (allocs.byte_allocator), the name of a variant (err.too_short), and the name of a declaration belonging to a type (fn pt.twice). All three are routes that point at a declared name, not operations on values. A dot attached before a name (.name) is text that does not exist (E-VOCAB-REMOVED).

6 Looking inside a value — field access and method calls — cannot be written with an attached dot. That is a form, and like every other form the name comes first: field and method (§6.2.10 and §6.11.3). In plain words

6.1.6 Newline is not a closer§

1 A newline does not close a form. It is treated exactly like a space.

2 A form ends at its own closer. The closer is one dot .. Parentheses are not closers (§6.1.5 (3a)).

2a do … end are brackets that pair with each other. end closes only its own do and does not close forms outside the block. So each statement inside a block shall be closed by its own dot, and if end is met while one is still unclosed, translation is refused (E-DOT-MISSING).

2b What has a block is closed by its own dot too. Statements whose body is a block (if · while · the four loops · match · case · region · borrow · task_group · pipe) and declarations (fn · proc · struct · enum · trait · actor · state · contract · test) end at the dot after end — if c. do … end . · fn f … do … end .. A chain continued with else is one statement, and there is one dot at the very end of the chain (if a. do … end else do … end .). If that dot is missing, translation is refused (E-DOT-MISSING).

2c A value that holds a block — lit t do … end . · pipe xs. do … end . — is closed by its own dot too, and the statement that uses that value is again closed by its own dot (let x lit t do … end . .).

2d A block cannot stand alone without the head that opens it (E-BLOCK-NOHEAD).

2e There is no dot that closes nothing. A doubled dot after a form already closed (if c. . do), a dot directly after the name in an op head (fn f . input …), and a dot in the middle of a head clause (input a . u64 .) do not conform (E-CLOSER-EXTRA). A type ends by its own grammar and so takes no dot (the dot in input b slice u8 . closes the clause). A head clause is closed by one dot, and the word after the dot is the word of the next clause or do. An asm clause separates its items (reg a .) with dots. Clause words (vector · output · effects …) cannot be the names of inputs (E-NAME-CLAUSE).

6.2 Types§

1 Every value has exactly one type. A type fixes both what the value can be and what can be done with it.

2 Every type in Lowent has a fixed size and representation. There is no place where the processor decides at will according to the machine.

2a The processor decides the type of the value of every expression. If a value whose type the processor cannot decide is put in a place where a type is written — a bound name · an assignment · an op’s arguments and return · the elements of a row · the fields of an aggregate — translation is refused (E-TYPE-UNKNOWN). A value whose type is not decided cannot be checked, so such a place is not let through as «correct».

6.2.2 Integer types§

1 The name of an integer type is made of a sign and a width. u means unsigned, i signed, and the number after it is the width in bits.

2 Integers are represented in two’s complement (§5.3).

3 usize and idiff are integers wide enough to count the sizes and indices of the address space. Even if they have the same width as u64 · i64, they are different types, and they do not convert into each other automatically. usize is the type for lengths and indices, idiff the type for the difference between two positions.

3-1 usize and idiff have the same width, and it is chosen by the implementation (implementation-defined). That width is 16 bits or more and does not exceed the width of the widest integer type the implementation has. The implementation documents the width. usize is unsigned and idiff a two’s-complement signed integer, so the positive numbers idiff holds are half the range usize holds.

3-2 usize · idiff do not mix with any other integer type. The widening table (§6.2.5 (4)) does not include them — there is no automatic conversion from u8 to usize, nor from usize to u64. If only one of the two operands of an arithmetic operation or comparison is usize (or idiff), translation is refused (E-TYPE-NOMINAL). The same holds between usize and idiff. Number literals follow the type of their place and so are not caught by this rule.

3-3 A conversion between usize · idiff and other integer types is written with cast (§6.2.16 (2)). cast gives the value if it fits the target type and traps if it does not. widen and narrow are refused at translation when the source or the target is usize · idiff (E-TYPE-NOMINAL) — whether that conversion widens or narrows depends on the implementation’s width, so a word that states a direction cannot write text that is true on every implementation. narrow_try · narrow_sat · narrow_wrap, whose names choose what happens when the value does not fit, accept usize · idiff as targets.

3-4 If a literal does not fit the implementation’s usize (or idiff), translation is refused (E-TYPE-WIDTH). This is the only place among integer conversions where the verdict on the same text depends on the implementation — the value has a size not in that implementation’s address space, so it is refused earlier than a trap during execution. Refusals of text that uses what a target lacks (§5.6 (4) · (4-2) — heap · floating point · 128-bit integers · atomic widths) are outside this sentence.

Caution — Text that does not rely on the width of usize

For the same text to stand on 16 · 32 · 64-bit implementations alike — ① write only lengths · indices · byte counts as usize, and keep positions inside files · times · hashes · protocol fields in types of fixed width. ② Compute where the two meet on the wider side (add off. cast u64 len b. . . .). ③ When moving a number from outside into usize, take it with narrow_try, so that the program refuses what does not fit. ④ Arithmetic on usize overflows at its width (§6.3), so places that multiply sizes take chk_mul. ⑤ A usize field of a struct differs in size between implementations, so it is not put in a layout that goes outside. ⑥ When taking the difference between two positions as idiff, cast idiff traps in the upper half of the usize range.

Caution — 0 is not false

C-family languages treat 0 as false and everything else as true. Lowent does not. Using an integer in a condition, as in if n. do, is refused at translation — what is being asked shall be written, as in if gt n. 0 . do. If what is asked is not written in the source, the reader has to guess it.

6.2.4 Floating-point types§

1 f32 and f64 are the IEEE 754 binary 32-bit and 64-bit formats respectively.

2 Floating-point operations happen at the width of their operands. Operations between f32s are computed as f32, and the processor does not secretly compute in wider precision.

2a One operation is one rounding. The processor does not merge two operations into one rounding — it does not turn a multiply-and-add (add mul a. b. . c.) into one fused multiply-add instruction (FMA). Rounding is the single mode «to nearest, ties to even», and a program cannot change it. Code emitted as C carries this promise in its source too — it writes directives so that the C compiler building that code does not merge them itself.

3 Integers and floating-point numbers do not convert into each other automatically. To convert, it shall be written explicitly.

4 If the result of an operation is NaN, that it is NaN is fixed. The sign bit and the remaining bits of that NaN are a free choice (FC-0004).

Free choice — FC-0004 — the sign of a NaN produced by an operation

When the result of a floating-point operation (including per-lane operations and reduce_*) is NaN, its sign bit and remaining bits are chosen by the processor. That the result is NaN, and the value of every result that is not NaN, are the same either way. The difference shows when the value is printed (nan and -nan) and when it is read as bits. IEEE 754 does not fix this place either, and machines and C compilers give different signs where two NaNs meet or at 0.0 / 0.0. Nailing it to one side would add a correcting instruction to every operation. To know whether a value is NaN, compare it with itself, as in ne x. x. — do not ask its sign.

6.2.5 Conversions between types§

1 Lowent has no implicit conversion that loses a value. A narrowing place is always written in the source. The only conversion the processor does by itself is the widening below; the word that writes any other conversion is cast (§6.2.16).

2 A conversion that loses no value is called widening. Widening does not change the value, so the processor may do it automatically — a u8 value may be passed as it is to a place that takes u32.

2a But widening may also be written in the source. widen u64 x. . widens x to u64. Even though the result is the same, it is used when the place where the width changes should be visible.

2b Widening to 128-bit integers (u128 · i128) is not automatic — it shall always be written with widen (§6.2.2 (3b-1)).

In plain words

In short — widening is automatic, narrowing is by hand. Widening keeps the value, so there is no room for mistakes, but narrowing can make a value disappear, so the author shall leave in the source that they know it.

3 A conversion that may lose a value is called narrowing and is written with narrow. Narrowing traps if the value does not fit the target type. It is not truncated silently.

4 The relations in which widening is allowed are as follows. A combination not listed here is not widening, and writing it is refused at translation (E-WIDEN-KIND · E-WIDEN-SIGN · E-WIDEN-NARROW).

6.2.6 Rows — arrays and slices§

1 array n t is a row of exactly n values of type t. The length is part of the type and is fixed at translation time.

1a Write the length n first, as an integer literal, and the element type after it — the same order as vec n t · matrix k d… t. Since the element type comes at the very end, the type knows its own end. Written the other way round (array t n — a type in the length position), it is refused (E-TYPE-ORDER; lowentc --fmt moves it to the new order). If the length is not a literal, it is refused (E-TYPE-ARRAY).

1b An op input input x array n t . means that it takes a slice t of length exactly n, and that length is checked at entry, like requires eq len x. . n. . ..

1c An op can return an array — output array n t ., or with a name, output r array n t . (§6.4.1 (3e)). An array has no way of being returned as a value, so the caller provides the place:

  • The caller binds the result to a name — var x array n t f a … . (let is the same). The bytes in that name’s frame are the place of the result,

and the callee builds directly there (it does not copy).

  • Inside an op that returns the same kind of array, return g … . passes on its own place as it is. But if an argument given to g can see the same bytes

as that place (the named result itself, or a name derived from it — a local whose initialiser or set right side mentioned it), the processor takes it into a temporary place and copies once — while g writes, the reading side does not see new values, so the answer is the same as when they do not overlap. It passes the place on directly only when they are seen not to overlap (when the arguments mention no such name). A return outside a block (guard … else return …) has no place to insert a statement, so this rule does not stand there — the E-RESULT-PLACE below applies as it is.

  • Calling an op that returns an array in any other place (the middle of an expression · an argument of another call · the source of copy) has no place, so

translation is refused (E-RESULT-PLACE). Bind it to a name first.

  • A named result starts at 0 (0 in every slot). return v. . of an unnamed result copies v into the place and returns. This shall be a return

inside a block — outside a block, as in guard … else return v. . ., it is refused (E-RESULT-PLACE). Such an op names its result.

  • The elements are of number types and the length is an integer literal (anything else is E-TYPE-ARRAY).

1d Arrays inside arrays — the element type may itself be an array. array n array m t is a row of n rows of length m laid out row-major without gaps (the same layout as C’s t a[n][m]). Since the element type comes at the very end, no parentheses are needed ((1a)).

  • idx a. i. . is a slice t (length m, no copy) that sees the bytes of row i — it follows the same rules as the sequence of rows of (9a). If the outer

one is mut, the slots of that row can be written too, and there is no set idx a. i. . <row> . that replaces a whole row (E-TYPE-SET).

  • An op input input x array n array m t . takes a slice of rows slice array m t, and that the number of rows is n is checked at entry ((1b)).

A sequence of rows, and a row view over bytes (§8.7 (7a)), can be passed as they are.

  • As a struct field it holds the bytes of n × m elements inside the record (the same as the array field of §6.2.7 (1a) — copying the struct copies them too).
  • A value is built with lit array n array m t <row>… [_] .. Each row is lit array m t …, and a final _ fills the remaining rows with 0 ((6a)).
  • The elements are sized numbers and bool. There is no limit on the number of levels — array 2 array 3 array 4 u8 is 2 planes of 3 rows of length 4 (C’s

u8 a[2][3][4]), and idx a. i. . is a slice of rows slice array 4 u8 that sees plane i. Each idx peels off one level. The rows of a sequence of rows · of a row view can also be arrays inside arrays (slice array 3 array 4 u8 · view_array array 3 array 4 u8 b.).

  • The depth of levels is part of the type — passing or binding a slice of rows of a different depth is refused (E-TYPE-ARG · E-TYPE-LET). A slice of rows

does not fit a place for a slice of elements either (idx gives a row instead of a number).

  • An op can return an array inside an array too — output r array n array m t .. As in (1c), the caller provides the place (var x array n array m t f … .),

and a named result starts as rows of 0.

6 Element-list literals — lit array n t v₁ … vₖ . is an array n t value, and lit slice t v₁ … vₖ . a slice t value of k elements. A list is a form closed by its own full stop: at the end of a statement the list’s dot and the statement’s dot come one after another (let t lit array 4 u8 1 2 3 4 . .); in the middle it is closed with one dot and the next operand follows. Since lit shows the type of the value, the binding statement does not write the type separately.

6a The number of array elements shall equal n. If there are fewer, a _ shall be written at the end of the list to say «the remaining slots are 0»; if there are more, or _ is somewhere other than the end, or a slice list has _, it is refused (E-LIT-COUNT). Slots are not filled silently.

6b Each element shall fit t — a negative number does not fit an unsigned t either (E-TYPE-WIDTH). bool elements are only true · false.

6c Filling chosen slots — lit array n t do <index> <value> . … [_ <value> .] end . puts each value into the slot whose index is written. The indices are integer literals from 0 to n − 1, each written once. _ <value> . comes only at the end and means «every slot whose index is not written». Every slot shall be decided — if slots remain and there is no _ <value> ., or _ has no slot to fill, it is refused (E-LIT-COUNT). If an index is not a constant, is outside the length, appears twice, or _ is somewhere other than the end, it is refused (E-LIT-INDEX). Values may be expressions and are computed in the order written; the value of _ is computed once. A list written as a block is a form too and is closed by its own dot — in let t lit array 8 u8 do 2 5 . _ 0 . end . . the first dot closes the list and the second closes let. It is not mixed with the form that lays out elements in a row

6d SIMD values — lit vec n t v₁ … [_] . is a vec n t value. The type of the value shall agree with the vec type of the binding place in number of lanes, element kind and width (E-TYPE-LANES · E-TYPE-WIDTH). Since it ends with placing values into lanes, the place rules of (7) do not concern it.

The receiving op may rewrite those slots.

Free choice — FC-0003 — whether read-only lists with the same contents are the same place

The processor may merge two read-only lists with the same contents (a string literal is a list too) into one copy at the same place, or keep them apart. Those two are the only range of choice — the contents and length of the list, and that it lives to the end of the program, are the same either way. There is one place where the difference shows — same_slice, which asks whether two lists are the same place. So if it is visible at translation that both sides came from such literals, the question is refused (E-LIT-IDENTITY), and where it is not visible, a program that relies on the answer does not conform. To know whether the contents are the same, compare the contents — do not ask about the place.

7a If a value that sees a slot of ⓐ · ⓒ is put in a place that lasts longer than its lifetime — return, a name declared outside the declaring block (including parameters and their fields · elements), a message sent to an actor declared outside the declaring block — it is refused (E-LIT-ESCAPE). It may be handed to an actor declared in the same block or further in, and the values that actor gives afterwards receive the same lifetime. Putting a temporary of ⓒ into a name is refused too — bind the list with var and use it as ⓐ. The flow is followed across calls: the result of a call carries only what belongs to the inputs that flow into the result in that op’s body, and a call that returns a scalar carries nothing out (the same distinction as region escape in §8).

7a-1 An unnamed struct value (the result of a call · lit) ends at the end of its statement. Putting a value that sees an array field of that value into a name · return · an outer place is refused (E-VIEW-TEMP) — once the statement ends, those bytes belong to the next value made. Only reading on the spot (taking numbers out with len · idx) conforms. To see a field for long, bind the struct to a name first (let b T … . and then field b. <field> .).

7b A list bound with var is a writable slice — slots are written with set idx buf. i. . v. .. set buf …, which rebinds that name to other storage, is refused (E-ARRAY-SET). Each element follows the width rule of (6b), and elements computed during execution shall agree with the element type (E-TYPE-SET · E-TYPE-WIDTH). A slot reached through idx and subslice is the same storage too — in set idx subslice buf. a. b. . i. . v. ., if buf is not a writable name it is refused (E-TYPE-MUT). 7b-1 Copying contents — copy <receiver> <giver> . copies the contents of the giving slice into the receiver. This processor’s limit is 65,536 bytes on a machine with an operating system · 4,096 bytes on a machine without one. If an op with such slots can reach itself (even through other ops), it is refused (E-FRAME-RECURSIVE) — frames multiply by the recursion depth, and that depth is not known at translation, so it cannot be shown that the stack does not run out. A list inside recursion is taken from an allocator ((7d)). Ops that run as tasks (spawn <op> · the handler of spawn send) are measured separately against the green-thread budget. During execution, too, the sum of ⓐ · ⓒ slots and the struct slots of (7c-1) alive at the same time on one call chain has a budget the processor states, and it stops rather than enter an op that would exceed it — the stack does not overflow and break silently. In plain words

In a language with only pointers, a person has to know separately “how many are there where this pointer points”. That knowledge is not written in the source, so it is easily wrong, and when it is wrong someone else’s memory is read. A slice removes the problem by putting that knowledge inside the value.

6.2.6.1 Rows of several dimensions — matrix§

1 matrix k d1 … dk t is a row of k dimensions holding d1 × … × dk values of type t. The number of dimensions and the sizes are part of the type and are fixed at translation. If even one of the number of dimensions or the sizes differs, it is a different type — matrix 2 3 4 u32 differs from matrix 2 4 3 u32 and from array 12 u32.

1a Write the number of dimensions first, then as many sizes as there are dimensions, and the element type at the very end (the same order as §6.2.6 (1a)). The number of dimensions is from 2 to 8 and the sizes are 1 or more, all plain decimal literals (in an op input a size may be the name of a translation-time value input — (3a)). The old order (matrix t k d… — element type first) is refused (E-TYPE-ORDER). The number of elements (the product of the sizes) cannot exceed 2^32. matrix or array cannot be written as the element type. Violations are refused (E-MATRIX-TYPE).

Note (informative)

Since the number of dimensions is written first, where the sizes end is known from the characters alone (a size may also be the name of an input). Even when elements follow (lit matrix 2 2 3 u32 1 2 3 4 5 6 .), where the sizes end and the elements begin is separated by the characters alone.

2 Layout. The elements are laid out contiguously in one block, row-major — the last index runs fastest. Size and alignment are the same as array n t (n is the product of the sizes), and no header is added.

Note (informative)

This layout is the same as C’s t a[d1]…[dk]. Passing flat m. . to an extern op with a slice t input, C receives a pointer and the number of elements, and reading that pointer as t (*)[d2]…[dk] points at the same slots.

3 A matrix type is written in places that make a name — the type of let · var, an op’s input and output, a struct field. It cannot be written as the element of another type, as a type argument or in the place of an alias (E-MATRIX-USE).

3a Only in an op’s input, the name of a translation-time value input of that op can be written in a size position — input comptime r u64 . input comptime c u64 . input m matrix 2 r c u32 .. The caller writes a number for that input (sum 3 4 a. .), and the shape of the argument shall be the same as the shape read with those numbers (E-MATRIX-SHAPE). The sizes of let · var · output · struct fields and of lit matrix shall be numbers (E-MATRIX-TYPE).

Note (informative)

An input that takes its sizes by name gets no entry contract on its length. What can come in that place is only a matrix whose shape the caller compared, and reading and writing elements receive the checks of (5) unchanged.

4 Values. lit matrix k d1 … dk t <element>… . lists the elements in row-major order. The number of elements shall equal the product of the sizes; if there are fewer, write _ at the end to fill the rest with 0. If a binding writes both a type and a literal, the two shapes shall be the same. Violations are refused (E-MATRIX-SHAPE). In a struct literal, the value of a matrix field is a lit matrix of the same shape as that field.

5 Reading and writing. idx m. i1 … ik . takes one index per dimension. If the number of indices differs from the number of dimensions, it is refused (E-MATRIX-INDEX) — an idx with fewer indices does not mean a row (a row is the row of (7a)). Each index is checked against the size of its own dimension: if any one of them is that size or more, execution stops. Index expressions are computed once each, in the order written. set idx m. i1 … ik . v. . writes that slot, and m shall be a writable name (E-TYPE-MUT).

6 dim m. j . is the size of dimension j (counting from 0). j shall be a plain decimal literal less than the number of dimensions (E-MATRIX-INDEX). Its value is a translation-time constant.

7 flat m. . is a slice t that sees the same elements as one row. It does not copy, and its length is the number of elements.

7a row m. i1 … i(k−1) . is the row that leaves one last dimension — one index for each dimension except the last, and its value is a slice t that sees the elements of that row. It does not copy, and its length is the size of the last dimension. If the number of indices differs it is refused (E-MATRIX-INDEX), and each index is checked against the size of its own dimension as in (5). If m is a writable name, that row can be bound to a mut slice t name and written; otherwise it cannot be bound that way (E-TYPE-MUT · E-IMMUTABLE if it is a field of a struct bound with let). There is no view that leaves two or more dimensions (a plane).

7b In the m position of (5) · (6) · (7) · (7a), not only a name written as matrix stands but also field x. g . that points at a matrix field — idx field b. g . r. c. ..

8 len m. . and for x m. do … end . are refused (E-MATRIX-USE). The size of one dimension is written with dim, and going over all elements with for x flat m. . do … end ..

9 The places where a matrix name can be written whole are the first argument of idx · row · dim · flat, an argument of an op with an input of the same shape, and the return of an op with a result of the same shape. Other places are refused (E-MATRIX-USE). Arguments and inputs, and the type of a binding and the result of the op called, shall agree in both number of dimensions and sizes (E-MATRIX-SHAPE).

9a A call of an op whose result is a matrix is placed in only two places — the value of a binding that makes a matrix name of the same shape, and the value of the return of an op with a result of the same shape. The return of an op whose result is a matrix gives a matrix name of that shape or a call of an op that gives that shape. 6.2.7 Aggregates — struct and enum§

1 A struct is a collection of named fields. Each field has its own type.

1a Array fields — if the type of a field is array n t, that field holds the bytes of n elements inside the record (since the length is in the type, the place is fixed). t is a sized number or bool — fields whose elements are structs or arrays this processor has not yet built (E-LIT-UNBUILT). The sum of the bytes of the array fields of one struct has the same limit as a frame (E-FRAME-SIZE, §6.2.6 (7c)). field r. body . is a slice that sees those bytes, and set idx field r. body . i. . v. . writes an element of the record. A list literal given to the field shall have the same element type and length as the field (E-TYPE-FIELD). In a byte layout (view · encode · size_of · the C-side layout) an array field lies as it is inside the struct bytes, as in C — its size is n × |t| and its alignment that of t (len u8 . body array 4 u8 . tail u16 . is 8 bytes — len from byte 0 · body from byte 1 · tail from byte 6). The array field of a view is a slice that sees those bytes, and writing the field copies into that place.

2 An enum is one of several. Each variant has a name and may carry values.

2a Each variant is closed with .. A newline is not a closer, so variants written one per line without dots run together into one variant and are refused (E-ENUM-DOT). The values a variant carries are written as <field name> <type> pairs — if the pairs do not match, it is refused (E-ENUM-FIELD).

2b An enum value is not a number — to use a variant’s number as a number, write cast (§6.2.16 (5)).

2c Every variant has a number. The first variant is 1, and the next variant is the number of the previous variant plus 1. An integer written after a variant name (ga 11 .) becomes that variant’s number, and the next variant counts on from there. The numbers shall increase in the order declared — a number not greater than the previous variant’s number is refused (E-ENUM-NUMBER). Numbers are written only in an enum with no variant that carries values (E-ENUM-NUMBER). 0 is not the first variant’s number — in an enum whose numbers are not written, 0 is no variant.

6.2.8 Types that hold an answer — result and option§

1 result t e holds either a successful value (t) or an error (e).

2 option t holds either a value or none.

3 Values of these two types shall be checked for which side they are before being taken out.

3a Taking out is a partial operation — taking out without checking is not itself refused at translation, and taking out the absent side during execution traps. That is, the check is not done for the author by translation; the author does it.

3b The type of the contained value is part of the type. option usize and option u64, result u32 e and result u64 e are different types, and putting one in the place of the other is refused at translation (E-TYPE-NOMINAL · E-TYPE-WIDTH · E-TYPE-SIGN). The type of a value taken out (some_value · ok_value) is the type of the contained value. When some · ok wrap a literal, it follows the type of the receiving place.

Source

  too_small .
end .

In plain words

There is a custom of using special values such as −1 or a null pointer to signal failure. Then “is this −1 an error or just −1” cannot be known from the source alone. result and option move that question into the type, so that the processor asks it instead.

4 The making side wraps values with ok (success) error (error) some (a value is present) none (no value).

5 The receiving side first asks which side it is — is_error (is it an error) is_some (is a value present). Then it takes out — ok_value (the success value) error_value (the error) some_value (the present value).

Diagram — wrap · ask · take out

 ok v  | error e  ──▶ is_error r ── false ──▶ ok_value r    = v
                                 └─ true ──▶ error_value r = e
 some v | none    ──▶ is_some o  ── true  ──▶ some_value o  = v
                                 └─ false ─▶ some_value o  → trap

6 value_or gives the value if there is one, otherwise the value given in its place. It reduces the two steps of asking and taking out to one.

7 try takes a result, takes out the value on success, and on failure passes that error on upward as it is (§6.5.7).

8 If a result is received and nobody looks at it, the processor reports it (W-RESULT-DISCARD). The design of returning failure as a value is kept only when the receiving side looks at that value. There are two shapes of not looking — calling the op as a statement and discarding the value without even a name, and putting it into a name and never reading it.

8a A place that deliberately lets a failure pass is written drop <name> .. Then it is not reported. There are places where there really is nothing to do with a failure — such as the place on an error path that closes resources and leaves. drop already means «I end this here», so no new word is put in that place.

In plain words

Why a report and not a refusal? Ignoring a failure is not always wrong — what is wrong is ignoring it silently. So what this clause requires is not «do not ignore» but «write that you ignore», and once it is written, a reader reads it as the author’s judgment. What is not written, nobody knows whether it is judgment or a mistake.

A row type shows its element type and its length · dimensions in its words. Hidden behind another name, a reader has to go to the declaration to know them — and there become two ways of writing the same type. A struct field is different: a different name makes a different type, so that name does not hide but separates.

Note (informative)

The two are separated to prevent mistakes. If user numbers and order numbers are both u64, the processor does not notice when they are swapped. Separated with newtype, the processor catches that mistake.

3 When a newtype is used as a name that separates storage (brand), one brand points at one storage. Opening storage twice with the same brand is refused (E-BRAND-REUSED) — then one name would point at two, and handles from different storage would look like the same type. That is exactly the confusion the brand was meant to prevent. If they must be separated, declare one more newtype.

6.2.10 Reading inside a value — field§

1 field is the form that reads what is inside a value. Its shape is field <value> <step> …, with one or more steps. With several steps it goes down one level at a time from left to right — field o. inner deep . means inner of o, and deep inside that.

2 A step is one of two things. A name is a field of a struct, and an integer is a position in a row (array · slice). The two may be mixed.

3 field is also a place — it can come on the left of set. The reading place and the writing place have the same spelling.

4 If a field not in the declaration is written, the processor refuses the program. Positions in rows follow the bounds rules of §6.2.6.

6.2.11 Values with lanes — vec§

1 vec <lane count> <element type> holds several values of the same type as one value (the same order as §6.2.6 (1a) — the lane count comes first; the old order vec <element type> <lane count> is E-TYPE-ORDER). scalable can also stand in the lane-count position (vec scalable u8). The lane count shall be a value fixed at translation time (§6.8).

2 Two vecs with different lane counts are different types and do not mix.

3 Arithmetic on a vec happens per lane, separately. Values do not cross between lanes.

3a The per-lane arithmetic is add · sub · mul · div · mod · neg · abs · min · max. Overflow of integer lanes wraps at the lane’s width (unlike scalars — the quotient of the smallest value of a signed lane divided by −1, and its neg · abs, are that value itself). If an integer lane’s div · mod has a lane whose divisor is 0, it stops as for scalars. The quotient is truncated towards 0, mod follows the sign of the divisor (§6.3), and min · max of signed lanes compare by sign (2026-11-02). Floating-point lanes have no mod — as for scalars, translation is refused (§6.3.3 (2a) · E-TYPE-KIND).

Note (informative)

If the machine can compute several lanes at once it does so; if not, it computes them one by one. Either way the answer is the same — the lane count is not a performance hint but part of the type.

6.2.13 An eye laid over bytes — views§

1 A byte slice can be read, without copying, as if it were an array of another type. This is called a view.

2 When a view is obtained, the alignment and length contract is checked. If the contract is broken, the program stops.

3 A view does not copy bytes. Writing through a view changes the original bytes.

Caution — A view counts its length in elements

The length of a byte slice is the number of bytes, but seen as an array of four-byte elements its length is the number of elements. Seeing the same storage with two eyes, len answers differently — because they are counting different things.

4 The opposite of a view is encode. encode <shape> <value> writes the value into bytes in the layout the shape specifies. If laying over and reading is view, writing down is encode.

5 A view laid over a struct is a window. view <struct> <bytes> gives a window that lays the layout of that struct over a byte slice. Reading a field of the window reads the bytes at that place, and writing a field writes the bytes at that place — it is not a copy. The type of a window is view T (a read window) or mut view T (a write window), different from the type T of a struct value. try_view does the same but gives none if the length · alignment do not fit or a field does not fit (9a) — its type is option view T · option mut view T, and some_value is the window. The conditions on length and alignment are specified by §8.7.2.

6 Windows and values do not mix. Putting a window in the place of a struct name T · option T — binding · returning · putting a whole struct value into a window name — is refused at translation (E-VIEW-COPY). A copy that lives apart from the bytes is made with cast T <window> . (§6.2.16 — an explicit conversion is cast). Binding a window to another window name sees the same bytes. A window can also be passed to an input that takes a value (input p T .) — the receiver only reads.

6.2.14 Parameters with a narrowed range of values — range§

1 If range <low> <high> is written in the type position of a parameter, that parameter accepts only values between the two ends, both included.

2 If the caller cannot prove that the value is within that range, translation is refused. A value that came from outside the program (an argument of the entry point and the like) has no caller to prove it, so it is checked at the boundary, and the program stops if it is out of range.

2a If the caller’s type is wider than the range, that alone is refused (E-TYPE-WIDTH). A value of the same width, which is not caught by that check, has its range checked at the op’s entry and stops if it is out of range (E-VM-CONTRACT) — the same check as writing requires ge <name> <low> . and requires le <name> <high> ..

3 A declared range is used with the same standing as a contract of §6.4 — the checker may take it as a fact and remove the checks that follow.

In plain words

(3) makes (2a) necessary. If the checker takes the range as a fact and removes bounds checks, while nobody keeps that fact, values outside the range pass through where the checks were removed. Until 2026-09-16 a range parameter of the same width was checked at no layer (defect note 10) — the only thing to trust is what is checked.

6.2.15 Nailing down the byte layout — layout and align§

1 A layout can be written inside a struct declaration. If none is written, fields are placed in declaration order, each aligned to its type’s alignment (with as much padding between as alignment requires). The processor does not change the order.

2 layout packed . puts no padding between fields — the fields are packed together in declaration order.

2a The layout words are a closed two — packed and native. Anything else is refused (E-TYPE-LAYOUT).

3 align <n> . nails down the alignment of the place where that struct begins. n shall be a power of 2. The alignment shall be a power of 2 (E-TYPE-ALIGN) — no machine can keep any other number.

marker (표지)

A word attached after a field that fixes how that field is placed and how it can be reached. It is not a type, so it does not change the size of the value; it fixes only the byte order and the way of reaching.

4 A marker can be attached after a field. The markers are these five and no more; writing any other word is refused at translation (E-FIELD-MARK).

6.2.16 Explicit conversion — cast§

1 Reading a value as another type happens only where the source says so. The only conversion the processor does by itself is widening (§6.2.5 (2)); every other conversion is written by the author with a word. The centre of those words is cast <type> <value> — cast is the word that takes charge of explicit conversion in this language. widen is used only where the value does not change, and conversions that may change the value are written with cast — places that change the sign, cross kinds, or narrow.

1a There are three words that write conversions, each with its own place.

Table 24 — The three words that write conversions

WordIts placeIf the value does not fit
widenwidening in which the value fits as it is (the table of ⟦§6.2.5⟧ (4)). The processor also does it by itself — writing it makes it visibledoes not happen

1b A conversion that could be read either way does not happen by itself; it goes through cast. That is a conversion where the same bits could be read as two numbers, or that widens or narrows depending on the target machine, or that changes the kind of the value. This rule also applies to types and conversions that enter the language in the future — if a new conversion is ambiguous its spelling is cast, and nothing is decided in the direction of adding implicit conversions.

In plain words

When conversions are written in the source, a reader can find every place where a value may change with their own eyes. Having found and read the casts, they have seen every place in that program where a type changes. If there were even one place where the processor changed it secretly, that promise would be broken. So this language has no implicit conversions for convenience. Writing them takes a little effort, but when reading there is no guessing «what changed here».

2 cast traps if the value does not fit the target type. It is not truncated silently. That is, cast is not a mark that says «anything may happen» but a mark that says “I know this is a place where the value may change”.

3 Converting a floating-point number to an integer truncates towards 0 — 7.9 becomes 7 and -2.9 becomes -2. Only the fractional part is discarded; if the integer part does not fit the target type, it traps as in (2).

Caution —

Discarding the fractional part does not trap. So cast does not violate “there is no implicit conversion that loses a value” of §6.2.5 (1) — because that conversion is not implicit. The author wrote cast, and that word itself is the mark that says «the value may change here».

3-1 A cast to a floating-point type — whether from an integer or from another floating-point type — gives the nearest value in the target type, and when two are equally near, the one whose last digit is even. Rounding happens once — converting an integer to f32 does not go through f64 and round twice. A value that rounds beyond the largest finite value of the target type becomes the infinity of the same sign, and NaN is NaN. This conversion does not trap as in (2) — a floating-point type has an infinity for an overflowing value to go to. From f32 to f64 the value is unchanged. cast f32 <f64 1e300> is +∞, and cast f32 <u64 16777217> is 16777216.

3a Between usize · idiff and other integer types the only crossing is cast (§6.2 (3-3)). This conversion is both a widening and a narrowing depending on the implementation’s width, so cast is its spelling — if the value fits it is given as it is; if not, it traps as in (2). On an implementation where the width is the same or grows, this cast leaves no check.

4 From a truth value to an integer goes by cast — cast <integer type> <truth value> is 1 for true and 0 for false. That value fits every integer type, so the trap of (2) does not happen. A floating-point type is not a target of this conversion (E-TYPE-KIND).

4a There is no cast from an integer to a truth value — bool cannot be the target of cast (E-TYPE-KIND). Write what is being asked: ne n. 0 . or eq n. 0 .. Which values of the number are true is decided by that question.

4b Truth values are not in the table of widen (§6.2.5 (4)) — widen <integer type> <truth value> is refused (E-WIDEN-KIND). The spelling that turns a truth value into a number is cast alone.

6.2.17 What holds characters — a string is not a type§

1 This language has no string type. What holds characters is a piece of bytes (slice u8), and that is all.

2 So the length is the truth. A mark that signals the end of a string (a null byte) is not part of the value, and scanning the bytes to count the length does not happen.

In plain words

A null-terminated string is a design that hides the length inside the value. So to know the length one has to scan, and if the mark is missing while scanning, what lies beyond is read — in practice the most common memory accident came from here. A piece carries its length outside, so that accident has no place to stand.

3 The null-terminated shape is needed only where C is met (§6.9.2). It is a shape built at the boundary, not a type this language has.

4 Handling characters — cutting · searching · joining · Unicode checks — is the work of libraries (§9.5). The processor knows only pieces and bytes.

6.2.18 Type names without meaning§

1 Some names are accepted but have no meaning. If such a name is written in a signature, the processor warns (W-NOT-YET). Those names are gathered in annex A.9 (2) — names such as byte · char · str · string · bytes_view · dyn · atomic.

2 Having no meaning means that the processor does not know the shape of the values that name holds. Neither the size, the layout, nor what can be done with the value is fixed, so checks that rely on that name do not stand.

Caution —

This is why this place shall speak. Translation passes and answers come out, so the checks that did not stand show nowhere. What silently dropped out, nobody finds — so the processor says so.

3 There are two ways to give a name meaning: write the underlying type directly, or declare that name (type str option u64 .). Once declared, it has a meaning, so there is no warning.

1 The variants of an enum can carry values. When writing a variant, the names and types of what it carries are written with it.

2 The shape that builds such a value is <enum>.<variant>, and it gives all of what the variant was declared to carry. If something is missing it is refused (E-ENUM-ARITY) — a half-built value is not made silently.

  guard isa m. data . else return 0 . .
  let d bytes payload m. data d . .
  return len field d. b . . .
end .

  let m msg msg.data lit bytes do b s. . end . . .

  let m msg msg.dot lit pt do x 1 . y 2 . z 7 . end . . .

6 If an enum carries itself as a value, its size is not fixed, so it is refused (E-ENUM-INFINITE). A recursive structure is built by putting something in between.

In plain words

A variant that carries values is not a new construct. There is just one field that indicates the variant and an aggregate holding what the variant carries; building is building an aggregate, and reading is reading a field. So this feature added not a single machine instruction — it lowers to what already existed, so it ran on both back ends by itself.

6.2.20 Seeing scattered pieces as one — segments§

1 Several pieces that are not contiguous can be seen with one eye. It consists of two things: the bytes lying behind, and a descriptor that says where in them and how much.

Table 26 — The ops that handle scattered pieces

opShapeWhat it does
view_segmentsview_segments <bytes> <descriptor>binds the two into one eye

1a An eye is an aggregate holding the fields back (the bytes behind) and descs (the descriptor). The number of pieces and the piece of a number are written by reading and cutting those fields, so they are not operations of the language but ops of the standard module segview (§9.3).

2 A descriptor is a piece holding pairs of «from where» and «how much». So these three add neither a new type nor a new machine instruction — they lower to building an aggregate, reading fields and cutting.

In plain words

Without a way to handle scattered pieces, the user has no choice but to gather them into one place. Gathering is copying, and copying where it need not be done is the cost this language sets out to remove. Given an eye, the copying disappears.

6.2.21 Fetching ahead — prefetch§

1 prefetch <piece> <number> tells the machine that the bytes at that place will be used soon.

2 This is only a hint. It leaves no value and does not change the meaning of the program, and if the machine ignores it, the answer is the same.

Caution —

A hint is a hint only if being wrong does not make the program wrong. Something that changes the meaning is not a hint but a command, and such things do not come in this place.

6.2.22 What it means for types to match§

1 In every place where a value is put, the type of the value shall be the same as the type that place states.

2 Aggregates and enums are declared with struct <name> do … end . · enum <name> do … end .. Trying to declare them in another shape is refused (E-TYPE-DECL).

In plain words

The seven in this table are all different places of the same sentence — the source wrote “the type of what comes here is this”, and the processor compares what is written with what actually comes. There is a separate diagnostic for each place because where it mismatched is the fact the person fixing it needs most.

6.2.23 The shape of writing fields§

1 A field of an aggregate is a name followed by a type (x u64 .). Anything not in that shape is refused (E-FIELD-FORM).

2 A field is read with field <value> <name> …. The old spelling that reads with an attached dot does not exist in this language (E-FIELD-GLUED).

3 A vec and a mask are values themselves, and pointing or borrowing markers cannot be attached to them (E-VEC-QUAL). Their lanes are positions inside a word, not positions in memory.

6.2.24 Integers of arbitrary width — bits§

1 type <name> bits <number> . makes an integer type with that many bits. The width is from 1 to 64.

2 The width need not be a power of 2 — bits 3 and bits 10 both stand.

Caution —

If the width does not match the machine word, speed is not guaranteed. What this language guarantees is correctness — bits 10 gives the answer computed in ten bits, but it does not say that this is faster than a sixteen-bit computation. To avoid making places whose cost is invisible, what is not guaranteed shall be written down as not guaranteed.
